MOTORLAB VELOCITY LAYER V1 - ADAPTIVE IDEA-TO-ARTIFACT ACCELERATION

STATUS
Mandatory MotorLab CORE capability for accelerating project work without weakening existing safety, lifecycle, verification or governance controls.
Established: 2026-09-29.

PURPOSE
Minimize the real elapsed time between Bruno expressing an idea/change and obtaining the first useful verified testable artifact (APK/ZIP/build/result), while preserving every existing MotorLab capability and protection. MotorLab complexity is justified only when it improves net execution: faster delivery, less manual work, less wasted work, fewer defects or materially better artifact quality.

FOUR DESIGN PILLARS - R21+
Every MotorLab optimization, past or future, is evaluated against four permanent design pillars:
1. ENGINE EFFICIENCY — minimize redundant reads, duplicate computation, unnecessary provider/tool calls, idle waits and repeated setup.
2. AUTOMATION / PROGRAMMING FACILITATION — remove avoidable manual coordination, repetition and re-entry of already-known technical decisions.
3. FINAL ARTIFACT QUALITY — produce stable, correct, compatible and appropriately verified artifacts with fewer avoidable regressions.
4. EXECUTION SPEED — PRIMARY OPTIMIZATION PRIORITY: minimize end-to-end elapsed time from request/approval to a useful testable artifact.

Speed is the primary optimization target, but not permission to violate safety, correctness, security, data integrity, signing/package identity, explicit approval, project-native authority or required final promotion gates. Between two equally trustworthy approaches, prefer the one with lower time-to-artifact, lower coordination overhead and greater automation.

NON-NEGOTIABLE PRINCIPLE - ADDITIVE ONLY
Velocity Layer is strictly additive.
It MUST NOT remove, replace, weaken, bypass, redefine downward or silently skip any existing MotorLab capability, including but not limited to:
- MADRE -> LAB -> CANDIDATA -> NEW MADRE lifecycle;
- MADRE immutability and historical rollback;
- atomic LAB scope;
- exact Candidate replay/promotion identity;
- explicit approval requirements;
- regression gates;
- Watchdog/anti-stall;
- heartbeat/progress fingerprint;
- checkpoint/recovery;
- single-writer lock;
- verified progress reporting;
- Visual Status;
- Background Execution / Single-Chat Continuity;
- cost-aware routing/cache policy;
- External Service Guard;
- structural/intent auto-bootstrap;
- project-native engine coexistence.

If a Velocity optimization conflicts with an existing MotorLab rule, the existing safety/governance rule wins and the optimization is disabled or degraded for that operation.

CORE GOAL
Make MotorLab less serial, more adaptive and measurably faster without becoming less safe.
The preferred acceleration pattern is:
UNDERSTAND ONCE -> BUILD DEPENDENCY GRAPH -> PRIORITIZE CRITICAL PATH -> FAN OUT INDEPENDENT RUNNERS -> CONTINUOUS COMPATIBILITY CONVERGENCE -> SINGLE INTEGRATION LANE -> VERIFY BY RISK -> ARTIFACT -> LEARN FROM EVIDENCE -> KEEP FULL PROMOTION SAFETY.

Global barriers are avoided when dependencies do not require them. A downstream task may start as soon as its own prerequisites are satisfied; it does not wait for unrelated runners merely because they belong to the same operation.

1. PROJECT SNAPSHOT
For onboarded projects, MotorLab should maintain/reconstruct a compact current project snapshot when technically possible.
The snapshot may include:
- project/repository identity;
- current approved MADRE ref/SHA;
- lifecycle branch conventions;
- major modules/components;
- important UI/runtime/service entry points;
- build/test commands;
- package/signing rules;
- external providers/services;
- regression-critical functions;
- adapter/routing state;
- recent approved change areas;
- known protected/blindata components;
- toolchain/dependency state sufficient for planning.

SNAPSHOT SAFETY
- Snapshot is an acceleration index, not source-of-truth replacement.
- Before any write, source ref/SHA and relevant files must be revalidated against the repository/current authoritative state.
- If snapshot baseline SHA differs from current authoritative SHA, invalidate/rebuild affected snapshot portions before writing.
- Never make a risky write from stale snapshot assumptions.
- Sensitive secrets are never stored in the snapshot.

2. CHANGE CAPSULE
Each concrete change request should be normalized into a compact Change Capsule containing, when determinable:
- user goal;
- requested visible behavior;
- project/lifecycle target;
- likely affected components/files;
- explicit protected/non-target areas;
- acceptance criteria;
- risk class;
- required service/provider constraints;
- minimum relevant checks for LAB;
- mandatory promotion checks that remain unchanged;
- whether user approval is already present.

The capsule reduces repeated re-interpretation of the same request during planning, writing, testing and recovery.

3. QUESTION MINIMIZATION
MotorLab should ask Bruno only for information whose absence materially changes architecture, behavior, safety, cost, privacy, irreversible state or the requested result.
When a detail can be safely derived from current project state, adapter, existing conventions or the explicit request, derive it instead of asking a redundant question.
Never invent a consequential requirement merely to avoid a question.

4. PRE-APPROVAL READ-ONLY PREPARATION
When project workflow requires Bruno to approve a modification before write-capable work, MotorLab may prepare read-only work before that approval, including:
- identify current MADRE/source baseline;
- locate likely files/components;
- inspect relevant code/config;
- inspect current adapter/routing/service constraints;
- form Change Capsule;
- identify regression-critical neighbors;
- prepare a proposed patch plan/diff outline;
- warm safe metadata/tooling caches where no project state is mutated.

It MUST NOT modify project source, branch state, releases, external production state or other write-capable resources before the required approval.
After approval, reuse the verified preparation rather than restarting analysis from zero, subject to source revalidation.

5. SAFE PARALLEL READ-ONLY ANALYSIS
MotorLab should parallelize independent read-only preparation where the execution surface permits it, for example:
- source inspection;
- dependency/config inspection;
- adapter/routing lookup;
- documentation lookup;
- service/provider limit lookup;
- test inventory/regression mapping;
- artifact/history inspection.

Single-writer remains mandatory. Parallel analysis may not create competing writers or two independent patch interpretations against the same target.

6. FAST LAB PATH
FAST LAB is an accelerated way to reach a testable LAB, NOT a new lifecycle state and NOT a shortcut around Candidate/MADRE safety.

Eligibility requires all of the following:
- current MADRE/source baseline is identified and protected;
- requested change fits atomic LAB scope;
- exact change target is sufficiently understood;
- required approval is present;
- no unresolved high-risk ambiguity remains;
- adapter permits the selected fast mechanics.

FAST LAB may accelerate:
- branch/ref preparation;
- targeted patch application;
- incremental build/test;
- safe cache reuse;
- feature-focused smoke checks;
- generation of an installable/testable artifact.

FAST LAB MUST NOT:
- edit MADRE directly;
- skip source identity checks;
- skip single-writer locking;
- weaken External Service Guard where providers are involved;
- silently broaden the requested scope;
- promote directly to CANDIDATA/MADRE;
- declare 100% before requested LAB result is verified.

7. RISK CLASSIFICATION
Before selecting fast mechanics, classify the requested modification using evidence from the actual project.

LOW RISK examples may include:
- text/copy changes;
- isolated styling/layout changes with clear boundaries;
- non-sensitive static assets;
- isolated configuration changes with deterministic validation.

MEDIUM RISK examples may include:
- ordinary feature logic;
- API integration adjustments;
- navigation/state changes;
- non-critical persistence changes;
- build/dependency updates with contained scope.

HIGH RISK examples may include:
- authentication/authorization/security;
- signing/package/update identity;
- destructive database/schema migration;
- payment/billing;
- production data mutation;
- lifecycle/promotion infrastructure;
- core playback/runtime/geospatial engine changes with broad blast radius;
- concurrency/background/job integrity;
- secrets/credentials;
- changes touching protected/blindata areas.

Risk class is a planning accelerator, not permission to skip mandatory promotion checks.
When uncertain between classes, choose the safer higher class until evidence justifies lowering it.

8. LAB VERIFICATION BY RISK
Velocity Layer may scale the FIRST LAB verification depth to risk while preserving final promotion requirements.

LOW RISK LAB:
- diff/scope verification;
- syntax/static validity where relevant;
- requested feature check;
- minimal critical smoke gates affected by the change.

MEDIUM RISK LAB:
- all LOW checks;
- targeted unit/integration checks;
- relevant service/provider checks;
- adjacent regression smoke gates.

HIGH RISK LAB:
- full applicable preflight from the beginning;
- broader regression/security/integrity checks;
- no reduced verification path where failure impact is high.

CANDIDATA/MADRE RULE
Before promotion, the existing full adapter-defined regression gates, exact Candidate reconstruction and approval rules remain mandatory regardless of LAB risk class.

9. BUILD READINESS / CACHE REUSE
MotorLab should reduce setup latency by keeping safe reusable build readiness when technically supported:
- persistent Gradle/npm/tool caches;
- dependency/tool download caches;
- reusable non-secret generated intermediates when compatible;
- incremental build outputs where the build system safely supports them;
- preflight/toolchain metadata;
- known build command/variant/package mappings.

Do not reuse incompatible/stale build state merely for speed.
Cache keys/invalidation must remain dependency/toolchain/source-aware.
A cold build remains acceptable when safety requires it.

10. DELTA-SCOPED INSPECTION
For a small approved change, inspect and test the smallest proven affected surface first rather than rereading/rebuilding unrelated areas by default.
Expand scope automatically when dependency/blast-radius evidence indicates the change crosses boundaries.
Promotion verification still follows full adapter gates.

11. PRECOMPUTED REGRESSION MAP
Adapters may define a map from component/change category to minimum relevant LAB smoke checks.
Examples:
UI copy -> screen render/navigation smoke;
API client -> service guard + parsing + fallback smoke;
playback -> playback/start/stop/background smoke;
persistence -> read/write/migration smoke.

This map accelerates test selection but cannot remove the canonical full regression gates required before promotion.

12. ONE-PASS TOOL/FILE GATHERING
When supported, gather independent required read-only inputs in one planning phase instead of repeated serial lookups.
Avoid re-fetching unchanged canonical files during the same operation unless freshness evidence requires it.

13. NO RE-ANALYSIS LOOP
Once a Change Capsule and source baseline are verified, downstream phases should reuse them.
Re-analysis from scratch occurs only when:
- Bruno materially changes the request;
- source baseline changed;
- new evidence contradicts prior assumptions;
- Watchdog/checkpoint recovery requires revalidation;
- safety/governance requires it.

14. APPROVAL CONTINUITY
If Bruno already approved the clearly described scope, MotorLab must not ask for the same approval again merely because execution moved between tools/executors/phases.
A new approval is required only when the scope materially changes, a new consequential decision appears, or an existing governance rule requires it.

15. FAST FAILURE
Detect deterministic blockers as early as possible before expensive build phases:
- missing required file/ref;
- incompatible dependency/toolchain declaration;
- absent signing/build input;
- malformed config;
- unavailable required provider/permission;
- stale snapshot/source mismatch;
- conflicting active writer.

Fail early with preserved state rather than spending time on a build known to be invalid.

16. WATCHDOG INTEGRATION
Velocity Layer never replaces Watchdog.
Fast preparation/build still uses heartbeat, progress fingerprint, bounded retry and checkpoint recovery.
A faster path that becomes stalled is handled exactly by MOTORLAB_WATCHDOG_V1.txt.

17. EXTERNAL SERVICE GUARD INTEGRATION
Velocity Layer must not accelerate API/provider work by increasing request pressure.
Any provider-dependent optimization must remain inside MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt budgets, queues, cache, deduplication, backoff, circuit and policy rules.

18. BACKGROUND EXECUTION INTEGRATION
Read-only preparation, cache warming, deterministic build/test and other backgroundable steps may be handed to durable executors when allowed.
Velocity Layer should overlap safe preparation with durable work where dependencies permit, while preserving canonical-chat continuity and single-writer safety.

19. PROGRESS REPORTING
Speed optimizations do not fabricate progress.
Report verified micro-milestones using MOTORLAB_PROGRESS_REPORTING_V1.txt.
A shorter path may legitimately reach milestones sooner; percentages still represent verified completion only.

20. PROJECT ADAPTER FIELDS
New/updated adapters may declare:
MOTORLAB_VELOCITY_MODE=<off|safe|aggressive-safe|custom>
MOTORLAB_PROJECT_SNAPSHOT=<supported|rebuild-on-demand|none-with-reason>
MOTORLAB_SNAPSHOT_INVALIDATION=<sha|manifest|custom>
MOTORLAB_FAST_LAB=<supported|conditional|forbidden>
MOTORLAB_RISK_MODEL=<default|custom>
MOTORLAB_INCREMENTAL_BUILD=<supported|conditional|none>
MOTORLAB_REGRESSION_MAP=<path/description>
MOTORLAB_PREAPPROVAL_READONLY=<allowed|restricted|none-with-reason>
MOTORLAB_PARALLEL_READONLY=<allowed|restricted|none-with-reason>
MOTORLAB_PARALLEL_EXECUTION=<adaptive|read-only|isolated-write|off-with-reason>
MOTORLAB_MAX_RUNNERS=<auto|N>
MOTORLAB_CONTINUOUS_CONVERGENCE=<supported|conditional|none-with-reason>
MOTORLAB_LEARNING_LOOP=<supported|d1|git-fallback|none-with-reason>
MOTORLAB_TIME_TO_ARTIFACT_METRICS=<supported|partial|none-with-reason>

Legacy adapters remain valid; MotorLab may use conservative default Velocity behavior until adapter-specific fields are added.

21. MINIMUM VELOCITY VERIFICATION CHECKS
For implementation/adoption, verify when applicable:
1. snapshot source SHA mismatch invalidates stale planning;
2. pre-approval preparation performs no project writes;
3. parallel preparation creates no conflicting writer;
4. Change Capsule preserves requested/protected scope;
5. LOW-risk change receives required LAB checks;
6. HIGH-risk change cannot enter reduced verification path;
7. FAST LAB starts from protected current MADRE/baseline;
8. FAST LAB cannot promote directly to MADRE;
9. Candidate still requires exact replay + full adapter regression gates;
10. cache/incremental reuse invalidates safely on incompatible inputs;
11. External Service Guard remains active for provider-dependent work;
12. existing Watchdog/checkpoint/progress/background rules continue operating.

22. SUCCESS CRITERIA
Velocity Layer is active when:
- idea/change request is converted quickly into a stable Change Capsule;
- redundant questions/re-reading are reduced;
- safe read-only work is parallelized;
- approval does not cause analysis to restart from zero;
- small/medium changes reach a testable LAB faster;
- risk scales LAB verification without weakening Candidate/MADRE gates;
- build readiness/cache reduce avoidable setup time;
- every previous MotorLab capability remains intact and authoritative.


23. PRIMARY KPI - TIME_TO_TESTABLE_ARTIFACT
The primary Velocity KPI is TIME_TO_TESTABLE_ARTIFACT (TTTA): elapsed wall-clock time from the earliest valid execution start for an approved/requested operation to the first verified testable artifact/result that satisfies the requested LAB-level acceptance gate.
Where measurable, also record phase timings such as planning/preflight, waiting, source modification, targeted verification, build/package, integration and artifact verification.
Do not game TTTA by emitting an unverified artifact, skipping required safety or moving necessary work outside the measured operation.
For defects using Artifact-First, causal closure may continue after TTTA while MOTORLAB_OVERALL_PROGRESS remains below 100%.

24. COMPLEXITY BUDGET - COMPLEXITY MUST PAY RENT
Every new MotorLab mechanism, check, service, runner or orchestration layer must justify its runtime/coordination cost against at least one of the four design pillars.
Prefer extending an existing responsible mechanism over adding a new always-on layer.
Do not run a capability merely because it exists. Activate it on demand when the current dependency/risk graph makes it useful.
If a new mechanism repeatedly increases TTTA or coordination overhead without necessary quality/safety benefit, simplify, merge, disable-by-default or supersede it under Change Compatibility Guard.
A more sophisticated MotorLab should feel simpler and faster to Bruno, not slower.

25. ADAPTIVE DAG / CRITICAL-PATH SCHEDULER
For non-trivial eligible work, normalize the Change Capsule into a dependency graph (DAG) of bounded tasks.
Each task should identify, when relevant:
- objective/output;
- prerequisites;
- affected resource/file/component scope;
- read-only or write-capable status;
- risk class;
- estimated/learned cost;
- required verification;
- integration contract;
- whether it blocks TTTA.
Prioritize the CRITICAL PATH: tasks whose completion directly determines artifact readiness receive first access to scarce executor/build resources.
Independent tasks should run as soon as their own prerequisites are satisfied instead of waiting at unnecessary whole-operation barriers.

26. ADAPTIVE RUNNER FAN-OUT
Runner count is chosen by expected net latency reduction, not by a fixed maximum or the belief that more agents are always faster.
Use one runner when decomposition/coordination overhead would exceed expected savings.
Use multiple runners when tasks are genuinely independent or can be isolated with explicit interfaces.
Scale runner count using available executor capacity, cost/quota, historical evidence, shared-resource contention, build-system characteristics and operation risk.
Do not create runner fan-out that overloads external providers, shared caches, build machines or repository write surfaces.

27. RUNNER ISOLATION + SINGLE INTEGRATION LANE
Parallel read-only work may share the same authoritative baseline.
Parallel write-capable work is allowed only when the execution surface can isolate mutations by non-overlapping resource scope or separate controlled ref/branch/worktree/ephemeral workspace and when the project adapter permits it.
No two runners may mutate the same ref/resource scope concurrently.
Each runner must receive an explicit scope and protected/non-target boundary.
The state that will produce the final artifact has ONE integration coordinator / SINGLE INTEGRATION LANE. Runner outputs are proposals/isolated changes until accepted by that coordinator.
This extends single-writer safety rather than bypassing it.

28. CONTINUOUS CONVERGENCE - NO UNNECESSARY GLOBAL BARRIERS
Do not wait for every runner before checking compatibility when partial results can already be validated.
As runner outputs become ready:
- validate interface/contracts against the current integration baseline;
- detect overlapping files/resources/behavior early;
- run the smallest useful compatibility/static/targeted checks;
- integrate independent compatible results when safe;
- update downstream DAG readiness;
- preserve evidence and runner provenance.
A slow unrelated runner must not block a ready critical-path task unless there is a real dependency.

29. CORRECTION RELAY
When convergence finds incompatibility, fan correction work back only to the affected runner(s)/component(s).
Do not restart the full operation or repeat unaffected analysis.
After correction, re-run the smallest compatibility gate that proves the conflict is resolved, then continue the DAG.
If integration evidence changes dependency boundaries, update the DAG rather than forcing the original plan.

30. BOUNDED SPECULATIVE EXECUTION
When two or more plausible approaches have materially uncertain latency/success and trying them in parallel is cheaper than serial failure, MotorLab may run bounded speculative alternatives only when:
- each alternative is read-only or safely isolated;
- no shared write conflict exists;
- external cost/quota remains acceptable and no hidden paid usage is introduced;
- risk is LOW/MEDIUM or the speculative portion itself is non-destructive;
- success criteria are explicit.
The first trustworthy valid result may win; losing alternatives are safely stopped/discarded.
Do not use speculative execution for irreversible production changes, signing/package identity, destructive migration, security-sensitive writes or provider-abusive traffic.

31. EVIDENCE LEARNING LOOP - ERRORS / RESEARCH / EXPERIENCE
MotorLab learns operationally from evidence without autonomously weakening governance.
Eligible lesson sources include:
- confirmed Root Cause incidents and prevention outcomes;
- successful/failed runner decompositions;
- searches/documentation that resolved a recurring uncertainty;
- build/test/cache timing;
- provider/tool latency and failure modes;
- repeated compatibility conflicts;
- TTTA and phase timing comparisons;
- successful recovery paths and ineffective retries.
A reusable lesson should record scope/context, evidence, strategy, observed effect, confidence, invalidation conditions and last verification.
Lessons are advisory acceleration knowledge, never a new technical source of truth and never automatic permission to write.
Before reuse, validate applicability against current source/tool/provider/risk state.
Prefer lessons that reduce TTTA, remove repeated work, improve automation or prevent known regressions.
Retire/down-rank lessons when newer evidence contradicts them.

32. LEARNING PERSISTENCE / BOUNDED MEMORY
When D1 is connected, bounded operational lessons may be stored through Persistent Operational State.
GitHub technical Change History may preserve durable high-value lesson provenance/fallback without logging high-frequency noise.
Do not store hidden chain-of-thought, secrets or raw private prompts.
Do not create unbounded knowledge accumulation: merge duplicates, keep evidence links, age/stale-mark context-sensitive lessons and preserve only information likely to affect future decisions.

33. INCREMENTAL EVERYTHING
Prefer incremental source inspection, targeted tests, dependency-aware build tasks, cache reuse and partial recomputation over full repetition.
A task already proven valid for the same authoritative inputs should not be rerun merely because another independent runner finished.
Invalidate only the affected cache/test/analysis surface when dependencies change.
Full rebuild/full regression remains available when required by risk, promotion or invalidation evidence.

34. R21 MINIMUM ADAPTIVE VERIFICATION
In addition to earlier checks, verify when applicable:
13. DAG contains no unresolved cyclic dependency before execution;
14. critical-path tasks are not delayed by unrelated global barriers;
15. concurrent writes have disjoint isolated scopes;
16. exactly one integration lane owns final artifact state;
17. convergence detects overlapping resource changes before final packaging;
18. correction relay does not restart unaffected work;
19. speculative alternatives remain bounded/isolated/cost-safe;
20. TTTA is measured from honest execution boundaries when metrics are available;
21. reused lessons include current applicability/invalidation checks;
22. complexity additions demonstrate a net pillar benefit or remain disabled/on-demand.

35. R21 SUCCESS EXTENSIONS
Velocity Layer is additionally successful when:
- MotorLab chooses one vs many runners adaptively;
- independent work overlaps without violating single-writer;
- critical-path work advances without waiting for unrelated runners;
- compatibility is checked continuously rather than only at the end;
- failed strategies and confirmed root causes improve later routing;
- build/test work is increasingly incremental;
- median TTTA for comparable recurring work trends downward without artifact-quality regression;
- increasing MotorLab internal complexity does not create increasing user-visible process latency by default.


36. R22 EXECUTION FABRIC - PLAN MUST BECOME ACTION
MOTORLAB_EXECUTION_FABRIC_V1.txt is the mandatory runtime dispatcher subordinate to this Velocity Layer.
Velocity remains the sole scheduling authority; Execution Fabric turns the selected graph/critical path into actual host/tool/job dispatch.
For every eligible non-trivial operation:
- run the Fast Decision Gate first so tiny deterministic work stays DIRECT_FAST;
- when the host supports concurrent calls, batch independent ready tool/read operations in the same execution cycle;
- when durable executors support concurrency, launch independent ready jobs without unnecessary barriers;
- recompute the READY set after any runner completes rather than waiting for the whole wave;
- preserve one integration lane and all write locks;
- record observed execution mode and proof instead of treating PARALLEL_EXECUTION=enabled as evidence.

37. OBSERVED PARALLELISM, NOT CONFIGURED PARALLELISM
The presence of DAG/fan-out settings does not prove that an operation ran in parallel.
Substantial operations should expose one of:
DIRECT_FAST
PARALLEL_OBSERVED
SERIAL_REQUIRED
SERIAL_HOST_LIMITED
PARALLEL_OBSERVED requires overlap/same-cycle evidence from real tool calls, jobs or executor intervals.
If useful concurrency was planned but the host only exposed one lane, report SERIAL_HOST_LIMITED and preserve the graph for an executor that can run it.

38. FAST DECISION / REASONING BUDGET
Do not spend deep orchestration effort on a known deterministic path.
Prefer:
KNOWN + LOW/CONTAINED RISK + VERIFIED LESSON/SNAPSHOT -> FAST decision + execute.
NOVEL/AMBIGUOUS/CONFLICTING/HIGH RISK -> deeper analysis as needed.
This is an orchestration rule, not a claim that MotorLab controls the host model's intrinsic reasoning speed.
Reduce repeated interpretation, repeated CORE reading and serial state gathering before reducing necessary verification.

39. GROUPED EXECUTION STATUS
User-facing updates for active r22 work should group concurrency:
- COMPLETATI INSIEME;
- IN CORSO INSIEME;
- SBLOCCATI / PROSSIMI NODI;
- CRITICAL PATH;
- execution mode + observed peak runners when known.
Do not narrate independent ready work as a long sequence of "adesso faccio..." messages.


40. R23 GLOBAL ORDER OF OPTIMIZATION
For speed work, optimize in this order unless evidence shows a safer faster exception:
1. ELIMINATE work through valid reuse/cache.
2. REDUCE work through incremental/delta invalidation.
3. PRIORITIZE the remaining TTTA critical path.
4. STREAM newly-unblocked work immediately.
5. PARALLELIZE independent remaining work adaptively.
6. BRANCH dynamically when discoveries justify it.
7. PRUNE obsolete/dominated pending work.
8. RACE alternatives only for bounded critical uncertainty.
This ordering supersedes the simplistic idea that more concurrency is the primary accelerator.

41. CONTENT-ADDRESSED / INCREMENTAL REUSE
Velocity owns the decision to reuse or invalidate prior work.
Prefer content-addressed identities that include every correctness-relevant input.
Examples of reusable classes when deterministic and fully keyed:
- unchanged source/config inspection;
- build/test outputs;
- dependency resolution metadata;
- generated intermediates;
- previously verified research tied to version/source;
- immutable artifact metadata.
Do not cache away live facts, time-sensitive provider state, security checks or mutable external conditions unless their freshness/invalidation is explicitly part of the key/contract.

42. DYNAMIC DAG
The DAG is not frozen at planning time.
Runner discoveries may add nodes/edges; validated evidence may prune pending nodes.
Velocity remains the sole scheduler and re-evaluates critical-path priority after material graph mutations.
Preserve unaffected completed nodes; graph mutation is not a reason to restart from zero.

43. PROGRESSIVE EXECUTION SHAPE
Choose the smallest useful topology:
FAST LINE: one direct path;
MINI TREE: small local branching without supervisory hierarchy;
FULL DYNAMIC GRAPH: larger work with multiple active branches and optional local supervisors/adapters.
Escalate only when expected TTTA benefit exceeds orchestration cost.
De-escalate/prune when complexity no longer pays rent.

44. EVENT-DRIVEN MEMORY / ORCHESTRATION
Use material execution events as compact operational memory.
The central orchestration view consumes events and current state; it does not require every runner to narrate every microstep.
Local supervisors/adapters may aggregate low-value noise before central persistence.
Persistent history must store decisions/results/evidence, never private chain-of-thought.

45. DEFERRED MATERIALIZATION
Prefer remote/reference/digest form for intermediate artifacts until bytes/rendered output are actually required.
Avoid download/copy/repackaging work that is not on the critical path.
Final artifact verification/delivery requirements still win.

46. PERFORMANCE ACCOUNTING
For comparable operations separate:
WORK_AVOIDED_BY_CACHE
WORK_REDUCED_BY_INCREMENTALITY
WORK_PARALLELIZED
SERIAL_CRITICAL_PATH
EXTERNAL_WAIT
COORDINATION_OVERHEAD
A speed improvement is real only when TTTA falls without required quality/safety regression.

R24 LATENCY-HIDING DECISION RULE
When a live task becomes slower than its declared useful threshold, Velocity should prefer productive independent work over passive waiting only when the expected TTTA saving is positive after orchestration/provider/lock overhead.
Decision order:
1. do not branch if there is no useful independent work;
2. do not duplicate irreversible or costly side effects as a blind race;
3. estimate branch benefit versus overhead/contention;
4. if positive, declare LATENCY_BRANCH_AFTER_MS, EXPECTED_GAIN_MS, OVERHEAD_MS and safe independent spawn candidates;
5. Execution Fabric triggers the branch only while the parent is still running;
6. reconverge through normal dependency and single-integration rules.
A timer is not an optimization by itself. The optimization is useful work overlapped with otherwise unavoidable latency.

R25 WORKGROUP / INTRINSIC SPEED DECISION ORDER
Permanent optimization order:
1. ELIMINATE: if safely unnecessary, do not execute it.
2. REUSE: prefer valid cache/checkpoint/result reuse.
3. REDUCE: run only invalidated delta.
4. ACCELERATE INTRINSICALLY: remove dispatcher/orchestration overhead without weakening semantics.
5. GROUP SEMANTICALLY: identify independent responsibility lanes among remaining necessary work.
6. PARALLELIZE only when expected TTTA gain exceeds coordination/contention overhead.
7. HIDE LATENCY with r24 only when useful independent work remains.
8. INTEGRATE once through the authoritative lane.
Semantic workgroups are an execution shape chosen by Velocity, not independent agents or schedulers.

R26 ADAPTIVE RUNTIME GOVERNANCE
Velocity remains the sole scheduling/planning authority. The Adaptive Runtime Governor is subordinate feedback control, not a second scheduler.

Permanent coordinated order:
1. ELIMINATE safely unnecessary work.
2. REUSE valid cache/checkpoint/result.
3. REDUCE to invalidated delta.
4. ACCELERATE intrinsic dispatcher hot path.
5. GROUP remaining independent semantic work.
6. ASSIGN adaptive lanes only where shared-resource/provider concurrency benefits from feedback control.
7. PARALLELIZE within global, lane, provider and write-conflict bounds.
8. RECOVER LATENCY through one controller:
   - explicit material stall on eligible hedge-safe work -> early bounded Triple Hedge;
   - otherwise eligible hedge-safe work -> hard Fresh Hedge trigger at 10000 ms;
   - non-hedge work with useful independent latency work -> r24 latency branch;
   - first valid hedge result wins; maximum two waves, maximum three attempts per wave.
9. CONVERGE through one integration lane.

External services remain subordinate to MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt. Equivalent external requests should normally coalesce, not hedge. External hedging requires explicit adapter/provider authorization and must remain inside documented/observed budgets.

Adaptive lane evidence uses actual latency, success, throttle and saturation signals. Increase concurrency gradually after healthy evidence; decrease quickly on throttling. Complexity still must pay rent.

R26 COORDINATED AUTO-ADAPTATION
Velocity remains the sole scheduler. The Adaptive Runtime Governor is subordinate and may tune only execution pressure/timing inside Velocity-approved work.

Permanent order:
1. ELIMINATE;
2. REUSE;
3. REDUCE;
4. ACCELERATE INTRINSICALLY;
5. GROUP SEMANTICALLY;
6. ALLOCATE adaptive lane capacity;
7. DISPATCH READY work;
8. RECOVER eligible slow work through the unified Latency Controller;
9. INTEGRATE once;
10. VERIFY + persist material adaptive evidence.

The governor may learn from observed latency, healthy completions, throttling, saturation, hedge outcomes and stall evidence. Learned state is bounded, context-aware and non-authoritative. Current provider limits, current source truth, External Service Guard, single-writer and approval always outrank learned state.

R27 DUAL-LANE RULE
- Different useful independent work starts immediately when it is READY or declared as safe productive sidework with positive expected gain.
- No 3-second or 10-second delay is required before different useful work starts.
- Recovery of the same unresolved task remains separate: bounded Fresh Hedge keeps the default 10000 ms hard trigger unless reliable stall evidence justifies earlier recovery.
- Immediate sidework and same-task recovery may coexist under the same Velocity scheduler.
- Single-writer, provider limits, runner limits and one integration lane remain mandatory.

Latency responsibility remains singular; r27 does not introduce another scheduler.
