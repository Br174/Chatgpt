UNIVERSAL APK REQUEST POLICY - GLOBAL

SCOPE
This policy is the canonical APK/ZIP request flow for Bruno's Android projects, including MusicLab, GeoVision and future projects. Project-specific adapters may define repositories, branches, workflows and package IDs, but they must not replace this request order.

MANDATORY FLOW
1. ARTIFACT-FIRST. On every request to obtain, download, generate or deliver an APK/ZIP, first check the configured project's latest UAB manifest.
2. If the manifest status is ready and it represents the same app source state, immediately return the existing APK and ZIP. The source state is considered the same when the commit matches exactly or when every change since the manifest commit is explicitly classified by that project's adapter as build/delivery infrastructure that cannot change the app binary. Do not rebuild unless Bruno explicitly requests a rebuild.
3. If no matching ready artifact exists, attempt a new build in this exact default order:
   a. local/current ChatGPT or AI execution environment;
   b. GitHub Actions using free included allowance only;
   c. Codemagic/UAB robust fallback with delivery through the central GitHub Releases registry.
4. The first two routes must fail fast during availability/preflight checks. Missing Android toolchain, authorization, free quota, runner, service or required configuration must cause immediate fallback instead of waiting minutes.
5. Once a provider has passed preflight and a real Android build has genuinely started, allow the build to finish normally.
6. If a real build fails because of project code, signing, dependencies or another project-level error, stop and diagnose it instead of repeating the same broken build on other providers.
7. If a provider fails before meaningful build steps run because of infrastructure, authorization, quota, runner or service availability, move immediately to the next provider.
8. Paid fallback is forbidden. Never enable paid overage or buy build minutes automatically.
9. Email, manual mailbox searches, AppDeploy and improvised artifact-recovery paths are not part of the normal flow.
10. The user must never need to remember or restate this policy. The AI/router must apply it automatically whenever an APK/ZIP is requested.
11. If an Android project is not yet UAB-enabled, the correct action is to onboard that project to the same UAB contract. Do not create a separate ad-hoc APK delivery method for that project.

LIVE BUILD MONITORING - MANDATORY
1. Every APK/ZIP request that requires a new build or waits for an in-progress build MUST automatically enter LIVE monitoring mode. Bruno must not need to ask for repeated status checks.
2. While an interactive chat/tool session is active, poll the active provider/check status at short intervals appropriate to the provider. Do not spam identical messages: surface an update when the phase/status changes, when a meaningful milestone is reached, or when the previous ETA materially changes.
3. Every visible live update should include: current phase/status, elapsed time, and an ETA/range when there is enough evidence to estimate one. ETA must be based on recent comparable builds or provider progress and must be revised when exceeded; never present a guessed ETA as certain.
4. Continue LIVE monitoring until a terminal result is reached: success, failure, cancellation, or a confirmed infrastructure blocker.
5. A provider-reported success is not enough for delivery. After success, verify the central latest.json manifest is status=ready and points to the exact requested source commit/build. Then verify the expected APK/ZIP assets are present before exposing download links.
6. Never deliver a stale APK/ZIP merely because it is the latest currently available artifact while a newer requested build is still running.
7. If the interactive session cannot remain active long enough for true short-interval monitoring, use the best available condition-watch/notification mechanism as a fallback and explicitly state its minimum checking cadence. Do not call an hourly or delayed background check “real time”.
8. If a build is already ready when requested, LIVE mode is unnecessary: return the verified APK/ZIP immediately.
9. LIVE monitoring is project-neutral and applies equally to MusicLab, GeoVision and every future UAB-enabled Android project.

DELIVERY
The stable retrieval endpoint is each project's latest.json manifest in the central artifact registry. APK and ZIP links from a matching ready manifest should be exposed directly to the user.

PROJECT NEUTRALITY
This policy must remain project-neutral. Each project supplies its own UAB project/router adapter. Future Android projects should be onboarded by pointing their adapter to this same flow rather than creating a separate APK-delivery method for that project.
