UNIVERSAL MOTORLAB/UAB POLICY - GLOBAL

SCOPE
This policy is the canonical build/test/delivery flow for Bruno's projects. Project-specific adapters may define repositories, branches, workflows, package IDs, signing, patch/repack rules and delivery details, but they must not bypass MotorLab CORE lifecycle, cost, verification, release, watchdog, visual-status, progress-reporting or background-execution rules.

NAME / COMPATIBILITY
Official engine name: MotorLab.
Legacy UAB filenames, variables and adapter keys remain temporarily valid so existing projects keep working during migration.

CORE PRINCIPLES
1. ONE ENGINE. MotorLab CORE is the single lifecycle/control engine. Project workflows are adapters, not independent engines.
2. LIFECYCLE. Every project follows MADRE -> LAB -> CANDIDATA -> NEW MADRE.
3. MADRE IMMUTABILITY. The current MADRE is the last approved stable state and must never be edited or overwritten in place.
4. LAB FROM MADRE. Every new experiment starts from the current MADRE unless Bruno explicitly chooses to continue an existing LAB.
5. CLEAN CANDIDATA. Candidate state is rebuilt cleanly from MADRE with only the proven LAB changes.
6. APPROVAL BEFORE PROMOTION. A CANDIDATA becomes a NEW MADRE only after regression checks and explicit approval.
7. HISTORY PRESERVATION. Historical MADRI remain permanently available as rollback points.
8. ARTIFACT-FIRST. Before any new build, check whether a verified matching artifact already exists.
9. FREE-FIRST. Never spend money automatically. Paid overage and paid runners require explicit authorization for that specific request. Codemagic is not part of MotorLab routing.
10. FAIL FAST. Availability, authorization, quota, runner, signing and toolchain checks should fail before a long build whenever possible.
11. DIAGNOSE CODE FAILURES. If a real build starts and fails because of project code, dependencies, signing or packaging, diagnose the project failure instead of blindly repeating it on another provider.
12. WATCHDOG. Long operations must be monitored for real progress, not just elapsed time. Suspected stalls use MotorLab Watchdog escalation with checkpoint recovery and single-writer safety.
13. VISUAL SUCCESS. Every meaningful verified success must be surfaced to Bruno with 2-4 fireworks plus an explanation of what succeeded.
14. FREQUENT PROGRESS. Substantial tasks must show verified percentage frequently throughout execution, including subtask/phase/status transitions. The same verified percentage may be repeated with new status instead of inventing progress.
15. BACKGROUND CONTINUITY. Long background-capable phases must be handed proactively to a durable executor when available so execution can continue independently of the visible ChatGPT screen. The project chat remains the canonical user-facing thread.
16. BUILD FAST LANE. Android update-family LABs use MOTORLAB_BUILD_FAST_LANE_V1.txt: one normal update Gradle build, permanent safety-source checkpoint, on-demand safety APK materialization, and immediate artifact-ready delivery.

MANDATORY LIFECYCLE FLOW
1. Identify and protect the current MADRE reference.
2. Create/use a LAB directly from that MADRE for requested experimental changes.
3. Build/test the LAB using the project adapter.
4. If LAB fails or seriously regresses another core function, reject that lineage and keep MADRE unchanged.
5. If LAB proves useful, create a clean CANDIDATA from the current MADRE and apply only the approved/proven changes.
6. Run adapter-defined regression gates on CANDIDATA.
7. Await explicit approval for promotion.
8. Promotion creates a NEW MADRE ref/version and, where applicable, a new immutable permanent Release.
9. Never delete or replace the previous MADRE.

RELEASE STORAGE - MANDATORY
1. Permanent GitHub Releases are a deposit of approved good versions (MADRI), not a scratch area for experiments.
2. LAB and CANDIDATA binaries use temporary Actions artifacts/test delivery until promotion.
3. Each MADRE release must use a unique immutable tag/version.
4. Never use --clobber, overwrite_files=true or equivalent against an existing MADRE tag/asset.
5. A 'latest' concept may exist only as metadata/pointer to the newest MADRE. It may not be the only binary store.
6. Downloader-style stable URLs may rely on GitHub's latest-release pointer only when each underlying release is uniquely tagged and preserved.
7. Chat attachments are convenience copies only for large binaries; they are never the authoritative store.

MANDATORY BUILD ROUTING
1. Read the project adapter/routing state and current repository visibility.
2. Check existing verified artifacts for the exact requested source state.
3. If a new build is required, choose the fastest safe route:
   a. adapter-approved patch/repack or local/current execution environment when immediately available and safe for that change type;
   b. PUBLIC repository: GitHub Actions on standard GitHub-hosted runners;
   c. PRIVATE repository: GitHub Actions only within included free allowance;
   d. if no allowed free route is available, stop and report the blocker.
4. Codemagic is REMOVED from MotorLab and must not be selected as primary, fallback or emergency provider.
5. Larger GitHub runners are not selected automatically.
6. Once a real build has started after preflight, allow it to finish normally while the watchdog observes progress.
7. Infrastructure failure before meaningful build work may move only to another route explicitly allowed by the project adapter; do not provider-hop blindly.
8. Genuine project/build failure is diagnosed, not provider-hopped.

PERSISTENT BACKGROUND EXECUTION - MANDATORY
1. The chat where Bruno starts/continues a project task remains the canonical user-facing chat.
2. MotorLab must not require routine manual migration between normal Chat, Work, MotorLab or another executor conversation merely because the backend changes.
3. MotorLab must classify substantial tasks before a long-running phase as CHAT_LOCAL, BACKGROUNDABLE, USER_BLOCKING or MIXED.
4. BACKGROUNDABLE/MIXED autonomous phases should be handed to a durable executor before depending on a long foreground chat turn.
5. A normal ChatGPT model turn alone is not a durable executor and must not be represented as background-safe.
6. Durable executors may include adapter-approved GitHub Actions, persistent workers/services, runners, Work/cloud when suitable, or other durable backends independent of visible chat lifetime.
7. Once safely handed off, the job continues autonomously through already approved steps while Bruno is away, with heartbeat, progress, checkpoints, watchdog and locks maintained.
8. Checkpointing does not mean pause-on-exit. Normal behavior is CONTINUE + SAVE CHECKPOINTS.
9. Job state must be durable and include operation/project/executor/ref/SHA/scope/phase/verified percentage/checkpoint/next step/lock/retry/artifact data when available.
10. Canonical job states: QUEUED, RUNNING, WAITING_EXTERNAL, WAITING_USER, RECOVERING, COMPLETED, FAILED_SAFE, CANCELLED_BY_USER.
11. When Bruno returns to the same project chat, MotorLab reconciles durable state before taking new write actions and reports what progressed while he was away.
12. Reopening the chat must never launch a duplicate writer against a still-running background job on the same lock scope.
13. If an executor quota/availability ends, preserve completed work and checkpoint; continue on another adapter-approved executor when safe and authorized; otherwise stop safely and report the blocker.
14. Work is optional and must not become a mandatory second user-facing conversation.
15. Notifications may be used for completion/WAITING_USER when supported, but do not become the authoritative conversation.
16. The background guarantee applies only once the task is on a real durable executor. MotorLab cannot force a suspended ordinary foreground chat turn to keep computing.
17. Detailed behavior is governed by MOTORLAB_BACKGROUND_EXECUTION_V1.txt.

PATCH / REPACK RULE
Patch/repack is preferred only when the project adapter marks it safe, typically for HTML/JavaScript/assets-only changes or equivalent non-native changes. Do not use patch/repack for native Kotlin/Java/Compose/Gradle/dependency/signing changes unless the adapter explicitly supports that exact change. Preserve package ID, signature expectations and install/update compatibility.

PUBLIC REPOSITORIES
1. Standard GitHub-hosted runners are the normal remote build route.
2. Do not route a public project to external build providers merely to save GitHub minutes.
3. Keep secrets in protected stores. Never commit API keys, passwords, signing secrets or private tokens in plaintext.
4. Permanent Releases are immutable MADRE releases only under the default MotorLab model.

PRIVATE REPOSITORIES
1. Prefer local or safe patch/repack when practical.
2. Use GitHub Actions only within included free allowance unless explicitly authorized otherwise.
3. Codemagic is not an allowed MotorLab fallback.
4. If free allowance is exhausted, stop rather than silently switch to billable usage or another provider.
5. Private projects keep private/authenticated release delivery unless an adapter explicitly defines a deliberate public distribution repository.

WEB / PWA PROJECTS
1. Web/PWA projects follow the same MADRE/LAB/CANDIDATA lifecycle.
2. Their artifact is web/PWA output rather than APK unless a real Android wrapper/project exists.
3. Deployment mechanics remain project-specific adapter behavior.

CACHE - MANDATORY
1. Safe persistent cache must be enabled wherever supported.
2. Android/Gradle routes use official Gradle caching and --build-cache unless documented incompatible.
3. Node/web routes persist package-manager download caches when safe.
4. Cache misses must not fail the build; they repopulate.

VISIBLE PROGRESS - MANDATORY
Broad full-task ladder:
5% accepted/scope locked
15% current MADRE identified/protected
30% LAB/config changes applied
45% static/source checks completed
60% preflight/cache/toolchain ready
75% build/test output completed
85% regression/artifact verification completed
95% candidate/handoff/promotion package ready
100% requested state verified and delivered

Progress reporting rules:
1. Report percentage throughout substantial work, not only at broad milestones.
2. Report at meaningful subtask starts/completions, phase changes, relevant code/config changes, check transitions, build/test transitions, artifact/checkpoint changes, watchdog interventions, recovery outcomes and delivery/promotion transitions.
PROJECT-LEVEL TERMINATION: a completed APK subtask, checkpoint, build, test, phase or delivered intermediate artifact does not finish the entire approved project. Continue the next safe authorized dependency within the same available turn, while delivering testable artifacts promptly; respect genuine blockers, approval gates and host limits.
3. Progress updates after roughly 1-3 meaningful operations are optional NON-TERMINAL observations when the interface permits; this is never a pit stop, mandatory response end, checkpoint timer or request for another OK. Continue all already authorized safe steps in the same available execution turn. When non-terminal updates are unavailable, batch observations until the next available control point.
4. Large broad phases may use real deterministic micro-milestones to produce justified intermediate percentages.
5. The same verified percentage may be repeated with a new explanation when status changes but no new completion is verified.
6. Long operations should surface job/provider phase changes when available rather than remain silent.
7. Never increase percentage because time passed.
8. Never report 100% until requested state/artifacts are verified and delivered.
9. On failure retain last verified percentage and identify the failing substep.
10. Watchdog messages should include current percentage when visible.
11. Fireworks success messages should include current percentage when useful.
12. Detailed behavior is governed by MOTORLAB_PROGRESS_REPORTING_V1.txt.

VISUAL SUCCESS STATUS - MANDATORY
1. Every meaningful verified completed item must be visibly reported to Bruno.
2. Use 🎆🎆 for a small verified success; 🎆🎆🎆 for a significant milestone/feature/build success; 🎆🎆🎆🎆 for a major or final verified completion.
3. Fireworks must always be accompanied by a short explanation of what succeeded and, where relevant, how it was verified.
4. Do not show fireworks for work that merely started, is pending, assumed successful or not yet verified when verification is possible.
5. Small resolved items should receive their own success signal; do not reserve fireworks only for the final response.
6. Do not repeat fireworks for the same success or decorate internal polling/no-op actions.
7. Fireworks do not replace progress percentages and do not create progress by themselves.
8. Watchdog lightning remains distinct: lightning means anti-stall intervention/protection; fireworks mean verified success.
9. Detailed behavior is governed by MOTORLAB_VISUAL_STATUS_V1.txt.

LIVE BUILD MONITORING + MOTORLAB WATCHDOG
1. New/in-progress build requests are monitored while an execution/control surface is available.
2. Report meaningful phase changes, not repeated identical status spam.
3. Provider success alone is insufficient; verify requested artifacts and source state. Conversely, once the requested verified artifact is uploaded/retrievable, do not wait for unrelated deferred work or whole-workflow terminal state before delivery.
4. Never deliver a stale artifact while a newer requested build is still running.
5. Repeated identical provider/job state does not count as progress.
6. Suspected stalls use adaptive thresholds based on operation class and provider evidence rather than one fixed timeout.
7. First intervention is always non-destructive verification.
8. User-visible watchdog intervention format is mandatory:
   ⚡ Verifica anti-stallo — <what appears stalled + what is being checked>
   ⚡⚡ Ripresa controllata — <how work continues without restarting completed work>
   ⚡⚡⚡ Recupero da checkpoint — <which checkpoint/substep is being recovered>
   ⚡⚡⚡⚡ Protezione MotorLab — <why safe automatic recovery stopped>
9. A lightning symbol must never be shown without an explanatory sentence.
10. Read-only diagnostics may run in parallel; conflicting write operations may not.
11. Recovery preserves the last verified checkpoint and percentage and targets the smallest stalled/failed substep.
12. Blind infinite reruns are forbidden. Repeated recovery without new evidence escalates to safe stop.
13. Detailed watchdog behavior is governed by MOTORLAB_WATCHDOG_V1.txt.

SECURITY
1. Public source must never contain plaintext secrets.
2. Build logs must not echo secrets.
3. Signing materials and credentials are not stored in unsafe caches.
4. Br174/Chatgpt remains the private MotorLab control/registry repository, not an application.

PROJECT NEUTRALITY
Current repository-specific mechanics belong in UAB_PROJECT_ROUTING.txt and each thin project adapter. Future projects are onboarded to MotorLab CORE rather than given a new independent engine.
