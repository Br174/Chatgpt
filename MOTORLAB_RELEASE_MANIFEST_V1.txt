UPDATE RULE
A project satellite compares its local RELEASE with CURRENT_RELEASE at a safe bootstrap boundary. If central is newer, synchronization follows MOTORLAB_SATELLITE_SYNC_V1.txt. Never replace the active local core in the middle of an active write/build/test/promotion operation.

ROLLBACK RULE
Before applying a newer satellite bundle, preserve the previously verified local core as LAST_GOOD. If validation of the new bundle fails, restore LAST_GOOD and report a visible MotorLab protection event.

NATIVE ENGINE RULE
Satellite synchronization must never overwrite project-native engines, application source, UI, package/signing identity, project adapters or lifecycle state. Only MotorLab control-plane files are synchronized.

VISIBLE STARTUP RULE
The normal visible activation banner is exactly:
"⚙️ MotorLab attivo"
Extra technical wording is reserved for actual warnings, recovery events or blockers.

FOREGROUND STALL RULE
MOTORLAB_FOREGROUND_STALL_GUARD_V1.txt is mandatory. Before long/risky phases MotorLab establishes recoverable checkpoint/next-step state, prefers a real persistent executor for backgroundable work when available, otherwise uses bounded recoverable foreground segments. ChatGPT client "still processing" UI is not a MotorLab heartbeat.

CHANGE COMPATIBILITY RULE
MOTORLAB_CHANGE_COMPATIBILITY_GUARD_V1.txt is mandatory before every write-capable MotorLab self-change and every write-capable change to a MotorLab-managed project. Overlaps/conflicts must be integrated, ordered or explicitly superseded before writing; unresolved unsafe conflicts block the write.

ANTI-LOOP / WAKE RULE - RELEASE R5+
For release 2026.09.29-r5 and later:
- Watchdog is the single coordinator for progress-health detection and anti-stall intervention;
- preventive progress-health checks occur during substantial work when control/status evidence exists, without interrupting healthy work;
- the same ineffective write/retry/recovery strategy may not be attempted a third materially identical time after two no-progress attempts without new evidence;
- Resume Recovery owns checkpoint continuation after Watchdog classification;
- Foreground Stall Guard owns prevention/chunking/durable handoff and routes emerging loops to Watchdog;
- Progress Reporting provides denser live-like operational status from observable actions/results, not hidden chain-of-thought;
- user message `⚡` is a universal manual health/recovery shortcut at the first available execution cycle;
- automatic recovery remains mandatory and does not depend on Bruno sending `⚡`;
- `⚡` cannot independently create a new execution cycle if the ChatGPT host is fully suspended and does not accept/deliver the message.

MANUAL LIGHTNING SAVE-THEN-RESUME RULE - RELEASE R6+
For release 2026.09.29-r6 and later, manual `⚡` uses a strict SAVE-THEN-RESUME order:
1. identify active/pending operation and previous checkpoint;
2. before recovery/retry/new write, create or refresh a lightweight MANUAL_LIGHTNING_SALVAGE checkpoint with the freshest recoverable material state currently available;
3. keep salvage bounded and fast: no full repository backup, exhaustive traversal, full log archive or rebuild merely to save state;
4. preserve completed work, verified percentage, provider/job/ref/artifact identity and single-writer ownership when available;
5. then Watchdog classifies health and Resume Recovery continues only the smallest safe pending step;
6. if healthy external work is still running, do not duplicate or cancel it;
7. hidden model reasoning interrupted before the new execution cycle cannot be retroactively captured.

MONOTONIC RECOVERY FLOOR RULE - RELEASE R7+
For release 2026.09.30-r7 and later:
- same-operation verified progress is monotonic by default across manual and automatic recovery;
- before continuation, Resume Recovery reconciles coherent progress evidence from persisted checkpoint/ledger, latest user-visible verified MotorLab percentage, verified micro-milestones and current provider/job/ref/artifact state;
- recovery_floor_percent is the highest coherent verified value on the same operation/progress scale;
- a stale lower checkpoint cannot override newer coherent verified progress;
- Watchdog must not authorize a lower recovery percentage unless material evidence proves previous progress was invalidated;
- invalidation must be explicit and visible, e.g. verified rollback/reset, milestone-invalidating job failure, required artifact proven missing/corrupt, or approved replacement with a new operation/progress scale;
- interrupted chat, failed `⚡` send, missing newer checkpoint, elapsed time or conversation-load problems are not invalidation evidence.

The recovery floor does not invent progress and does not turn user-visible unverified estimates into verified milestones. It preserves only progress that MotorLab previously represented as verified or that current material state verifies.

FUTURE PROJECT RULE
Every future MotorLab software project receives the current satellite files during onboarding when repository integration is available and inherits all current guards and anti-loop/wake/save-then-resume/monotonic-recovery behavior automatically.
