SATELLITE LOCAL FILES
Each registered project should contain MOTORLAB_PROJECT_HOOK.txt, .motorlab/MOTORLAB_LOCAL_CORE.txt, .motorlab/MOTORLAB_LOCAL_CORE_LAST_GOOD.txt and .motorlab/MOTORLAB_SYNC_STATE.txt. Each project also references one central Project Continuity ledger, one technical Change History registry, and for r14+ one visible Registro Modifiche e Ripristini.

SAFE UPDATE
Adopt a newer MotorLab release only at a safe boundary, preserve the current verified local bundle as LAST_GOOD, and never switch release mid active write/build/test/promotion.

VISIBLE STARTUP RULE
First user-visible line for MotorLab project work: "⚙️ MotorLab attivo".

R11+ ROOT CAUSE
Contain the symptom, determine why it happened, correct/contain the causal mechanism, inspect recurrence surfaces and add proportionate prevention before definitive closure.

R12+ FAST ITERATION / NO-SPIN
Risk-scaled LAB iteration is allowed only where eligible. HIGH-risk and CANDIDATA/MADRE keep full gates. Persistent executor handoff must not cause indefinite foreground polling.

R13+ TECHNICAL CHANGE HISTORY
MOTORLAB_CHANGE_HISTORY_REGISTRY_V1.txt remains the technical semantic provenance/history layer backed by immutable Git. It can retain historical, superseded and automatically verified records for discovery, diagnosis and selective restore provenance.

R14+ PRE-CHANGE APPROVAL
MOTORLAB_PRE_CHANGE_APPROVAL_GATE_V1.txt is mandatory. A request to modify/correct/add/remove/restore expresses desired intent but does not authorize the first project/application write. MotorLab first shows a concise pre-change report; only a later Bruno approval of that report authorizes writing. Read-only preparation is allowed before approval. Material scope expansion requires an amended report and new approval.

R14+ REGISTRO MODIFICHE E RIPRISTINI
MOTORLAB_MODIFICATION_RESTORE_REGISTER_V1.txt is the user-facing restore-point layer. Visible numbers are plain stable integers 1, 2, 3... One feature family keeps one number. Only a specific modification Bruno confirms as working and wants conserved may create/update a visible slot. Automated build/test success alone is insufficient. Failed, ambiguous, experimental or unconfirmed attempts do not enter the visible register. A multi-change LAB/APK registers only the exact item(s) Bruno identifies for conservation. A newer confirmed implementation of the same feature updates the existing number; older provenance remains in Git/technical history. After persistence MotorLab explicitly reports the saved number. Existing pre-r14 technical records are not promoted automatically. "Ripristina N" resolves the visible slot but still requires the pre-change report and Bruno approval before writing.

CURRENT/FUTURE PROJECT RULE
All current and future MotorLab-managed software projects inherit hard pre-change approval plus a visible user-confirmed Registro Modifiche e Ripristini in addition to Project Continuity and technical Change History.

NO RUNTIME REGRESSION
MotorLab control-plane metadata alone must not alter application runtime, UI, package/signing identity, lifecycle or project-native engines.
