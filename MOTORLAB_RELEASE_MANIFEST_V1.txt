R11+ ROOT CAUSE
Every real problem still requires causal investigation, correction/containment and proportionate prevention before definitive closure.

R12+ FAST ITERATION / NO-SPIN
Eligible LOW/MEDIUM LAB work uses risk-scaled iteration; HIGH-risk and CANDIDATA/MADRE keep full gates. Durable handoff must not cause indefinite foreground polling.

R13+ TECHNICAL CHANGE HISTORY
Technical Change History is immutable-Git-backed provenance/search and remains distinct from visible restore slots.

R14+ PRE-CHANGE APPROVAL + VISIBLE RESTORE REGISTER
Initial change wording is intent only; show plan first and wait for Bruno approval before first write. Visible restore slots contain only specific Bruno-confirmed working modifications using stable plain integers.

R15+ ARTIFACT-FIRST + DEFERRED ROOT CAUSE
MOTORLAB_ARTIFACT_FIRST_ROOT_CAUSE_V1.txt is mandatory.
When Bruno requests an APK/ZIP/testable artifact for an approved defect/regression:
- default critical path is REPAIR -> RISK-APPROPRIATE VERIFY -> ARTIFACT -> DELIVER;
- safely deferrable causal/prevention work is persisted in POST_ARTIFACT_ROOT_CAUSE_QUEUE and continues afterward;
- Root Cause Closure remains mandatory and cannot be abandoned;
- non-deferrable safety/security/signing/data-integrity/unreliable-build or equivalent high-risk causes remain before artifact delivery when needed to trust the artifact;
- delivered artifact identity/ref/checksum is preserved while Bruno tests it;
- prevention requiring later code changes uses a separate controlled follow-up LAB/ref;
- `Artefatto: 100%` may coexist with `Progresso MotorLab complessivo: <100%` until causal closure is complete;
- `✅ Problema risolto` and `💯 Conclusione definitiva` remain unavailable while mandatory causal work is pending.

R16+ MULTI-SERVICE AUTHORITY + PERSISTENT STATE
MotorLab r16 adds a non-conflicting service architecture:
- GitHub = durable technical authority;
- Cloudflare D1 = persistent live operational state target;
- Cloudflare KV = reconstructible cache only;
- PostHog = runtime observability/evidence only;
- Notion = human-readable status projection only;
- GitBook = stable architecture/manual projection only;
- Superpowers = subordinate engineering-method layer;
- Context7 = on-demand version-aware documentation.
Every logical operation should use one MOTORLAB_OPERATION_ID for cross-service correlation.
No optional service may become a single point of failure or silently enable paid usage.
Actual provider/plugin connection is capability-gated and must not be claimed until verified.
MOTORLAB_SERVICE_INTEGRATION_STATUS_V1.txt is the required registry separating CORE readiness from real connection/resource readiness.
Existing project instrumentation/adoption occurs only at safe approved boundaries.

CURRENT/FUTURE PROJECT RULE
All current/future MotorLab software projects inherit r16 authority/data-ownership, persistent-state/fallback, observability and knowledge-routing rules in addition to existing approval, lifecycle, restore, Root Cause, Artifact-First, progress and safety rules.

NO RUNTIME REGRESSION
MotorLab control-plane metadata alone must not alter application runtime/UI/package/signing/lifecycle/native engines.

R19+ FOUNDATIONAL CHANGE COMPATIBILITY PILLAR
MOTORLAB_CHANGE_COMPATIBILITY_GUARD_V1.txt is a permanent mandatory pillar for MotorLab and every current/future managed software project.
Before any write-capable change, read authoritative current state and classify existing overlap/redundancy/conflict. Apply ONE RESPONSIBILITY = ONE ACTIVE COORDINATOR: reuse/extend/merge existing behavior or explicitly supersede obsolete/conflicting paths. Do not accumulate parallel implementations for the same responsibility. Fast paths, Velocity, automation, restore, migration and optimization may not bypass this pillar.

R18+ PAIRED SAFETY LABS
Every verified LAB NN aggiornamento in update-family mode must also produce LAB di sicurezza NN from the same exact functional source state, with a distinct package/family and unique test-only signing certificate. Safety checkpoints are immutable and provide a recovery floor from which a new active update family may be created.

R17+ ANDROID UPDATE FAMILIES
MOTORLAB_UPDATE_FAMILY_LIFECYCLE_V1.txt is mandatory for Android projects using Bruno's persistent LAB-update method. Same-family LAB revisions keep applicationId + signing certificate and increase versionCode; LAB -> CANDIDATA creates a new family without mutating LAB; approved CANDIDATA -> MADRE promotes the same candidate family/source identity.

R20+ POLLICINO EXTERNAL CONTINUITY PILLAR
MOTORLAB_POLLICINO_CONTINUITY_V1.txt is mandatory.
Pollicino is an external control-plane trace/sentinel, never breadcrumbs injected into application code.
It combines supported-executor liveness evidence, progress fingerprints, terminal seals, compact session journal and preemptive RESUME_READY preparation.
Watchdog remains sole stall/recovery-level coordinator; Resume Recovery remains sole continuation coordinator.
When a supported enrolled session loses liveness without a terminal seal, a durable external sentinel should prepare RESUME_READY before a later Bruno `continua`.
Opaque ordinary ChatGPT thinking cannot be truthfully pinged unless the host exposes a real side-channel; risky work should therefore use observable persistent executors or bounded recoverable segments.


R21+ FOUR DESIGN PILLARS + ADAPTIVE VELOCITY
MOTORLAB_VELOCITY_LAYER_V1.txt r21 semantics are mandatory.
Every current/future MotorLab project inherits:
- ENGINE EFFICIENCY, AUTOMATION/PROGRAMMING FACILITATION, FINAL ARTIFACT QUALITY and EXECUTION SPEED as the four design pillars;
- execution speed / honest TIME_TO_TESTABLE_ARTIFACT (TTTA) as the primary optimization KPI, subject to hard safety/correctness/approval/lifecycle constraints;
- COMPLEXITY MUST PAY RENT: avoid always-on orchestration that adds recurring latency without a required net pillar benefit;
- dependency-DAG planning for eligible non-trivial work;
- CRITICAL-PATH-FIRST scheduling;
- adaptive one-or-many runner fan-out;
- parallel writes only in disjoint isolated scopes with one final integration lane;
- continuous convergence and correction relay instead of unnecessary global barriers/full restarts;
- bounded speculative execution only when isolated, safe, quota/cost appropriate and likely faster than serial trial;
- incremental inspection/test/build/cache reuse with dependency-aware invalidation;
- bounded evidence learning from Root Cause, research, timings, provider/tool behavior, runner conflicts, recoveries and successful/failed strategies;
- current evidence/invalidation checks before any lesson is reused.
Velocity learning never grants write authority and never replaces GitHub/current project technical truth.
Repeated TTTA regression without required quality/safety justification is treated as an optimization defect.


R22+ OPERATIONAL EXECUTION FABRIC
MOTORLAB_EXECUTION_FABRIC_V1.txt is mandatory and subordinate to Velocity Layer.
r22 converts r21 planning into observable dispatch:
- Fast Decision Gate avoids orchestration overhead for trivial deterministic work;
- eligible independent ready nodes are dispatched concurrently when the host/executor supports it;
- concurrent tool/read calls are batched in the same execution cycle where supported;
- durable runners may overlap through Background Execution;
- dependency completion unlocks downstream work immediately without unrelated global barriers;
- same-scope writes never overlap; isolated writes still converge through one integration lane;
- correction relay reworks only affected scopes;
- substantial operations record Proof of Parallelism: execution mode, observed peak concurrency, critical path, overlap evidence, single-integration-lane verification and host limitation;
- capability configuration is never presented as proof that parallelism actually occurred;
- SERIAL_HOST_LIMITED is reported honestly when useful concurrency exists but the host exposes one lane;
- user-visible updates group completed/running/unlocked runner sets rather than serial microstep narration.
Reference dispatcher: templates/execution/motorlab_execution_fabric.mjs.


R23+ INCREMENTAL DYNAMIC CRITICAL-PATH ENGINE
r23 evolves r22 without replacing it.
Canonical optimization order:
- eliminate safely reusable work through content-addressed/result reuse;
- recompute only invalidated deltas;
- prioritize the remaining TTTA critical path;
- stream newly-unblocked nodes immediately;
- parallelize only the remaining useful independent work;
- grow the DAG dynamically from verified discoveries;
- prune pending obsolete/dominated work;
- use bounded racing only for critical uncertainty where duplicate cost is justified;
- defer materialization of large intermediates until required.

Execution Fabric reference behavior now includes stable content keys, cache-hit worker skipping, dynamic task spawning, pending-task pruning and bounded material event history.
Persistent Operational State reuses operation_events as central material event memory and adds bounded incremental_result_index metadata.
Cache/result indexes are non-authoritative: invalid/stale/ambiguous reuse becomes a MISS, and cache loss causes recomputation rather than correctness loss.
Small operations start FAST LINE and escalate to MINI TREE / FULL DYNAMIC GRAPH only when expected TTTA savings exceed orchestration cost.

R24+ LATENCY BRANCH TRIGGER
r24 adds evidence-gated latency hiding on top of r23:
- slow live tasks may trigger preplanned independent useful work after a declared threshold;
- trigger requires EXPECTED_GAIN_MS > OVERHEAD_MS;
- dispatcher wakes immediately when latency work is spawned;
- parent completion before the threshold cancels the branch;
- single-writer, lock scopes, runner caps and one integration lane remain mandatory;
- irreversible/costly provider side effects are not blindly duplicated;
- proof records latency branch count/tasks/expected gain/failures;
- fictional completion countdowns are prohibited.
Reference implementation remains templates/execution/motorlab_execution_fabric.mjs.

R25+ SEMANTIC WORKGROUPS + INTRINSIC ENGINE ACCELERATION
r25 adds two complementary speed layers on top of r24:
A) Semantic Workgroups
- eliminate/reuse/reduce before grouping;
- map remaining independent responsibility lanes into named workgroups;
- parallelize only when expected gain beats overhead;
- preserve same-scope serialization and one integration lane;
- retain r24 latency branches for slow live work.

B) Intrinsic Engine Acceleration
- cache validated graph/tail-score analysis until topology changes;
- avoid unnecessary async event scheduling hops when no listener exists;
- retain exact listener await semantics when a listener exists;
- expose schedulerGraphRecomputes and eventFastPathCount as proof.

Observed LAB benchmark on GitHub Actions:
- semantic workgroups final gate: 232.28 ms serial vs 95.09 ms parallel, 59.06% lower TTTA / 2.44x speedup;
- intrinsic dispatcher final gate: 183.956 ms baseline vs 61.225 ms optimized, 66.72% lower dispatcher time / about 3.00x speedup.
- final LAB gate: GitHub Actions run 37632156382, 20 tests passed / 0 failed.
These are controlled benchmark observations, not universal speed guarantees.

R26+ COORDINATED ADAPTIVE RUNTIME
r26 adds one coordinated feedback layer on top of r25:
- Triple Fresh Hedge: eligible tasks may expand from the original attempt to at most three total attempts; first valid result wins.
- Explicit material-stall signal can trigger recovery early.
- Default hard Fresh Hedge trigger: 10000 ms.
- At most two hedge waves; no exponential fan-out.
- Write/integration hedge is forbidden.
- External/provider hedge requires explicit adapter authorization and remains subordinate to External Service Guard.
- Adaptive Lane Pool uses measured success/latency/throttle/saturation feedback with rapid decrease on throttling and gradual recovery.
- Ordinary non-adaptive tasks retain the lightweight r25-compatible fast path.
- r24 useful-work latency branching and immediate dispatcher wake remain preserved.
- Velocity remains sole scheduler; one integration lane and all single-writer/project-native boundaries remain mandatory.

Final LAB gate evidence, GitHub Actions run 37639565434:
- 29 tests passed / 0 failed;
- semantic workgroups: 232.76 ms serial vs 95.65 ms parallel, 58.90% lower TTTA / 2.43x;
- intrinsic dispatcher: 62.099 ms average on the 1200-task benchmark;
- controlled stall recovery: 80.93 ms baseline vs 29.25 ms hedged, 63.86% lower time / 2.77x;
- adaptive lane trace under synthetic 429 + recovery: 3 -> 1 -> 1 -> 2.
These are controlled observations, not universal speed guarantees.

R26+ COORDINATED ADAPTIVE RUNTIME
r26 adds one subordinate runtime governor instead of additional competing schedulers.

Capabilities:
- Adaptive Lane Pool with AIMD-style pressure control;
- laneKey/adaptiveLane shared-capacity domains;
- default 10,000 ms Fresh Hedge hard trigger;
- early explicit-stall activation;
- bounded Triple Hedge: max 3 attempts per wave, max 2 waves / 6 attempts total;
- first valid result wins, losers receive abort/cancel requests;
- writes/integration are never hedged;
- external hedge requires explicit provider-adapter authorization and Service Guard compliance;
- r24 useful-work latency branching remains the fallback for non-hedge tasks;
- adaptive governor state can load/store across runs as non-authoritative evidence;
- ordinary tasks retain a lightweight r25-compatible fast path.

Controlled GitHub Actions evidence:
- final verification run 37640102912: 30 tests passed / 0 failed;
- semantic workgroups: 232.92 ms serial vs 95.04 ms parallel, 59.20% lower TTTA / 2.45x speedup;
- ordinary intrinsic dispatcher: 1,200 tasks, 9 rounds, median 57.245 ms (average 55.959 ms; noisy p90 129.682 ms);
- adaptive hedge benchmark: 81.05 ms baseline vs 28.37 ms hedged, 65.00% lower TTTA / 2.86x speedup;
- lane AIMD trace under synthetic 429 then healthy recovery: 3 -> 1 -> 1 -> 2.
These figures are controlled benchmark observations, not universal performance guarantees.
