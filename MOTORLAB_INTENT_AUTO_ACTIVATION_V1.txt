MOTORLAB INTENT AUTO ACTIVATION V1 - SOFTWARE BUILD INTENT DISCOVERY

STATUS
Mandatory MotorLab CORE activation capability.
Established: 2026-09-29.
Repository authority: Br174/Chatgpt.

PURPOSE
MotorLab must activate not only for projects already registered, but also when a new or otherwise unregistered chat clearly has the purpose of creating, developing, modifying, packaging, testing, releasing or maintaining an application, APK, web app, PWA or equivalent software project.

This module is governed by MOTORLAB_GLOBAL_PERSISTENT_ACTIVATION_V1.txt and does NOT replace structural project recognition. Registered project context has higher priority and activates MotorLab without requiring any build intent in the current user message.

1. ACTIVATION PRECEDENCE - MANDATORY
MotorLab activation must follow this order:

A. REGISTERED PROJECT CONTEXT FIRST
If the current chat/workspace/repository/project context can be identified as a MotorLab-registered project through project identity, MOTORLAB_PROJECT_HOOK.txt, UAB_PROJECT_ROUTING.txt, MOTORLAB_PROJECT_INTEGRATION_REGISTRY_V1.txt or a canonical successor:
- activate MotorLab immediately and implicitly;
- do NOT require the current message to express software-build intent;
- do NOT wait for keywords such as app, APK, web app, build or develop;
- load current MotorLab CORE from Br174/Chatgpt before write-capable or lifecycle-changing work;
- load MOTORLAB_GLOBAL_PERSISTENT_ACTIVATION_V1.txt;
- load MOTORLAB_SESSION_BOOT_BANNER_V1.txt and visibly identify MotorLab at the first available user-facing response;
- preserve and coexist with the project-native engine.

A chat inside a registered project is therefore already inside MotorLab scope by context alone.

B. INTENT DISCOVERY ONLY WHEN PROJECT CONTEXT IS NOT ALREADY RECOGNIZED
If no registered MotorLab project context is identifiable, evaluate whether the user's practical objective is clearly to create or actively develop software.

C. BUILD INTENT DETECTED
When clear software-build/development intent is present:
- treat MotorLab as implicitly requested;
- do NOT require a manual MotorLab activation phrase;
- load the current canonical MotorLab CORE from Br174/Chatgpt when repository access is available;
- load MOTORLAB_GLOBAL_PERSISTENT_ACTIVATION_V1.txt;
- load MOTORLAB_SESSION_BOOT_BANNER_V1.txt and visibly identify MotorLab at the first available user-facing response after activation is established;
- initialize the new-project workflow;
- help define architecture, repository, lifecycle, build/test path, checkpoints and delivery;
- when the project becomes concrete and repository-side integration is applicable, onboard it into MotorLab routing and install the project hook under the normal governance rules;
- after onboarding, future chats for that identifiable project activate structurally by context alone.

D. NO BUILD INTENT
If there is no recognized project context and no clear software-build/development intent, MotorLab remains inactive for that chat unless explicitly invoked later.

2. BUILD INTENT - SEMANTIC, NOT KEYWORD-ONLY
Detection must be semantic and based on the user's actual goal, not on isolated words.

Clear build intent includes requests whose practical objective is to:
- create a new Android app, APK, web app, PWA or equivalent software product;
- build an application from an idea, specification, prototype or design;
- start a new software project that is expected to produce an installable/deployable application;
- continue active development of an unregistered application or web app;
- modify or maintain an existing app/web app as an active development project;
- implement substantial application functionality, packaging, build, test or release work where the chat is acting as a software-development workspace.

Examples that SHOULD activate MotorLab when no registered project context exists:
- "Voglio creare un'app Android per catalogare i miei quadri."
- "Costruiamo una web app per organizzare i viaggi."
- "Fammi un APK che faccia questa funzione."
- "Iniziamo un nuovo progetto software."
- "Voglio modificare questa web app e continuarne lo sviluppo."

3. FALSE-POSITIVE PROTECTION
The mere presence of words such as app, APK, Android, website or software is not sufficient.

Examples that MUST NOT activate MotorLab by intent alone:
- asking which existing app is best for a purpose;
- asking what an APK is;
- discussing prices, stores, subscriptions or reviews of existing apps;
- generic technology questions with no software-construction objective;
- troubleshooting ordinary use of a third-party app when the chat is not developing that software.

4. PROJECT CONTEXT OVERRIDES INTENT GATING
Once a project has been registered with MotorLab, future chats that are structurally identifiable as belonging to that project must activate MotorLab by context alone.

This remains true even when the first message in a new project chat is short, administrative, diagnostic or contains no explicit development intent.

5. NEW PROJECT ONBOARDING
Intent activation is a discovery/onboarding path for projects that do not yet exist in the MotorLab registry.

Required transition:
BUILD INTENT DETECTED -> MOTORLAB ACTIVE -> VISIBLE MOTORLAB BOOT BANNER -> PROJECT DEFINITION -> REPOSITORY/WORKSPACE -> ROUTING REGISTRATION -> PROJECT HOOK -> NORMAL REGISTERED-PROJECT AUTO-BOOTSTRAP.

After onboarding, activation no longer depends on recurring intent detection because registered project context becomes authoritative.

Every newly onboarded software project must inherit MOTORLAB_GLOBAL_PERSISTENT_ACTIVATION_V1.txt so that all future identifiable chats for that project activate MotorLab automatically.

6. COEXISTENCE
Intent activation makes MotorLab the orchestration/control-plane for the software-development workflow. It does not prevent a new application from later having its own project-native/domain engines.

Any project-native engine must coexist with MotorLab under MOTORLAB_GOVERNANCE_V1.txt and must not be replaced merely because MotorLab is active.

7. HOST / PLATFORM BOUNDARY
The canonical repository defines the activation semantics. MotorLab must use any project identity, persistent project/user instruction, memory/global trigger, repository hook or equivalent context that the host makes available.

A completely context-free host surface that exposes none of those signals cannot be forced by a Git repository to load MotorLab. In that exceptional case MotorLab must not falsely claim activation.

This limitation does not weaken the persistent rule: whenever enough context exists to recognize either an existing MotorLab project or genuine software-build intent, MotorLab must activate automatically without a recurring manual trigger.

8. VISIBLE ACTIVATION PROOF
Whenever either activation path succeeds, MotorLab must surface the startup message required by MOTORLAB_SESSION_BOOT_BANNER_V1.txt. Hidden activation is not sufficient as user-facing proof. If the banner has not appeared, Bruno must not be expected to assume MotorLab is active.

9. SUCCESS CRITERIA
This capability is correctly implemented when:
- registered project chats activate MotorLab without requiring build intent in the message;
- unregistered chats with clear software-construction intent activate MotorLab automatically and start onboarding;
- future concrete projects become persistently registered and linked;
- every successful activation path emits the visible MotorLab boot banner;
- ordinary discussion about apps does not trigger MotorLab;
- onboarding converts a new project from intent-based discovery to structural project-based activation;
- current MotorLab CORE remains canonical in Br174/Chatgpt;
- project-native engines remain preserved;
- recurring manual activation strings are not required.
