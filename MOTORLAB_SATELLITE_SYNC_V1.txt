MOTORLAB SATELLITE SYNC V1

STATUS
Mandatory MotorLab synchronization capability.
Central authority: Br174/Chatgpt.

PURPOSE
Keep one verified local MotorLab satellite in each registered project while Br174/Chatgpt remains authoritative, with safe release adoption and no silent loss of newer CORE gates.

BOOT
1. Read project MOTORLAB_PROJECT_HOOK.txt.
2. Read .motorlab/MOTORLAB_SYNC_STATE.txt and .motorlab/MOTORLAB_LOCAL_CORE.txt.
3. Verified local core is immediately available as fallback.
4. When central is reachable, read MOTORLAB_RELEASE_MANIFEST_V1.txt and compare local/central releases.
5. Reconcile project Project Continuity/live state before selecting a safe update boundary.
6. Load all release-required capabilities, including r12 Fast Iteration/No-Spin, r13 technical Change History/selective restore, and r14 Pre-Change Approval + user-confirmed Registro Modifiche e Ripristini.

SAFE UPDATE
- pin one MotorLab release during an active write/build/test/promotion;
- adopt newer release only at a verified safe boundary;
- preserve current verified bundle as LAST_GOOD;
- fetch MOTORLAB_SATELLITE_BUNDLE_V1.txt;
- validate release id and all required markers;
- replace only MotorLab control-plane files;
- metadata-only synchronization uses safe CI suppression/path filters where supported;
- never suppress validation when real app/source/config changes are in the same commit;
- update sync state and project hook as needed;
- re-read/verify local files before declaring adoption complete;
- update central continuity/integration state so local adoption cannot remain silently stale.

R12+ FAST ITERATION / NO-SPIN
Eligible LOW/MEDIUM isolated LAB iteration may use risk-scaled checks. HIGH-risk and CANDIDATA/MADRE retain full gates. Durable executor handoff must not cause indefinite foreground polling.

R13+ TECHNICAL CHANGE HISTORY
Technical Change History is a Git-backed semantic provenance/search layer. It may auto-capture verified technical records and preserve superseded/backfilled history. It is not the r14 visible confirmed restore list.

R14+ HARD PRE-CHANGE APPROVAL
Initial user wording requesting a new modification is intent only. Before first application/project write, perform read-only preparation, show the concise pre-change report, and wait for Bruno approval of that report. Material scope expansion requires amended approval. Resume Recovery may continue already-approved unchanged scope without re-asking.

R14+ REGISTRO MODIFICHE E RIPRISTINI
Visible restore slots use plain stable integers 1,2,3... One feature family has one current slot. Only a specific modification Bruno confirms as working and wants conserved may create/update the visible slot. Multi-change batches never auto-register as a whole. Ambiguous subchange identity is confirmed before saving. Failed/unconfirmed attempts stay out. After persistence, MotorLab explicitly reports the number. Pre-r14 technical records are not auto-promoted. "Ripristina N" identifies a target but does not bypass the approval gate.

ROLLBACK
If a newer bundle cannot be verified, keep/restore LAST_GOOD, preserve project state and report fallback.

CENTRAL UNAVAILABLE
Use previously VERIFIED local release plus live repository/provider evidence conservatively. Do not invent newer rules as locally installed until synchronization can occur.

FUTURE PROJECTS
Future MotorLab projects receive hook + local satellite + Project Continuity + technical Change History + visible Registro Modifiche e Ripristini during onboarding.

AUTOMATIC MEANING
Synchronization happens only when an execution cycle with repository access exists; repository text cannot self-update or wake a frozen host.

NO APP RUNTIME CHANGE
.motorlab/control metadata must not intentionally alter app code/UI/package/signing/native engines/runtime dependencies.
