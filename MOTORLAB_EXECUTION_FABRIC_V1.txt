MOTORLAB EXECUTION FABRIC V1 - R23 INCREMENTAL DYNAMIC EXECUTION

STATUS
Mandatory MotorLab CORE execution capability.
Central authority: Br174/Chatgpt.
Established: 2026-10-06.

PURPOSE
Turn Velocity Layer r21 scheduling decisions into real, observable execution behavior. MotorLab must not merely declare that parallel execution is supported; when an execution surface supports useful concurrency, it must dispatch independent work concurrently, advance newly-unblocked work immediately, preserve single-writer safety, and produce evidence of what actually ran in parallel.

OWNERSHIP / NO DUPLICATE COORDINATOR
- MOTORLAB_VELOCITY_LAYER_V1.txt remains the ONLY scheduler/planning authority for DAG, critical path, runner count, complexity budget and TTTA optimization.
- Execution Fabric is subordinate runtime machinery: it executes the Velocity plan.
- MOTORLAB_EXECUTION_CONTINUITY_V1.txt owns continuation after approval.
- MOTORLAB_BACKGROUND_EXECUTION_V1.txt owns durable executor/job handoff.
- Change Compatibility Guard + single-writer own write compatibility.
- Watchdog owns stall/recovery classification.
- Progress Reporting owns visible percentage.
Execution Fabric MUST NOT become a competing planner, lifecycle engine, recovery engine or project-native domain engine.

1. FAST DECISION GATE
Before creating orchestration overhead classify the operation:
DIRECT_FAST:
- one atomic/deterministic task or coordination overhead >= expected speed benefit;
- act directly after required gates; do not build a ceremonial DAG.
PARALLEL_LOCAL:
- two or more independent short/medium tasks can run concurrently on the current host/tool surface.
PARALLEL_DURABLE:
- long-running independent tasks benefit from persistent/queryable executors.
SERIAL_REQUIRED:
- true dependency/conflicting write/risk constraint makes serial order necessary.
SERIAL_HOST_LIMITED:
- useful parallelism exists but the current host exposes only one usable execution lane.
Do not confuse SERIAL_HOST_LIMITED with a MotorLab design choice.

2. EXECUTION GRAPH
For non-trivial work, Velocity emits a compact graph. A task should contain only what the dispatcher needs:
TASK_ID
DEPENDENCIES
KIND=<read|write|integration|external>
LOCK_SCOPES
CRITICAL_PATH_WEIGHT/estimated cost when known
OUTPUT/acceptance condition
EXECUTOR eligibility
RISK/verification requirement
Do not inflate the graph with low-value microsteps.

3. READY-QUEUE DISPATCH
Execution Fabric maintains READY, RUNNING, COMPLETED, FAILED/WAITING state.
At each safe execution cycle:
A. identify every task whose dependencies are satisfied;
B. order critical-path/blocking tasks first;
C. launch as many compatible ready tasks as the adaptive runner limit permits;
D. do not wait for unrelated runners before unlocking downstream tasks;
E. when any runner finishes, immediately recompute READY;
F. integrate results continuously instead of using unnecessary whole-operation barriers.

4. REAL CONCURRENCY
When the host supports batching/concurrent calls, independent read/tool/provider operations SHOULD be launched in the same execution cycle rather than as conversational one-by-one calls.
When durable executors support concurrent jobs, independent jobs SHOULD overlap when net TTTA improves.
More runners are not automatically better. Fan-out must consider startup overhead, quotas, cache contention, provider pressure and expected duration.

5. WRITE ISOLATION / SINGLE INTEGRATION LANE
- same ref/resource/lock scope: never two concurrent writers;
- disjoint writes may overlap only if executor/project adapter provides real isolation;
- isolated runner results are not authoritative final state until accepted by the single integration lane;
- integration tasks that can mutate final artifact state are serialized through one integration coordinator;
- a read may continue alongside a write only when it cannot observe/use an unsafe intermediate state.

6. EVENT-DRIVEN CONVERGENCE
Do not use a global "wait for everybody" barrier unless the next task actually depends on everybody.
Runner completion is an event:
RUNNER_DONE -> validate smallest relevant interface -> unlock downstream tasks -> integrate if safe.
A slow unrelated runner must not hold the critical path.

7. CORRECTION RELAY
If convergence detects a conflict/regression:
- identify affected scopes/runners;
- create correction task(s) only for those scopes;
- preserve all unaffected completed work;
- re-run the smallest proof necessary;
- do not restart the whole graph unless evidence invalidates the common baseline.

8. FAST REASONING / NO RE-THINK LOOP
MotorLab orchestration must minimize reasoning that does not change a decision.
Use:
- verified snapshot/Change Capsule;
- RESUME_READY;
- applicable velocity lessons;
- one-pass parallel state gathering;
- deterministic rules for known operations.
Escalate to deeper analysis only for novelty, ambiguity, conflict, high risk or contradictory evidence.
MotorLab cannot change the host model's intrinsic internal reasoning speed and must not claim it can. It can reduce time spent on the critical path by avoiding repeated interpretation and moving deterministic work to tools/executors.

9. PROOF OF PARALLELISM - MANDATORY
Parallelism is a measured operation property, not a capability flag.
For substantial work record when observable:
EXECUTION_MODE=<DIRECT_FAST|PARALLEL_OBSERVED|SERIAL_REQUIRED|SERIAL_HOST_LIMITED>
PLANNED_RUNNERS
OBSERVED_PEAK_CONCURRENCY
TASKS_STARTED / TASKS_COMPLETED
CRITICAL_PATH
OVERLAP_EVIDENCE (runner/job/tool intervals or same-cycle concurrent dispatch evidence)
SINGLE_INTEGRATION_LANE_VERIFIED
CORRECTION_RELAYS
HOST_LIMITATION when applicable
Do not report PARALLEL_OBSERVED without evidence of overlapping work.

10. USER-VISIBLE EXECUTION STATUS
For substantial work, status should describe groups rather than narrating every microstep.
Preferred style:
COMPLETATI INSIEME: A, B, C.
IN CORSO INSIEME: D, E, F.
SBLOCCATI DOPO D: G, H.
CRITICAL PATH: D -> G -> artifact.
MODALITA: PARALLELA — picco N corridori reali.
If serial:
MODALITA: SERIALE NECESSARIA — reason.
or
MODALITA: SERIALE LIMITATA DALL'HOST — useful parallelism exists but is not exposed here.
Avoid repetitive "ora faccio X, poi faro Y" when independent tasks can be grouped.

11. TOOL-BATCHING RULE
When one model/execution cycle can invoke several independent read-only tools/calls, batch them concurrently where supported.
Do not serialize repository reads, status checks, independent searches or artifact metadata lookups without a dependency reason.
Write calls remain sequential for overlapping scopes. Independent isolated writes may use separate executor lanes only when explicitly supported.

12. DURABLE RUNNERS
Execution Fabric may delegate nodes to Background Execution adapters.
A durable node must expose enough identity/status for Watchdog/Pollicino when supported.
The foreground chat must not spin-poll a healthy durable job; while it runs, dispatch other independent ready work.

13. FAIL-FAST / FAIL-SMALL
A runner failure blocks only its dependency descendants unless shared-baseline evidence requires broader invalidation.
Continue independent safe branches.
Apply Two-Strike/Root Cause rules to repeated failures; do not duplicate the same ineffective runner strategy.

14. TTTA ACCOUNTING
Record enough timestamps to distinguish:
- orchestration/planning;
- host/tool queue;
- parallel runner work;
- serial critical-path work;
- integration;
- build/package;
- verification.
Optimization targets CRITICAL PATH and TTTA, not total summed CPU/tool time.

15. REFERENCE EXECUTOR
The repository reference implementation is:
templates/execution/motorlab_execution_fabric.mjs
It validates DAGs, prioritizes critical-path work, dispatches compatible ready tasks without global barriers, enforces write-scope collision rules, supports correction relays, and emits observed parallelism proof.
It uses an injected worker callback: it does not execute arbitrary shell commands itself and therefore does not create independent write authority.
Host/project adapters may wrap this reference behavior in their native tool/job system.

17. SUCCESS CRITERIA
Execution Fabric r22 is active when:
- eligible independent operations are actually overlapped on capable surfaces;
- newly-unblocked tasks start without waiting for unrelated runners;
- conflicting writes never overlap;
- one integration lane owns artifact-producing state;
- correction relay preserves unaffected work;
- DIRECT_FAST avoids orchestration overhead for trivial work;
- host-limited serial execution is reported truthfully;
- substantial operations expose observed, not merely configured, parallelism;
- user-facing updates group completed/running/next work;
- TTTA improves without weakening artifact quality or existing safety.


18. R23 WORK-ELIMINATION FIRST
Before dispatching a ready task, ask whether the task can be safely avoided.
Preferred order:
A. VALID CONTENT/RESULT CACHE -> do not run the worker;
B. VALID INCREMENTAL RESULT -> recompute only the affected delta;
C. REQUIRED NEW WORK -> schedule by critical-path value;
D. PARALLELIZE only the remaining useful work.
A runner that never needs to start is faster than a faster runner.

19. CONTENT-ADDRESSED RESULT IDENTITY
Reusable deterministic work should carry a cache identity derived from all inputs that can change correctness, for example:
- action/command/test identity;
- authoritative source/ref/input digests;
- relevant config/dependency manifests;
- toolchain/runtime versions;
- policy/verification version;
- environment dimensions that materially affect output.
The reference executor exposes makeContentKey() using a stable SHA-256 digest.
Cache keys are correctness identities, not merely filenames or timestamps.
Security-sensitive, non-deterministic, provider-live or environment-dependent results are cacheable only when their invalidation contract explicitly makes reuse safe.

20. CACHE AUTHORITY / INVALIDATION
Cache is an acceleration layer, never a new source of truth.
A cache hit may replace execution only when:
- key inputs are complete and current;
- result provenance is compatible with the requested acceptance gate;
- no invalidation condition is active;
- required freshness/live-provider checks are not being bypassed.
Stale/ambiguous cache -> MISS, not guess.
Cache loss must only cause more work, never correctness loss.

21. DYNAMIC GRAPH GROWTH
The graph may grow during execution.
A completed runner may emit DISCOVERY_BRANCH / TASK_SPAWNED nodes when it discovers independent or newly-required work.
Dynamic children inherit the parent dependency by default unless explicitly detached by an allowed adapter contract.
New nodes enter the same READY queue and scheduler; do not restart the operation or rebuild already-valid branches from zero.

22. PROGRESSIVE BRANCHING
Branching is adaptive:
FAST LINE -> MINI TREE -> FULL DYNAMIC GRAPH.
Start with the lightest execution shape that fits the known work.
Create branches only when expected TTTA reduction or required independent verification exceeds branching/coordination cost.
Small work should not pay full-tree overhead merely because dynamic branching exists.

23. PRUNING
When new evidence makes pending work unnecessary, obsolete or dominated by a verified result, prune it immediately.
Pruning rules:
- only pending/not-yet-authoritative work may be removed automatically;
- a running task is not silently killed unless the executor exposes safe cancellation semantics;
- never prune a required safety/lifecycle/verification gate;
- record the pruning event and reason.
Pruned dependency nodes count as intentionally resolved only for descendants whose contract accepts that pruning decision.

24. EVENT MEMORY
Execution Fabric emits bounded material events such as:
EXECUTION_STARTED
CACHE_HIT / CACHE_MISS / CACHE_STORED
RUNNER_STARTED / RUNNER_COMPLETED / RUNNER_FAILED
TASK_SPAWNED
TASK_PRUNED
CORRECTION_RELAY
EXECUTION_COMPLETED
Persistent Operational State may persist/coalesce these at meaningful boundaries.
This event memory is operational evidence, not chain-of-thought.

25. DEFERRED MATERIALIZATION
Do not download/copy/render/materialize large intermediates merely because they exist.
Keep provider-native references/digests until the result is actually required for:
- downstream computation that cannot consume the remote/reference form;
- verification;
- user delivery;
- lifecycle/promotion evidence.
Deferred materialization must never hide a verification requirement.

26. CRITICAL-PATH-FIRST RESOURCE ALLOCATION
After cache/pruning removes avoidable work, scarce runner/build/provider capacity goes first to nodes that block TTTA.
Non-critical branches may continue concurrently when resources are spare but must not starve critical-path nodes.

27. SELECTIVE RACING
Bounded speculative racing from Velocity may be used for a critical uncertain node only when:
- alternatives are safe/isolated;
- first VERIFIED valid result can satisfy the same contract;
- cancellation/discard of losing work is safe;
- expected time saved exceeds duplicate cost/quota pressure.
Do not race ordinary deterministic work that cache/incrementality can eliminate.

28. R23 PROOF
For substantial work Proof of Execution should additionally record when observable:
CACHE_HITS
CACHE_AVOIDED_ESTIMATED_WORK
DYNAMIC_TASKS_CREATED
TASKS_PRUNED
EVENTS_RECORDED
DEFERRED_MATERIALIZATION_COUNT when meaningful
The performance story must distinguish:
work avoided,
work reduced,
work parallelized,
work remaining on the serial critical path.

29. R23 REFERENCE EXECUTOR BEHAVIOR
templates/execution/motorlab_execution_fabric.mjs now supports:

- worker skip on valid cache hit;

R24 LATENCY BRANCH TRIGGER
When a live runner crosses a declared latency threshold, Execution Fabric may unlock preplanned independent useful work instead of passively waiting.
Rules:
- Velocity remains the sole authority deciding whether a latency branch is worthwhile.
- A latency branch is eligible only when LATENCY_BRANCH_EXPECTED_GAIN_MS > LATENCY_BRANCH_OVERHEAD_MS.
- The branch must be independent of the still-running parent until an explicit later join; it may prepare downstream reads/computation or other safely isolated work.
- Never duplicate irreversible/external side effects merely to race a slow provider.
- Existing lock scopes, single-writer rules, runner limit and single integration lane remain mandatory.
- If the parent finishes before the threshold, the trigger is cancelled and no branch is created.
- When triggered, the dispatcher wakes immediately; it must not wait for the slow parent to finish before scheduling newly READY work.
- Material events include LATENCY_BRANCH_TRIGGERED and LATENCY_BRANCH_FAILED.
- Proof records branch count, spawned task count, expected gain and failures.
- Do not display fictional countdowns. A time value is either observed elapsed time, a configured trigger threshold, or explicitly an estimate.

R25 SEMANTIC WORKGROUPS + INTRINSIC ENGINE ACCELERATION
Work elimination remains first. Semantic workgroups are formed only from work that still must exist after cache/reuse/delta/pruning decisions.
Rules:
- semantic groups represent independent responsibility lanes such as Playback, Sources, Build/Test or analogous project-specific domains;
- do not create a workgroup for work marked NOT_NEEDED or already safely reusable;
- use the existing Velocity scheduler and Execution Fabric only; no second scheduler is introduced;
- fan-out requires positive expected TTTA gain after orchestration overhead and existing conflict/lock checks;
- same-scope writers still serialize and all compatible branches reconverge through one integration lane;
- workgroup labels are material execution metadata and may be surfaced in status reporting;
- r24 latency branching remains active inside/around workgroups when a live task becomes slow.

Intrinsic acceleration:
- reuse validated static graph analysis and tail scores until the graph topology actually changes;
- invalidate cached graph analysis only when dynamic tasks change topology;
- when no external event listener exists, record material events without an unnecessary asynchronous scheduling hop;
- preserve listener ordering/await semantics when an external listener is present;
- intrinsic optimization must not change task results, dependency semantics, locks, cache semantics, event history, approval gates or project-native authority.
Proof may report semantic workgroups, eliminated groups, estimated semantic gain, scheduler graph recomputes and event fast-path count.

R26 ADAPTIVE RUNTIME COORDINATION
r26 coordinates the existing r23-r25 speed layers through one subordinate runtime governor; it does not introduce a second scheduler.

A. TRIPLE FRESH HEDGE
- Hedge only work explicitly classified hedge-safe by Velocity/project adapters.
- Write/integration tasks never duplicate through Fresh Hedge.
- External/provider tasks require explicit HEDGE_EXTERNAL_ALLOWED=true and remain subordinate to External Service Guard budgets, queueing, coalescing, Retry-After, backoff and circuit state.
- Default hard trigger is 10000 ms for an eligible task that has not completed.
- An explicit material stall signal may trigger the first hedge wave earlier than 10000 ms.
- First wave contains at most three total attempts including the original attempt.
- First valid result wins. Abort-capable losers receive cancellation; non-cooperative losers are ignored after settlement.
- If all attempts in wave 1 stall/fail/timeout, one additional wave of at most three attempts may start.
- Maximum waves are bounded to two; never multiply 3 -> 9 -> 27.
- Invalid/stalled results never win merely because they arrived first.

B. ADAPTIVE LANE POOL
- Lane limits are subordinate resource caps inside Execution Fabric, never a scheduler.
- Adaptive lane control applies only to declared adaptive lanes; ordinary local work stays on the r25 fast path.
- Use AIMD-style control: healthy evidence permits gradual increase; throttling cuts concurrency rapidly; saturation decreases conservatively.
- Global maxConcurrency, provider limits, single-writer conflict rules and integration-lane rules remain hard upper bounds.
- Governor state can be restored from prior evidence when the host persists it; cache/state loss causes conservative relearning, never correctness loss.

C. UNIFIED LATENCY CONTROLLER
- Velocity remains the only authority deciding which tasks are hedge-safe and what alternative useful work is eligible.
- Explicit stall on hedge-safe work may invoke Fresh Hedge immediately.
- Hard 10s on hedge-safe work invokes bounded Fresh Hedge.
- Non-hedge work may still use the r24 useful-work latency branch.
- Dynamic branch creation still wakes the dispatcher immediately.
- Do not stack independent retry/hedge schedulers for the same responsibility.

D. MEASUREMENT
Proof records hedge waves/wins/exhaustion/cancellation requests, material progress/stall signals, lane adjustments/throttle/saturation signals and the governor snapshot, alongside existing r23-r25 proof.

R26 ADAPTIVE RUNTIME GOVERNOR
Execution Fabric implements the runtime mechanisms selected by Velocity and coordinated by MOTORLAB_ADAPTIVE_RUNTIME_GOVERNOR_V1.txt.

Adaptive Lane Pool:
- task laneKey identifies a shared capacity domain;
- adaptiveLane enables governor-controlled capacity;
- external tasks default to adaptive lane control;
- healthy evidence may increase capacity gradually;
- throttling/rate-limit evidence reduces capacity multiplicatively;
- saturation reduces pressure conservatively;
- configured provider ceilings and External Service Guard always win.

Unified Latency Controller / Triple Hedge:
- default Fresh Hedge hard trigger is 10000 ms;
- explicit reliable stall signals may trigger before 10 s;
- Wave 1 = original + at most two fresh attempts, maximum 3;
- Wave 2 = at most 3 additional fresh attempts;
- maximum 2 waves / 6 total attempts;
- first valid result wins and losers receive abort/cancellation where supported;
- no unbounded 3->9->27 expansion;
- writes/integration never hedge;
- external/provider hedge requires explicit hedgeExternalAllowed and remains inside Service Guard budgets;
- if hedge is not eligible, r24 useful-work latency branching remains available.

Persistence and proof:
- governor snapshot may load/store through host callbacks;
- learned state is non-authoritative and safely disposable;
- proof records hedge, lane, throttle/saturation, stall, adaptive state and existing critical-path/integration evidence.
Ordinary tasks that do not use adaptive features stay on the r25-compatible lightweight fast path.

R27 DUAL-LANE ACTIVE WAIT / ZERO-IDLE SIDEWORK
r27 separates productive progress from same-task recovery.

A. IMMEDIATE PRODUCTIVE SIDEWORK
- If independent READY work exists, dispatch it in the same scheduler cycle; do not wait for a 3 s/10 s timer.
- A task may declare productiveSpawn, productiveBranchExpectedGainMs and productiveBranchOverheadMs.
- When PRODUCTIVE expected gain exceeds overhead, productiveSpawn tasks are inserted immediately as detached independent work and the scheduler is awakened immediately.
- Productive sidework advances different useful work. It must not be a disguised duplicate of the slow task.
- Material events: PRODUCTIVE_SIDEWORK_STARTED / PRODUCTIVE_SIDEWORK_FAILED.
- Proof: productiveBranches, productiveBranchTasks, productiveExpectedGainMs, productiveBranchFailures.

B. SAME-TASK RECOVERY REMAINS SEPARATE
- The original task remains alive while productive sidework proceeds.
- Fresh Hedge keeps the default 10000 ms hard trigger for eligible unresolved work, unless an explicit reliable stall signal triggers earlier.
- Fresh Hedge duplicates/replaces the SAME task only inside existing bounded hedge rules.
- Productive sidework and Fresh Hedge may overlap; one MUST NOT suppress the other.

C. VISIBLE TIMELINE SEMANTICS
- At available user-visible control points, an active wait/analysis status should be followed by concise truthful updates for materially started independent work, so a wait state does not remain the only visible latest activity.
- Never emit fake activity merely to move the timeline.
- Opaque host ChatGPT reasoning/spinner state cannot be inspected, cancelled or duplicated unless the host exposes a real control surface; r27 applies to MotorLab-controlled tasks/executors and to visible updates at supported control points.

D. SAFETY
- No second scheduler is introduced. Velocity remains scheduler authority; Adaptive Runtime Governor remains latency/capacity tuner; Execution Fabric remains dispatcher.
- Single-writer, provider limits, lock scopes, runner caps and single integration lane remain mandatory.
- If the host exposes only one usable lane, report SERIAL_HOST_LIMITED rather than pretending sidework overlapped.
