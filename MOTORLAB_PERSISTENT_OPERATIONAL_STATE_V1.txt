MOTORLAB PERSISTENT OPERATIONAL STATE V1

STATUS
Mandatory MotorLab CORE contract for durable operational continuity.
Central authority: Br174/Chatgpt.
Primary operational backend target: Cloudflare D1, with Cloudflare KV as cache only.

PURPOSE
Reduce forgotten steps, stale chat-state reconstruction, duplicated work and interrupted operations by maintaining a durable operational ledger outside ephemeral chat context.

PRIMARY MODEL
GitHub remains the technical source of truth.
D1 stores the live operational state needed to continue work correctly.
KV accelerates reads but is reconstructible and never authoritative.

MINIMUM D1 ENTITIES
1. projects
- project_id
- repository
- lifecycle identity
- current known technical ref/head pointers
- local satellite release state
- updated_at

2. operations

4. checkpoints
- operation_id

6. artifacts

7. root_causes

- status

8. operation_events
Append-oriented operational history for material transitions only.
Examples: request parsed, pre-change report emitted, approval captured, write started, checkpoint reached, artifact verified, artifact delivered, causal queue opened/closed, operation closed.
Do not log every low-value internal thought/tool call.

9. live_directives
- directive_id

- directive_type
- value
- priority
- created_at
- expires_at or durable flag

- applied_checkpoint
- status: pending/applied/superseded/rejected
Live directives contain orchestration metadata only: no raw API keys, access tokens, credentials or secrets.


10. command_queue

- requested scope summary
- arrival order
- priority_override flag
- status

11. completion_barriers
- stable fingerprint
- operation_id/project_id
- defect/cause/evidence

- repair/prevention/verification

R17 APPROVAL FIELDS
Approval records additionally persist category, classification rationale, timer_started_at, auto_approve_after_seconds, auto_approve_at, decision state/evidence and manual-only status.
Exact eligible durations are 10/20/60/300 seconds.

WRITE DISCIPLINE
- D1 writes must be bounded and meaningful; avoid polling/event spam.
- Persist at material transitions and checkpoints.
- Live directive writes are transition-based and deduplicated; safe-point reads must not create event spam.
- Use idempotent keys where possible so Resume Recovery does not duplicate state.
- One logical operation uses one MOTORLAB_OPERATION_ID.
- Approval records must preserve scope identity so old approval cannot authorize broadened scope.

KV POLICY
KV may cache:
- current operation summary per project;
- latest verified progress snapshot;
- quick project status cards;
- frequently-read reference pointers;
- reconstructible active-directive summaries when useful.
KV values must include freshness/version metadata where useful.
Loss or staleness of KV must not lose authoritative state.

GITHUB CHECKPOINT BACKSTOP
At major durable boundaries, especially artifact delivery, promotion, definitive closure, long-lived external wait or material Live Control state transition, persist enough technical state in GitHub Project Continuity/technical registries so the operation can still be reconstructed if D1 is unavailable.
Do not mirror every D1 event into GitHub.

FALLBACK MODE
If D1 is unavailable:
1. do not invent D1 state;
2. use GitHub canonical technical state + project live evidence + verified local satellite;
3. preserve new operational changes in an in-turn checkpoint and, where appropriate, GitHub continuity backstop;
4. use repository Live Control fallback metadata conservatively when available;
5. mark D1_RECONCILE_PENDING;
6. when D1 returns, reconcile from authoritative evidence before accepting cached state.

RECONCILIATION
On D1 recovery:
- compare operation ids, source refs/heads, artifact checksums and durable GitHub transitions;
- reconcile live directive ids/status without re-applying superseded/expired directives;
- never overwrite newer verified GitHub technical truth with stale D1 data;
- merge only non-conflicting operational records;
- stale locks must be validated before release/reuse;
- unresolved conflicts become explicit reconciliation tasks, not silent guesses.

QUOTA/COST SAFETY
D1/KV usage must comply with current free-plan limits and MotorLab External Service Guard.
Use cache, deduplication, batch writes and transition-based persistence to minimize quota consumption.
Never auto-enable paid billing.

SECURITY
Store no raw API keys, access tokens, credentials or secrets in D1/KV operational records or live directives.
Only identifiers/masked references permitted where needed.

IMPLEMENTATION PHASES
Phase A: CORE contract/schema and fallback logic.
Phase B: actual Cloudflare D1/KV resources and provider-native secrets/bindings.
Phase C: project adapters incrementally write/read operational state.
No project may be forced onto Phase C during active/unsafe work; adoption occurs at safe boundaries.

SUCCESS CRITERIA
- interrupted approved work can resume from durable state;
- approval scope is not forgotten;
- active locks/checkpoints/artifacts/root-cause queues survive chat changes;
- applicable Live Control directives survive/reconcile without becoming write authority;
- optional cache loss is harmless;
- D1 outage does not make MotorLab unusable;
- GitHub remains the durable technical backstop.
