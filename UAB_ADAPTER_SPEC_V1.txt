UAB PROJECT ADAPTER SPEC V1

COMPATIBILITY NOTE
Official engine name: MotorLab.
Legacy UAB filenames and environment keys remain valid for backward compatibility while projects migrate gradually. Do not rename them blindly if that could break an existing adapter.

Every repository handled by MotorLab/UAB declares a small project adapter. The adapter describes mechanics only; lifecycle policy remains owned by MotorLab CORE.

Legacy adapters that do not yet declare watchdog/background/service-guard/velocity fields remain usable. MotorLab applies conservative defaults, MUST NOT claim true persistent background continuity unless a durable executor is actually defined and observable, MUST NOT invent provider quota values that have not been established, and MUST NOT use a Velocity optimization that cannot be proven compatible with existing MotorLab safety rules.

MANDATORY ADAPTER BEHAVIOR
1. Adapter cannot make a LAB permanent.
2. Adapter cannot overwrite an immutable MADRE release.
3. Adapter cannot promote CANDIDATA to MADRE without explicit approval.
4. Adapter must preserve prior MADRI.
5. Adapter must define cache behavior and progress milestones.
6. Adapter must define the core regression gates that must pass before promotion.
7. Adapter may keep legacy workflows temporarily, but those workflows are not authoritative promotion paths until aligned with MotorLab CORE.
8. LAB scope is atomic: one requested modification, or one small inseparable change-set for that single modification. Unrelated changes require a new LAB from the current MADRE unless Bruno explicitly combines them.
9. A CANDIDATA must be created fresh from the exact same MADRE ref/SHA used by the approved LAB.
10. The CANDIDATA must replay exactly the approved LAB change-set. No extra cleanup, refactor, dependency update or unrelated fix may be inserted without explicit approval.
11. Before candidate approval, the adapter must verify that MADRE->CANDIDATA source changes are equivalent to MADRE->approved-LAB changes for the approved change-set.
12. When Bruno approves the CANDIDATA as NEW MADRE, the new Mother source ref must point to the exact approved CANDIDATA commit SHA. Do not create another source commit merely to promote it.
13. If final Android Mother packaging/signing differs from Candidate test packaging, it must use the exact approved Candidate source SHA and may alter only adapter-declared packaging/signing metadata, never application source.
14. If the Mother/LAB/change-set/Candidate identity chain cannot be proven, promotion must stop rather than guess.
15. Substantial operations must expose enough state for MotorLab to distinguish a healthy wait from a true stall when the provider supports observability.
16. Repeated identical status output does not count as progress. Adapters should expose a meaningful progress signal or fingerprint source.
17. Write-capable operations must declare or derive a lock scope so the watchdog cannot create two conflicting writers.
18. Safe recovery must target only the stalled/failed substep when possible and preserve verified completed work.
19. Adapter watchdog events shown to Bruno must always use lightning emoji plus plain-language explanation; never emit a bare lightning symbol without context.
20. Adapter watchdog behavior is governed by MOTORLAB_WATCHDOG_V1.txt and may not override its non-interruption, checkpoint, bounded-retry or single-writer rules.
21. Long background-capable work must be routed proactively to a durable executor before MotorLab depends on a long foreground chat turn.
22. The project chat where Bruno initiated/continued the task remains the canonical user-facing thread. Backend/executor changes must not require routine user migration to another chat.
23. Background work must maintain durable operation/checkpoint state and reconcile that state when the canonical project chat is reopened.
24. Reopening the canonical chat must not start a duplicate writer when a durable background job is still RUNNING on the same lock scope.
25. Checkpointing is a safety mechanism, not a reason to pause when Bruno leaves. A durable job should continue autonomously through pre-approved steps until completion, failure, external blocker or WAITING_USER.
26. If an executor quota/availability ends, preserve the checkpoint and continue on another adapter-approved executor when safe and authorized; otherwise stop safely with the exact blocker.
27. A normal chat turn alone must never be described as persistent background execution.
28. Background execution behavior is governed by MOTORLAB_BACKGROUND_EXECUTION_V1.txt and may not override lifecycle, cost, watchdog or single-writer rules.
29. New or materially changed external API/provider integrations must apply MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt rather than relying on uncontrolled direct calls or infinite retries.
30. Provider-aware cache, deduplication/coalescing, official batching/pagination and request budgeting should reduce avoidable calls before any retry/failover behavior is considered.
31. Retry-After must be honored when valid; otherwise transient failures use bounded exponential backoff with jitter. Deterministic request/auth/policy errors go to diagnosis instead of tight retry loops.
32. Repeated rate-limit/transient pressure should open or suspend the relevant provider/endpoint/credential scope so normal traffic stops until conservative recovery/health checks justify reopening.
33. Credential failover is sequential: keep the current healthy credential; switch only on a classified failure the credential pool is allowed to handle; do not continuously rotate healthy credentials.
34. Multiple credentials or providers must not be used to evade a provider's intended quota/rate-limit policy. Quota failover is valid only for independent authorized capacity when provider policy permits it.
35. All-provider/all-credential failure must stop safely, preserve useful queue/cache/checkpoint state and avoid infinite loops.
36. Existing project-native provider logic should be wrapped/aligned incrementally; MotorLab service protection must not replace the project's domain semantics merely for architectural uniformity.
37. For a new/updated provider integration, execute the applicable minimum verification set in MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt, including cache reuse, deduplication, limiter/concurrency enforcement, Retry-After, circuit open/half-open recovery, safe all-failure behavior and degraded-mode regression checks.
38. Velocity Layer is strictly additive. An adapter may accelerate preparation/build/testing mechanics but may not remove, weaken, bypass or redefine any existing MotorLab lifecycle, approval, regression, Watchdog, checkpoint, single-writer, progress, background, service-guard, cost, signing/package or coexistence rule.
39. A project snapshot is an acceleration index only. Before write-capable work, the adapter must revalidate authoritative source ref/SHA and relevant files; stale snapshot state must be invalidated rather than trusted.
40. Pre-approval acceleration may perform only read-only preparation allowed by MOTORLAB_VELOCITY_LAYER_V1.txt. It may not change source, branches, releases, production state or other write-capable project resources before required approval.
41. Independent read-only preparation may run in parallel where safe; write-capable work remains single-writer.
42. FAST LAB is not a new lifecycle state. It must still start from the protected current MADRE/baseline, stay atomic, preserve the approved scope and cannot promote directly to CANDIDATA or MADRE.
43. LAB verification depth may scale by evidence-based risk classification, but HIGH-risk work cannot use a reduced verification path and all CANDIDATA/MADRE promotions still require the canonical exact-replay and full adapter-defined regression gates.
44. Build/cache/incremental reuse must invalidate on incompatible source/dependency/toolchain inputs. A cold/full build remains mandatory when safe reuse cannot be established.
45. Change Capsule/project snapshot reuse must stop and revalidate when Bruno changes the request materially, source baseline changes, evidence contradicts assumptions, recovery requires revalidation or governance demands it.
46. Existing approval remains valid across phases/executors for the same clearly described scope; do not ask Bruno to repeat the same approval unless scope/consequences materially change or another canonical rule requires renewed approval.
47. Provider-dependent acceleration must remain inside MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt budgets/circuit/backoff/failover rules; speed may not come from increasing API pressure.
48. Adoption of Velocity Layer must execute the applicable verification checks in MOTORLAB_VELOCITY_LAYER_V1.txt, including stale-snapshot invalidation, no pre-approval writes, no conflicting writer, risk gating, FAST LAB lifecycle safety, cache invalidation, Service Guard preservation and continued Watchdog/checkpoint/progress operation.
49. Android update-family mode is governed by MOTORLAB_UPDATE_FAMILY_LIFECYCLE_V1.txt. Later LAB aggiornamento builds in one family MUST keep applicationId + signing certificate and increase versionCode.
50. LAB -> CANDIDATA in update-family mode creates a NEW immutable candidate family from the exact approved LAB state/change-set and MUST NOT mutate or repurpose the LAB family package/signing identity.
51. If a candidate needs source changes, return to the LAB family, create the next LAB aggiornamento, approve it, then create a new CANDIDATA number; do not patch an existing candidate.
52. Approved CANDIDATA -> MADRE promotes the same candidate source identity. Android packaging may preserve that candidate family identity as the future MADRE identity according to project policy; no LAB test key may silently become a production key.
53. Update-family artifact gates MUST verify package/applicationId, monotonically increasing versionCode and signing certificate identity before calling the artifact update-compatible.
