MOTORLAB WATCHDOG V1 - PERSISTENT ANTI-STALL CORE

STATUS
Mandatory MotorLab CORE capability.
Established: 2026-09-28.
Repository authority: Br174/Chatgpt.

NAME / COMPATIBILITY
The engine's official human-facing name is MotorLab.
Legacy UAB filenames, variables and adapter keys remain temporarily valid for backward compatibility and must not be mass-renamed in a way that breaks existing project adapters.

PURPOSE
MotorLab must detect apparent stalls and emerging no-progress loops during programming, build, GitHub, API and tool operations and attempt safe continuation without discarding completed work, duplicating writes or corrupting project state.

COORDINATION ROLE - MANDATORY
Watchdog is the single coordinator for progress-health detection and anti-stall intervention.
Related modules retain distinct responsibilities:
- MOTORLAB_FOREGROUND_STALL_GUARD_V1.txt owns prevention, risky-phase classification, chunking and durable handoff preparation;
- MOTORLAB_RESUME_RECOVERY_V1.txt owns deterministic continuation from checkpoint/pending state after tool return or interruption, including the manual-lightning Rapid Salvage Checkpoint pre-step;
- MOTORLAB_BACKGROUND_EXECUTION_V1.txt owns persistent executor/job semantics;
- MOTORLAB_PROGRESS_REPORTING_V1.txt owns user-visible operational status and verified percentages;
- MOTORLAB_CHANGE_COMPATIBILITY_GUARD_V1.txt owns pre-change conflict/overlap/regression compatibility.
These modules must not launch competing recoveries for the same event. Watchdog decides the health/intervention level; Resume Recovery preserves the manual-lightning salvage checkpoint and performs checkpoint continuation when recovery is required.

CORE PRINCIPLE
A timer alone is not proof of a stall. MotorLab must distinguish:
- alive and progressing;
- alive but waiting legitimately;
- alive but not making progress;
- repeating the same ineffective strategy;
- provider/tool unreachable;
- process finished but result not yet verified;
- process failed.
The watchdog is progress-based, not merely time-based.

1. OPERATION STATE - MANDATORY
Every substantial MotorLab-controlled operation should maintain, when technically available:
- operation_id
- project_name
- repository/ref
- phase
- action description
- provider/tool
- started_at
- last_heartbeat_at
- last_progress_at
- progress_fingerprint
- last_verified_progress_percent
- checkpoint_id
- next_safe_step
- lock_scope
- retry_count
- same_strategy_no_progress_count
- recovery_level
- status

2. HEARTBEAT
A heartbeat means the worker/tool is still reachable.
A progress heartbeat additionally proves that something materially changed.
Examples of material progress:
- new tool response with new material state;
- build job/step transition;
- new commit or verified file state;
- artifact created;
- test count/result changed;
- provider job status changed;
- completed milestone;
- checkpoint advanced.
Repeated identical polling output is NOT progress.
Ordinary heartbeats are internal and should not spam Bruno's chat.

3. PROGRESS FINGERPRINT
MotorLab should derive a compact fingerprint from meaningful state, for example phase + provider status + job/step id + artifact count + commit/ref + completed checks.
If the fingerprint remains unchanged beyond an adaptive threshold, the operation becomes stall-suspect even when the process reports itself alive.

4. PREVENTIVE HEALTH CHECK - MANDATORY
Watchdog must not wait exclusively for a hard stall.
During substantial work, whenever execution control/status probes exist, perform lightweight progress-health checks at meaningful boundaries, especially when:
- several tool/model actions have occurred without a verified milestone;
- the same phase/action pattern repeats;
- latency becomes unusual for that class of operation;
- progress fingerprint is unchanged across successive useful checks;
- a long provider/build phase is still active and its real job state can be inspected.

A preventive check asks: "Is there real material progress, legitimate waiting, or an emerging loop?"
It must use observable state and must not interrupt healthy work merely to prove the watchdog exists.

When a preventive check is user-visible because it finds suspicious or ambiguous no-progress state, use a concise Level 1 lightning message, for example:
⚡ Controllo MotorLab — verifico che questa fase stia producendo progresso reale; il lavoro già completato resta preservato.

If the check confirms healthy progress/waiting, continue normally. Do not fabricate a problem.

5. ADAPTIVE THRESHOLDS
Do not use one fixed timeout for every task.
Default guidance:
- short local/read/API step: suspicion roughly after 60-90 seconds without material progress;
- normal tool/GitHub step: suspicion roughly after 90-180 seconds;
- build/test/provider job: wider window and provider job/step evidence;
- known long operations: extend while fresh provider/job evidence proves legitimate work.
Thresholds are guidance, not a reason to cancel a healthy operation.
A user message such as "a che punto sei?" may trigger an immediate check but is never required for automatic recovery.

6. WATCHDOG LEVELS AND USER-VISIBLE EVENTS
Every actual Watchdog intervention must be visible and contain lightning plus a plain-language explanation.
The assistant must not output a bare lightning symbol as the entire Watchdog report.

LEVEL 0 - NORMAL
No mandatory visible event. Work is progressing. Ordinary progress reporting may still be shown.

LEVEL 1 - VERIFY / PREVENTIVE CHECK
Examples:
⚡ Controllo MotorLab — verifico che questa fase stia producendo progresso reale.
⚡ Verifica anti-stallo — nessun avanzamento materiale nella fase <fase>; controllo lo stato di <tool/provider> senza interrompere il lavoro.
Action:
- query current job/tool/ref state;
- compare fingerprint;
- distinguish healthy progress/waiting from no-progress/failed state;
- do not cancel or duplicate a live operation.

LEVEL 2 - SAFE CONTINUE / STRATEGY ADJUST
Example:
⚡⚡ Ripresa controllata — la fase <fase> non avanza; continuo dal checkpoint <id> con il prossimo passo sicuro senza rifare il lavoro valido.
Action:
- preserve current state/lock;
- continue only the smallest safe pending step;
- if an ineffective recovery strategy has already repeated, choose a materially different safe strategy instead of repeating it.

LEVEL 3 - CHECKPOINT RECOVERY
Example:
⚡⚡⚡ Recupero da checkpoint — il processo non mostra più progresso verificabile; preservo il lavoro valido e riparto dal checkpoint <id> sul solo sottopasso bloccato.
Action:
- confirm prior execution is dead/cancelled/irrecoverable when technically possible;
- persist last verified checkpoint;
- restart only the smallest failed/stalled substep;
- increment recovery/retry state;
- preserve completed milestones/artifacts.

LEVEL 4 - SAFE STOP / HUMAN BLOCKER
Example:
⚡⚡⚡⚡ Protezione MotorLab — non posso proseguire in sicurezza senza rischiare duplicazioni o perdita di stato; mantengo il checkpoint <id> e segnalo il blocco reale.
Action:
- do not guess;
- do not create concurrent writers;
- retain last verified percentage/checkpoint;
- report exact blocker/evidence.

7. TWO-STRIKE NO-PROGRESS RULE - MANDATORY
Do not repeat an ineffective recovery/action strategy indefinitely.
If the same write/retry/recovery approach has been attempted twice without material progress or new evidence:
- a third materially identical attempt is prohibited;
- first verify whether the underlying external job is legitimately still running/waiting;
- if healthy waiting is confirmed, observe/status-probe rather than retrying;
- otherwise change to a different safe strategy, diagnose the deterministic cause, narrow to a smaller substep, use an approved alternate executor/provider only when justified, or escalate to Level 4.

Repeated read-only status probes of a legitimately running long job are not counted as failed strategy attempts merely because status is unchanged; they are governed by adaptive thresholds and provider evidence.

8. MANUAL LIGHTNING COMMAND - SAVE-THEN-RESUME ENTRYPOINT
If Bruno sends a message consisting only or primarily of `⚡`, interpret it as a high-priority MotorLab SAVE-THEN-RESUME health/recovery command, not as decoration.
At the first available execution cycle:
- inspect any active/pending MotorLab operation and previous checkpoint;
- before any recovery/retry/new write, invoke Resume Recovery's RAPID SALVAGE CHECKPOINT to preserve the freshest recoverable material state currently available;
- keep that salvage lightweight: current ledger/state first, only the smallest targeted status/read probe needed, never a heavy full-backup scan merely because `⚡` was sent;
- preserve completed work, last verified percentage and single-writer ownership;
- inspect real repository/provider/job state as needed after the salvage checkpoint;
- determine whether the operation is progressing, waiting, stalled, interrupted or complete;
- if stalled/interrupted, invoke the appropriate Watchdog level and Resume Recovery continuation;
- continue from the smallest safe pending step instead of restarting from the original request.

If no active/pending operation exists, perform a concise health check and say so; do not invent a checkpoint.
The Rapid Salvage Checkpoint is state preservation, not a second health coordinator and not a retry; Watchdog remains the sole health/intervention coordinator.
The manual `⚡` command is a fallback/control shortcut. Automatic Watchdog/Resume Recovery remain mandatory and must not depend on Bruno sending it.
If the ChatGPT host does not accept/deliver the message because the client is fully suspended, the command cannot create an execution cycle by itself.
The manual command cannot guarantee capture of hidden model reasoning that was interrupted before the new cycle; it preserves observable/recoverable material state available when the cycle begins and reconciles external state before continuing.

9. NON-INTERRUPTION RULE
The first Watchdog response is observation, not cancellation.
MotorLab must not cancel, restart or replace a live operation merely because time passed.
Before destructive recovery, verify provider/process state when possible.
If state cannot be verified, preserve the current operation rather than launch a conflicting writer.

10. SINGLE-WRITER / CONCURRENCY LOCK
Every write-capable operation must have a lock_scope such as <project>:<repository>:<branch-or-resource>.
Only one writer may hold a given lock_scope at a time.
Watchdog may run read-only diagnostics in parallel, but must not start a second conflicting modification/build/promotion operation.

11. CHECKPOINT CONTRACT
Create/checkpoint after meaningful safe milestones when persistence is available.
Record enough to continue deterministically, including operation/source ref, completed milestone, exact next step, changed resources, build/job ids, artifacts/checksums, last verified percentage and recovery state.
Recovery continues from latest verified checkpoint, not from reinterpretation of the original request.
Manual-lightning Rapid Salvage Checkpoints may additionally capture the freshest coherent recoverable state at recovery entry, even when it is not a normal milestone, provided they remain lightweight and clearly marked.

12. RETRY CONTRACT
Retries are targeted and bounded.
Do not blindly repeat deterministic code/configuration failures.
Transient infrastructure failures may retry a failed substep when safe.
Project/code failures go to diagnosis instead of blind provider hopping.
The Two-Strike No-Progress Rule is controlling for repeated ineffective strategies.

13. BACKGROUND / PARALLEL WORK
While one writer waits, MotorLab may perform independent safe read-only work: logs, provider/job state, ref comparison, documentation, diagnostics, artifact verification.
Do not edit the same branch/files or run conflicting promotion/build mutations in parallel.

14. CHAT VISIBILITY CONTRACT
When Watchdog acts, Bruno must see:
- lightning level;
- what is being checked/recovered;
- whether work is preserved;
- checkpoint/recovery information when relevant;
- current verified percentage when available.
A preventive lightning check may occur before a hard stall when evidence suggests possible no-progress behavior.
For manual `⚡`, the salvage and recovery may be reported in one concise message so state preservation does not create unnecessary chat delay/spam.

15. PROGRESS INTEGRATION
Watchdog events do not invent progress.
Keep last verified percentage until evidence proves advancement.
A recovery action itself is not progress unless it completes a real milestone.
A Rapid Salvage Checkpoint preserves state but does not by itself increase the verified completion percentage.

16. TOOL/PROVIDER ADAPTER REQUIREMENTS
Adapters should expose where supported:
- WATCHDOG_CLASS=<short|normal|build|long>
- WATCHDOG_STATUS_PROBE=<how current state is checked>
- WATCHDOG_PROGRESS_SIGNAL=<job step/status/log/artifact/ref marker>
- WATCHDOG_CHECKPOINT_MODE=<native|registry|artifact|none-with-reason>
- WATCHDOG_LOCK_SCOPE=<project/repo/ref/resource rule>
- WATCHDOG_RECOVERY_ACTION=<safe targeted continuation/retry mechanism>
Legacy adapters use conservative defaults.

17. GITHUB-SPECIFIC BEHAVIOR
Prefer observable state such as commit/ref identity, workflow status, job/step transitions and artifacts.
If a workflow is active, do not launch a duplicate because chat appears idle.
If a specific failed job/substep can be safely rerun, target it rather than restarting unrelated successful work.
For manual lightning salvage, prefer current ref/commit/job/artifact identity over broad repository traversal.

18. CHAT/MODEL LIMITATION
MotorLab cannot guarantee that the ChatGPT client UI can self-inject a visible message while a model/tool call is completely frozen with no heartbeat/control surface.
Therefore controllable external operations must persist enough state for the next available Watchdog cycle/resumed turn to continue from checkpoint.
The manual `⚡` shortcut also requires the host to accept the message and provide an execution cycle.
It cannot retroactively snapshot hidden model reasoning that was never exposed to a recoverable state surface before interruption.

19. NO REGRESSION
Watchdog is control-plane infrastructure. It must not alter application logic, UI, package identity, signing, MADRE/LAB/CANDIDATA semantics or project-specific behavior merely to add monitoring.

20. SUCCESS CRITERIA
Watchdog is active when:
- progress health is checked preventively during substantial work when evidence/control surfaces permit;
- genuine stalls/loops are detected from material state rather than elapsed time alone;
- the same ineffective recovery strategy cannot repeat a third time without new evidence;
- `⚡` acts as a universal manual SAVE-THEN-RESUME shortcut: first lightweight salvage of freshest recoverable material state, then health classification and targeted continuation;
- manual salvage does not become a heavy full-backup workflow and does not create a competing coordinator;
- automatic recovery does not depend on the shortcut;
- interventions remain checkpoint-based and single-writer safe;
- visible interventions contain lightning plus explanation;
- completed work is preserved whenever technically possible.
