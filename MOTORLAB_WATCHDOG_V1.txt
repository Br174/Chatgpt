MOTORLAB WATCHDOG V1 - PERSISTENT ANTI-STALL CORE

STATUS
Mandatory MotorLab CORE capability.
Established: 2026-09-28.
Repository authority: Br174/Chatgpt.

PURPOSE
Detect stalls/no-progress loops and safely continue without discarding completed work, duplicating writes or corrupting project state.

COORDINATION ROLE
Watchdog is the single coordinator for progress-health detection and anti-stall intervention.
- Foreground Stall Guard owns prevention/chunking/durable handoff.
- Resume Recovery owns deterministic continuation, manual-lightning salvage and monotonic recovery-floor reconstruction.
- Background Execution owns persistent executor/job semantics.
- Progress Reporting owns visible numeric percentages/status density.
- Visual Status owns canonical user-facing emoji+label language.
- Root Cause Closure owns symptom/cause/prevention closure after real faults/anomalies.
- Change Compatibility Guard owns pre-change conflict/overlap/regression checks.
- Pollicino Continuity owns external supported-session liveness/progress evidence, terminal seals and RESUME_READY packaging; Watchdog remains the sole health/stall/recovery-level coordinator.
No competing recovery paths are allowed for the same event.

CORE PRINCIPLE
A timer alone is not proof of a stall. Distinguish healthy progress, slow-but-live progress, legitimate external waiting, no-progress, repeated ineffective strategy, unreachable provider/tool, finished-unverified result and failure using observable evidence.

1. OPERATION STATE
Maintain when available: operation_id, project, repository/ref, phase, action, provider/job, timestamps, progress fingerprint, last verified percent, latest visible verified percent, recovery floor/source, checkpoint, next safe step, lock scope, retry count, same-strategy count, internal recovery level and status.

2. HEARTBEAT / MATERIAL PROGRESS
Heartbeat means reachable; progress means material state changed. Examples: new job step/status, new commit/ref, artifact, test result, checkpoint, verified milestone. Repeated identical polling is not progress.

2A. POLLICINO DUAL-SIGNAL INPUT
When Pollicino evidence exists:
- ALIVE + changing coherent progress fingerprint is strong healthy-progress evidence.
- ALIVE + repeated unchanged fingerprint while progress is expected is STALL_SUSPECTED evidence, not automatic final diagnosis.
- WAITING_EXTERNAL suppresses false loop classification while provider/job evidence remains coherent.
- loss of a real enrolled liveness channel without terminal seal is interruption evidence only after reconciling whether an external executor/job is still alive.
- ordinary ChatGPT UI spinner/Thinking text and absence of an unsupported hidden ping are not liveness evidence.
Pollicino may request Watchdog classification; it may not independently select a recovery strategy.

3. PREVENTIVE CHECKS
During substantial work perform lightweight progress-health checks at meaningful boundaries when progress is unclear, repetitive or unusually slow. Do not interrupt healthy work merely to prove Watchdog exists.

User-facing distinction is mandatory:
- 👍🏻 Procede tutto bene — observable work is healthy and normal.
- 🐢 Lentezza rilevata — observable work is still alive/legitimate but materially slower than normal.
- ⏳ Attesa esterna — a provider/job/build/API/service is legitimately waiting and MotorLab should not duplicate it.
- ⚡ Risveglio / recupero — actual health/recovery investigation or continuation is required.
Do not use ⚡ merely because work is slow or externally waiting when evidence still shows a healthy state.

4. ADAPTIVE THRESHOLDS
Guidance only: short read/API ~60-90s no material progress; normal GitHub/tool ~90-180s; builds/provider jobs use wider evidence-based windows. Healthy active jobs are not cancelled because time passed.

5. INTERNAL RECOVERY LEVELS
Internal recovery levels remain control-plane metadata, not a visual code:
- Level 0 NORMAL: healthy progress/waiting.
- Level 1 VERIFY: inspect current state/fingerprint without cancellation.
- Level 2 SAFE_CONTINUE: continue smallest safe pending step or choose a different safe strategy.
- Level 3 CHECKPOINT_RECOVERY: reconcile state and restart only the failed/stalled substep.
- Level 4 SAFE_STOP: stop because safe continuation is not possible.

User-facing mapping follows Visual Status:
- healthy normal: 👍🏻 Procede tutto bene — ...
- slow but live: 🐢 Lentezza rilevata — ...
- legitimate external wait: ⏳ Attesa esterna — ...
- Level 1/3 actual recovery activity: ⚡ Risveglio / recupero — ...
- Level 2 when strategy must materially change: 🧭 Cambiare approccio — ...
- Level 4: 🛑 Stop di sicurezza / blocco reale — ...
- small bounded issue discovered during diagnosis: ⚠️ Piccolo problema risolvibile — ...

6. TWO-STRIKE NO-PROGRESS RULE
After two materially identical ineffective write/retry/recovery attempts with no progress/new evidence, a third identical attempt is prohibited. First distinguish healthy external waiting. Otherwise diagnose, narrow the substep, change strategy, use an approved alternate executor only when justified, or safe-stop.

7. MANUAL `⚡` COMMAND - SAVE THEN RESUME
If Bruno sends only/primarily `⚡`, treat it as the manual MotorLab health/recovery command.
At the first available execution cycle:
- inspect active/pending operation and previous checkpoint;
- create/refresh the lightweight Rapid Salvage Checkpoint before recovery/retry/new write;
- reconstruct the same-operation Monotonic Recovery Floor;
- reconcile latest verified visible progress with repo/provider/job/artifact evidence;
- preserve completed work, highest coherent verified progress and single-writer ownership;
- keep salvage bounded/fast; never perform a heavy full backup merely because lightning was sent;
- classify health;
- if healthy but slow, report 🐢 Lentezza rilevata and keep the same live operation;
- if legitimately waiting externally, report ⏳ Attesa esterna and keep the same live operation;
- if stalled/interrupted, report ⚡ Risveglio / recupero and continue the smallest safe pending step compatible with the floor;
- never duplicate/cancel healthy external work.

8. NON-INTERRUPTION RULE
First response is observation, not cancellation. Verify provider/process state before destructive recovery when possible. If state cannot be safely verified, preserve the operation rather than launch a conflicting writer.

9. SINGLE-WRITER
Only one writer may mutate the same project/repo/ref/resource scope. Read-only diagnostics may run independently.

PROJECT-LEVEL WATCHDOG: completion of one tool/subtask/checkpoint is healthy progress, not a terminal seal or stall. A controlled stop requires full project verification, evidenced blocker/safety boundary, or real verified durable handoff; never escalate solely due to a routine completed node.
10. CHECKPOINT CONTRACT
Checkpoint after meaningful safe milestones when persistence exists. Checkpoint creation is not a pause, response-finalization trigger, approval request, or reason to cancel healthy parallel runners. Record enough to continue deterministically: operation/ref, completed milestone, exact next step, changed resources, job ids, artifacts/checksums, verified percent, visible verified percent, recovery floor/source and recovery state.
Recovery uses freshest coherent verified state, never blindly an older checkpoint.

11. RETRIES
Retries are targeted and bounded. Deterministic code/config failures go to diagnosis rather than blind repetition/provider hopping.

12. BACKGROUND / PARALLEL WORK
While one writer waits, independent safe read-only diagnostics may continue. Do not launch conflicting writes/build/promotion work.

13. CHAT VISIBILITY + PERCENTAGE
When Watchdog surfaces a meaningful status during a substantial quantified operation, Bruno sees:
- the canonical emoji + canonical label;
- what is being checked/recovered/waited on;
- whether completed work is preserved;
- checkpoint/recovery information when relevant;
- the classic `Progresso MotorLab: N%` whenever a verified percentage exists.
Do not hide the percentage just because the same N% was already shown; repetition is correct when state changes without new verified progress.

14. PROGRESS / MONOTONIC FLOOR
Watchdog does not invent progress. Keep highest coherent verified percentage for the same operation unless material evidence invalidates it. Older checkpoints, interrupted chat, failed/queued lightning, elapsed time or conversation-load failure are not invalidation evidence.
A real regression requires material evidence such as verified rollback/reset, milestone-invalidating job failure, corrupted/missing required artifact or an explicitly approved replacement operation/scale, and must be explained visibly.

15. ROOT-CAUSE HANDOFF AFTER FAULT / RECOVERY - MANDATORY
When Watchdog detects a real failure/anomaly or performs a non-trivial recovery:
- immediate recovery/containment may restore progress;
- if the fault is non-transient, repeated, configuration/state related, unexpected, or capable of recurring, invoke MOTORLAB_ROOT_CAUSE_CLOSURE_V1.txt before definitive problem closure;
- identify whether the cause is confirmed, hypothesized, external or unknown;
- correct/prevent the causal mechanism when safe;
- check the smallest relevant recurrence surface;
- do not emit `✅ Problema risolto` solely because a retry/recovery succeeded once.

Purely transient provider noise may be closed with evidence that the external transient condition cleared and no project-side causal defect exists; otherwise Root Cause Closure remains controlling.

16. GITHUB-SPECIFIC BEHAVIOR
Prefer commit/ref identity, workflow/job/step transitions and artifacts. Do not duplicate an active workflow because chat appears idle. For manual salvage prefer targeted current ref/job/artifact state over broad traversal.
A GitHub job that remains alive but slow may use 🐢; a queued/running job legitimately awaiting provider progress may use ⏳; use ⚡ only when a real health/recovery check is warranted.
If a control-plane-only commit unexpectedly triggers application build/release workflows, classify it as an anomaly and route to Root Cause Closure rather than treating the build as normal app lifecycle progress.

17. PLATFORM LIMIT
MotorLab cannot self-inject while the host exposes no execution cycle, and the manual lightning command also requires delivery of the user message. It cannot retroactively snapshot hidden model reasoning that was never persisted to a recoverable state surface.

18. VISUAL STATUS PRECEDENCE
MOTORLAB_VISUAL_STATUS_V1.txt is authoritative for user-facing emoji semantics and labels.
Legacy repeated lightning counts in older examples/history are obsolete as user-facing status language.
Internal Watchdog levels remain fully active and must not be inferred from emoji count.

19. NO REGRESSION
Watchdog is control-plane infrastructure and must not alter application logic/UI/package/signing/lifecycle merely to add monitoring.

SUCCESS CRITERIA
Watchdog is active when stalls/loops are evidence-based, slow work and external waiting are distinguished from recovery, two-strike protection is enforced, manual lightning saves/reconciles then resumes, monotonic recovery is preserved, single-writer safety holds, meaningful visible status carries the verified numeric percentage when available, and real recovered faults pass through Root Cause Closure before being called definitively solved.
