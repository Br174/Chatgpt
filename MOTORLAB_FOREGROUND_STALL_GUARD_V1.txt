MOTORLAB FOREGROUND STALL GUARD V1 - PREVENT FOREGROUND SILENCE + PREPARE DURABLE RECOVERY

STATUS
Mandatory MotorLab CORE capability.
Established: 2026-09-29.
Central authority: Br174/Chatgpt.

PURPOSE
Reduce long silent/apparently frozen foreground phases by preparing durable state before risky work, preferring persistent execution for long/backgroundable phases, preventing emerging no-progress loops and making foreground-only operations resumable.

ROLE / PRECEDENCE
Foreground Stall Guard owns prevention before risky execution: classification, preflight checkpoint, chunking and durable handoff preparation.
Watchdog owns health detection/intervention and strategy-switch decisions.
Resume Recovery owns continuation after interruption.
This guard must not launch an independent competing recovery path.

CORE PRINCIPLE
PREVENT THE UNRECOVERABLE FOREGROUND GAP BEFORE IT STARTS.
A normal ChatGPT foreground turn is not a durable executor. UI "still processing" is not proof MotorLab has a live control cycle.

1. FOREGROUND RISK CLASSIFICATION - MANDATORY
Before substantial execution classify:
- FOREGROUND_SHORT: bounded immediate tool/model steps;
- FOREGROUND_RISK: long reasoning, many serial tool calls, provider delay, build wait, large traversal or uncertain latency;
- BACKGROUNDABLE: safe for persistent executor;
- USER_BLOCKING: Bruno's decision is needed.

2. PRE-FLIGHT CHECKPOINT - MANDATORY FOR FOREGROUND_RISK/BACKGROUNDABLE
Before entering such a phase, persist/reconstruct when technically available:
- operation_id;
- project/repository/ref;
- approved scope;
- current phase;
- completed work;
- exact next safe step;
- pending verification;
- last verified percentage;
- source/ref identity;
- lock_scope;
- provider/job identifiers;
- same_strategy_no_progress_count when relevant.
Do not begin a fragile long phase without a recoverable next step.

3. DURABLE-EXECUTOR FIRST RULE
If the next autonomous phase is BACKGROUNDABLE and an approved persistent executor is available, hand it off before depending on a long ordinary chat turn.
Examples: adapter-approved GitHub Actions/runner, remote worker, Work/cloud execution or another durable executor.
Do not claim background continuity until the handoff is real and durable state/job identity exists.
When that executor exposes a supported liveness/control surface, enroll the operation/session in Pollicino before entering the opaque phase.

4. FOREGROUND CHUNKING RULE
If no persistent executor is available:
- split work into smallest practical safe segments;
- prefer bounded write/tool groups followed by state reconciliation;
- checkpoint after material milestones;
- revalidate external/repository state before the next write segment;
- avoid unnecessary rereading/reasoning loops.
This optimizes recoverability, not message spam.

4A. R27 ZERO-IDLE SIDEWORK
When a foreground-risk task enters a known wait/analysis phase, all compatible independent useful work already READY should continue immediately through Velocity/Execution Fabric. Safe predeclared productive sidework may also be spawned immediately when its expected gain exceeds overhead. Do not add a 3-second or 10-second pause before different useful work begins. Recovery of the same unresolved task remains separate and uses the existing Fresh Hedge/Watchdog rules.

5. EMERGING LOOP PREVENTION
Before continuing a repeated foreground pattern, check whether the last actions materially changed progress fingerprint/state.
If the same recovery/write/retry strategy has produced no material progress twice:
- do not start a third materially identical attempt;
- preserve/update checkpoint;
- invoke Watchdog's Two-Strike No-Progress Rule;
- switch to a materially different safe strategy, diagnosis, smaller substep or safe-stop as Watchdog determines.
Legitimate repeated read-only status checks of a healthy external job are not automatically an ineffective strategy.

6. PREVENTIVE WATCHDOG HANDOFF
If chunking reveals repeated unchanged state, unusual latency, repeated action pattern or missing verified milestone, hand health assessment to Watchdog before a hard stall occurs.
When useful and execution control exists, Watchdog may surface a Level 1 lightning check.
This guard itself does not invent a stall.

7. NO FALSE HEARTBEAT
A ChatGPT UI message saying systems are still processing, spinner, typing indicator or elapsed time is NOT a MotorLab heartbeat or material progress.
An ordinary opaque ChatGPT reasoning turn also cannot be treated as queryable merely because Pollicino exists. Real heartbeat/probe claims require an enrolled executor/host surface that actually exposes them.
Only observable model/tool/provider/job/repository state counts.

8. HOST-SUSPENSION DETECTION AT NEXT CONTROL CYCLE
If host/client shows extended processing and no MotorLab cycle is available, MotorLab cannot inject lightning during that unavailable interval.
At the first later execution cycle:
- load Resume Recovery;
- restore checkpoint/pending action;
- inspect current provider/repository/job state before writing;
- preserve single-writer safety;
- let Watchdog classify the interruption/stall;
- emit lightning if a real recovery is performed;
- continue smallest safe pending step without requiring task reconstruction.

9. VISIBLE WATCHDOG SEMANTICS
Lightning is shown only when MotorLab has an execution cycle and Watchdog actually performs a health/recovery action.
Preventive Level 1 lightning is allowed before a hard stall when evidence justifies a progress-health check.
Do not promise lightning while host/model is fully suspended.

10. LONG PROVIDER/BUILD RULE
Do not keep a long build/provider job dependent on foreground chat when durable job state exists.
Start/hand off job, record id/checkpoint and inspect via status probes. Later chat reconciliation must not duplicate the job.

11. FAILURE / NO DURABLE EXECUTOR
If a long task cannot be safely backgrounded:
- preserve latest checkpoint;
- use bounded foreground segments;
- apply Watchdog preventive checks when evidence suggests no-progress;
- never claim independent wake-up capability;
- resume at first available cycle if host suspends.

12. RELATION TO WATCHDOG
Watchdog detects health/no-progress and decides intervention/strategy level.
Foreground Stall Guard reduces the chance of reaching a state with no control surface and feeds Watchdog explicit checkpoint/fingerprint state.

13. RELATION TO RESUME RECOVERY
Resume Recovery handles same-turn continuation and first-available-cycle recovery. This guard ensures useful checkpoint and next action exist first.

14. RELATION TO BACKGROUND EXECUTION
Background Execution defines durable jobs. This guard decides early when long work should move from ordinary foreground to that path.

15. MANUAL `⚡`
The user `⚡` shortcut is handled by Watchdog + Resume Recovery. Foreground Stall Guard does not create a separate manual recovery implementation. When such a cycle begins, provide current checkpoint/risk state to those modules when available.

16. NO PROJECT REGRESSION
This module changes MotorLab orchestration only. It must not alter application logic, UI, package/signing identity, source lineage, project-native engines, lifecycle semantics or approved project behavior.

17. SUCCESS CRITERIA
The guard is active when:
- risky phases are checkpointed before they begin;
- backgroundable long work uses real persistent execution when available;
- ordinary-chat-only work uses recoverable bounded segments;
- emerging two-attempt no-progress loops are handed to Watchdog before a third identical attempt;
- UI processing states are never mistaken for progress;
- first later cycles recover deterministically;
- no duplicate recovery mechanism competes with Watchdog/Resume Recovery.

R37 CONTINUE-UNTIL-TERMINAL RULE (2026-10-14; USER APPROVED)
WHOLE-PROJECT FOREGROUND PRECEDENCE: a completed microtask is not a reason to finalize; keep executing approved ready project steps while the host grants control. Preserve real blockers and host limits.
Within each available execution cycle, after a status explanation or partial report, continue already approved programming, diagnostics, verification and artifact work without requiring another 'procedi'. A status update is NOT a stop signal. Continue to verified completion or a concrete nondelegable user action, material authorization/safety boundary, or genuine host/tool limit. Before a forced stop, record a precise resumable checkpoint, progress and next executable step. If a real durable approved executor exists, hand off suitable background work and report its job ID; do not claim ordinary ChatGPT continues after its execution cycle ends. No unbounded spin or bypass of approvals, locks or risk gates.
