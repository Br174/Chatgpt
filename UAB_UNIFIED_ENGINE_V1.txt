MOTORLAB UNIFIED ENGINE V1

COMPATIBILITY NOTE
Official engine name: MotorLab.
Legacy UAB filenames, variables, branch conventions and adapter keys remain valid during gradual migration so existing projects do not break.

PURPOSE
This is the single lifecycle/control model for every Bruno project handled through MotorLab. Projects may differ in language, build system, package/signing rules and delivery channel, but they do not get independent lifecycle engines.

UNIVERSAL LIFECYCLE
MADRE -> LAB -> CANDIDATA -> NEW MADRE

1. MADRE
- The MADRE is the last user-approved, verified stable state.
- It is immutable: do not edit, force-move, overwrite, rebuild in-place or replace its permanent release asset.
- Every project must have one current MADRE reference, even when the project is web/PWA rather than Android.
- Historical MADRI remain preserved.
- For Android projects, a MADRE permanent GitHub Release must use a unique immutable tag/version and keep APK/ZIP/checksums permanently.
- For web/PWA projects, the MADRE reference is the approved stable source/deployment state; the artifact type follows the project adapter.

2. LAB - ATOMIC EXPERIMENT RULE
- Every experiment starts directly from the current MADRE, never from a failed LAB and never from an unapproved CANDIDATA.
- A LAB must contain ONE requested modification at a time, or at most one small inseparable group of tightly related changes that together implement the same requested modification.
- Do not accumulate unrelated feature requests, later experiments or opportunistic cleanup into the same LAB.
- If a second unrelated modification is requested, create a new LAB again from the current MADRE unless Bruno explicitly asks to combine them.
- The LAB must record its exact MADRE source ref/commit and its exact approved change-set so the same change can be replayed without reinterpretation.
- A LAB may fail. If it fails, abandon it and start the next experiment again from the current MADRE unless Bruno explicitly asks to continue that exact LAB.
- Android LAB builds must use a distinct package/application ID whenever parallel installation is required by the project adapter.
- LAB output is temporary Actions artifact/test output only. LAB must not overwrite or replace a MADRE release.

3. CANDIDATA - EXACT REPLAY RULE
- When Bruno says that a LAB may become CANDIDATA, do NOT rename, move or directly promote the LAB branch.
- Create the CANDIDATA fresh from the SAME MADRE ref/commit from which that approved LAB was created.
- Apply exactly the same approved modification/change-set that was tested in the LAB. Do not add extra fixes, cleanup, refactors, dependency changes or other interpretation unless Bruno explicitly approves them.
- The expected source relationship is: CANDIDATA = SAME MADRE + SAME APPROVED CHANGE-SET.
- If the approved LAB contained one atomic commit, replay that exact commit/change-set onto the fresh CANDIDATA where technically possible. If the mechanism differs, verify that the resulting source diff against the MADRE is equivalent to the approved LAB diff.
- Candidate tests must cover both the requested feature and core regression gates defined by the adapter (for example audio playback, startup, navigation, signing/package identity, critical UI flows).
- CANDIDATA remains non-authoritative until Bruno approves the real result.
- Candidate binaries are test artifacts, not permanent MADRE releases.

4. NEW MADRE - EXACT CANDIDATE SOURCE RULE
- Promotion occurs only after candidate verification and explicit approval.
- The new MADRE source ref/tag must point to the EXACT source commit SHA of the approved CANDIDATA. Do not rebuild the source history, cherry-pick again, regenerate equivalent source or create a new source commit merely for promotion.
- In other words: the source Bruno approved as CANDIDATA is the source that becomes the NEW MADRE.
- If an Android adapter requires different final packaging/signing metadata for a MADRE binary, that binary may be packaged/signed from the exact approved CANDIDATA source commit, but no application source changes are allowed during promotion. The adapter must verify package/signing sanity separately.
- Promotion creates a new immutable MADRE reference and a new permanent release/version where the project has release artifacts.
- Never delete or replace the previous MADRE when promoting a new one.
- The previous MADRE remains an immediate rollback point.

5. PROMOTION IDENTITY RECORD - MANDATORY
For every LAB that is eligible for promotion, MotorLab must be able to identify:
- MADRE source ref and commit SHA;
- LAB source ref and commit SHA;
- exact approved change-set/diff identity;
- CANDIDATA source ref and commit SHA;
- verification result;
- final NEW MADRE ref pointing to the approved CANDIDATA source SHA.
If this chain cannot be established, automatic promotion must stop instead of guessing.

RELEASE STORAGE RULE
GitHub Releases are a deposit of good, approved versions.
- Permanent Releases are for MADRI only, unless an adapter explicitly defines another approved-release class.
- No fixed tag/asset may overwrite a previous MADRE binary.
- Do not use --clobber, overwrite_files=true or equivalent against an immutable MADRE tag.
- A 'latest' concept may exist only as metadata/pointer to the newest immutable MADRE. It must not be the sole storage location and must never destroy the previous binary.
- Downloader-style stable URLs may use GitHub's latest-release pointer while each underlying release tag remains unique and immutable.

ONE ENGINE / MANY ADAPTERS
MotorLab CORE owns:
- lifecycle state and promotion rules;
- atomic LAB scope rule;
- exact LAB change-set replay into CANDIDATA;
- exact approved CANDIDATA source SHA promotion to NEW MADRE;
- frequent verified progress percentages and micro-milestone reporting;
- cache requirements;
- free-first provider routing;
- immutable release policy;
- artifact verification and checksums;
- rollback/history rules;
- rule that 100% means verified completion only;
- anti-stall watchdog, heartbeat interpretation and progress fingerprints;
- checkpoint/recovery rules;
- single-writer lock/concurrency safety;
- visible watchdog intervention messages using lightning emoji plus explanation;
- persistent visual success feedback using fireworks plus explanation for verified completions.

Each project adapter may define only project-specific mechanics:
- project type (Android, hybrid, web/PWA, delivery-only);
- build/test commands or workflow;
- safe patch/repack capability;
- package/application ID strategy;
- signing requirements;
- cache implementation;
- regression gates;
- artifact names/types;
- deployment/delivery destination;
- watchdog operation class, status probe, progress signal, checkpoint mode, lock scope and safe recovery action;
- project-specific deterministic progress micro-milestones when available.

An adapter may not override MADRE immutability, atomic LAB-from-MADRE, exact CANDIDATA reconstruction from the same MADRE and same approved change-set, approval-before-MADRE, exact candidate-source promotion, permanent history retention, MotorLab Watchdog safety rules, MotorLab visual-status rules, or MotorLab progress-reporting rules.

PROGRESS CONTRACT
Broad default milestones:
5 accepted/scope locked
15 current MADRE identified and protected
30 LAB/config changes applied
45 source/static checks complete
60 cache/toolchain/preflight ready
75 build/test output complete
85 regression/artifact verification complete
95 candidate/handoff or promotion package ready
100 requested state verified and delivered

Progress reporting behavior:
- report percentage throughout substantial work, not only at broad milestones;
- report when meaningful subtasks start/finish, phases change, files/config are applied, checks/build/test steps change, artifacts/checkpoints change, watchdog/recovery events occur, and handoff/promotion/delivery state changes;
- as a practical default, avoid more than roughly 1-3 meaningful operations/tool interactions without a user-visible progress update when the chat surface permits;
- long single external operations should surface provider/job phase changes when available;
- broad phases may be divided into real deterministic micro-milestones so intermediate percentages are justified by completed work;
- the same verified percentage may be repeated with a new explanation when status changes but no additional completion is yet verified;
- never increase progress because time passed;
- non-applicable phases are removed and progress recalculated;
- on failure retain the last verified percentage and identify the failing substep;
- watchdog events should include the last verified percentage when visible;
- fireworks messages should include percentage when useful;
- never claim 100% on a failed, pending or unverified result;
- detailed mandatory behavior is defined by MOTORLAB_PROGRESS_REPORTING_V1.txt.

VISUAL SUCCESS CONTRACT
- Every meaningful verified success must be visibly surfaced to Bruno.
- Use 🎆🎆 for small verified successes.
- Use 🎆🎆🎆 for significant milestones, completed features, builds or regression successes.
- Use 🎆🎆🎆🎆 for major/final verified completions.
- Fireworks must always be accompanied by an explanation of what succeeded and, where relevant, how it was verified.
- Do not show fireworks for merely started, pending, assumed or unverified work.
- Small resolved items receive their own success signal; do not reserve fireworks only for the end of a long task.
- Fireworks complement progress percentages and do not create progress by themselves.
- Watchdog lightning and success fireworks are distinct status languages.
- Detailed mandatory behavior is defined by MOTORLAB_VISUAL_STATUS_V1.txt.

WATCHDOG / ANTI-STALL CONTRACT
- Long-running work must be assessed by material progress, not by time alone.
- Ordinary heartbeat/status checks are internal and must not spam Bruno.
- Repeated identical state is not material progress.
- Thresholds are adaptive to operation type and provider evidence.
- First intervention is non-destructive verification.
- Visible levels are:
  ⚡ Verifica anti-stallo — explain what appears stalled and what is being checked.
  ⚡⚡ Ripresa controllata — explain how execution continues without discarding completed work.
  ⚡⚡⚡ Recupero da checkpoint — explain which verified checkpoint/substep is being recovered.
  ⚡⚡⚡⚡ Protezione MotorLab — explain why automatic recovery cannot continue safely.
- Lightning emoji must always be accompanied by an explanation.
- The watchdog must preserve completed milestones, verified artifacts and checkpoint state whenever technically possible.
- Read-only diagnostics may run in parallel, but two conflicting writers may not operate on the same lock scope.
- Recovery targets the smallest stalled/failed substep and bounded retries prevent infinite loops.
- Detailed mandatory behavior is defined by MOTORLAB_WATCHDOG_V1.txt.

CACHE CONTRACT
Every adapter must use safe persistent cache when supported. Android/Gradle routes use official Gradle caching and --build-cache unless documented incompatible. Node/web routes persist package-manager download cache. Cache misses are allowed and repopulate automatically.

ROUTING CONTRACT
- Public repositories: standard GitHub-hosted runners are the normal remote route.
- Private repositories: conserve included allowance; no automatic paid overage.
- Codemagic is REMOVED from MotorLab routing and must not be selected as primary, fallback or emergency provider.
- If the allowed GitHub/local route is unavailable, stop and report the blocker instead of provider-hopping.
- Real project/code failures are diagnosed; do not blindly rerun the same broken build on another provider.

REGRESSION RULE
A feature-specific change is not acceptable if it breaks an unrelated core function. Candidate verification must include the project's adapter-defined core health checks before promotion.

ROLLBACK RULE
If a LAB or CANDIDATA introduces a serious regression, discard it and return to the current MADRE. Do not repair on top of a corrupted experimental lineage unless Bruno explicitly chooses that path.

SINGLE-SOURCE-OF-TRUTH RULE
Br174/Chatgpt is the private MotorLab control/registry repository. This file, UAB_ENGINE_CONTRACT.txt, UAB_GLOBAL_APK_POLICY.txt, UAB_PROJECT_ROUTING.txt, MOTORLAB_WATCHDOG_V1.txt, MOTORLAB_VISUAL_STATUS_V1.txt and MOTORLAB_PROGRESS_REPORTING_V1.txt define the canonical engine behavior. Project repositories keep only thin adapters/workflows required to execute their mechanics.
