MOTORLAB UNIFIED ENGINE V1

COMPATIBILITY NOTE
Official engine name: MotorLab.
Legacy UAB filenames, variables, branch conventions and adapter keys remain valid during gradual migration so existing projects do not break.

PURPOSE
This is the single lifecycle/control model for every Bruno project handled through MotorLab. Projects may differ in language, build system, package/signing rules and delivery channel, but they do not get independent lifecycle engines.

UNIVERSAL LIFECYCLE
MADRE -> LAB -> CANDIDATA -> NEW MADRE


PAIRED SAFETY CHECKPOINTS
For every verified LAB NN aggiornamento in Android update-family mode, MotorLab produces LAB di sicurezza NN from the exact same functional source state. The safety artifact uses a different package/family and a different test-only certificate, is immutable, and becomes a recovery checkpoint. If the active family breaks after many revisions, a new active update family may start from the last known-good safety checkpoint rather than returning to MADRE. Safety is not CANDIDATA and cannot promote directly to MADRE.

ANDROID UPDATE-FAMILY MODE
For Android projects explicitly using Bruno's persistent test-family workflow:
- one new LAB family is installed/configured once;
- later visible LAB NN aggiornamento revisions keep the same applicationId and signing certificate and strictly increase versionCode;
- the immediately previous LAB aggiornamento is the source baseline for the next revision inside that family;
- CANDIDATA is a new immutable family created from the exact approved LAB state/change-set, never a package-id conversion of the LAB;
- if a candidate needs changes, return to the LAB family and create the next LAB aggiornamento, then create a new candidate number;
- approved CANDIDATA -> NEW MADRE promotes the same candidate source identity/family according to project signing policy;
- package/signing/versionCode compatibility is part of artifact verification;
- detailed rules are in MOTORLAB_UPDATE_FAMILY_LIFECYCLE_V1.txt.

1. MADRE
- The MADRE is the last user-approved, verified stable state.
- It is immutable: do not edit, force-move, overwrite, rebuild in-place or replace its permanent release asset.
- Every project must have one current MADRE reference, even when the project is web/PWA rather than Android.
- Historical MADRI remain preserved.
- For Android projects, a MADRE permanent GitHub Release must use a unique immutable tag/version and keep APK/ZIP/checksums permanently.
- For web/PWA projects, the MADRE reference is the approved stable source/deployment state; the artifact type follows the project adapter.

2. LAB - ATOMIC EXPERIMENT RULE
- Every experiment starts directly from the current MADRE, never from a failed LAB and never from an unapproved CANDIDATA.
- A LAB must contain ONE requested modification at a time, or at most one small inseparable group of tightly related changes that together implement the same requested modification.
- Do not accumulate unrelated feature requests, later experiments or opportunistic cleanup into the same LAB.
- If a second unrelated modification is requested, create a new LAB again from the current MADRE unless Bruno explicitly asks to combine them.
- The LAB must record its exact MADRE source ref/commit and its exact approved change-set so the same change can be replayed without reinterpretation.
- A LAB may fail. If it fails, abandon it and start the next experiment again from the current MADRE unless Bruno explicitly asks to continue that exact LAB.
- Android LAB builds must use a distinct package/application ID whenever parallel installation is required by the project adapter.
- LAB output is temporary Actions artifact/test output only. LAB must not overwrite or replace a MADRE release.

3. CANDIDATA - EXACT REPLAY RULE
- When Bruno says that a LAB may become CANDIDATA, do NOT rename, move or directly promote the LAB branch.
- Create the CANDIDATA fresh from the SAME MADRE ref/commit from which that approved LAB was created.
- Apply exactly the same approved modification/change-set that was tested in the LAB. Do not add extra fixes, cleanup, refactors, dependency changes or other interpretation unless Bruno explicitly approves them.
- The expected source relationship is: CANDIDATA = SAME MADRE + SAME APPROVED CHANGE-SET.
- If the approved LAB contained one atomic commit, replay that exact commit/change-set onto the fresh CANDIDATA where technically possible. If the mechanism differs, verify that the resulting source diff against the MADRE is equivalent to the approved LAB diff.
- Candidate tests must cover both the requested feature and core regression gates defined by the adapter.
- CANDIDATA remains non-authoritative until Bruno approves the real result.
- Candidate binaries are test artifacts, not permanent MADRE releases.

4. NEW MADRE - EXACT CANDIDATE SOURCE RULE
- Promotion occurs only after candidate verification and explicit approval.
- The new MADRE source ref/tag must point to the EXACT source commit SHA of the approved CANDIDATA.
- Do not rebuild the source history, cherry-pick again, regenerate equivalent source or create a new source commit merely for promotion.
- If an Android adapter requires different final packaging/signing metadata for a MADRE binary, that binary may be packaged/signed from the exact approved CANDIDATA source commit, but no application source changes are allowed during promotion.
- Promotion creates a new immutable MADRE reference and a new permanent release/version where the project has release artifacts.
- Never delete or replace the previous MADRE when promoting a new one.
- The previous MADRE remains an immediate rollback point.

5. PROMOTION IDENTITY RECORD - MANDATORY
For every LAB eligible for promotion, MotorLab must be able to identify MADRE source ref/SHA, LAB ref/SHA, exact approved change-set, CANDIDATA ref/SHA, verification result and final NEW MADRE ref pointing to the approved CANDIDATA source SHA.
If this chain cannot be established, automatic promotion must stop instead of guessing.

RELEASE STORAGE RULE
GitHub Releases are a deposit of good, approved versions.
- Permanent Releases are for MADRI only unless an adapter explicitly defines another approved-release class.
- No fixed tag/asset may overwrite a previous MADRE binary.
- Do not use --clobber, overwrite_files=true or equivalent against an immutable MADRE tag.
- A 'latest' concept may exist only as metadata/pointer to the newest immutable MADRE and must never destroy previous binaries.

ONE ENGINE / MANY ADAPTERS
MotorLab CORE owns:
- lifecycle state and promotion rules;
- atomic LAB scope rule;
- exact LAB change-set replay into CANDIDATA;
- exact approved CANDIDATA source SHA promotion to NEW MADRE;
- frequent verified progress percentages and micro-milestone reporting;
- cache requirements;
- free-first provider routing;
- immutable release policy;
- artifact verification and checksums;
- rollback/history rules;
- rule that 100% means verified completion only;
- anti-stall watchdog, heartbeat interpretation and progress fingerprints;
- checkpoint/recovery rules;
- single-writer lock/concurrency safety;
- visible watchdog intervention messages using lightning emoji plus explanation;
- persistent visual success feedback using fireworks plus explanation for verified completions;
- persistent background-execution policy;
- durable background job/checkpoint state;
- single-chat continuity so the project chat remains the canonical user-facing thread while executors may change behind the scenes.

Each project adapter may define only project-specific mechanics:
- project type;
- build/test commands or workflow;
- safe patch/repack capability;
- package/application ID strategy;
- signing requirements;
- cache implementation;
- regression gates;
- artifact names/types;
- deployment/delivery destination;
- watchdog operation class/status/progress/checkpoint/lock/recovery;
- project-specific deterministic progress micro-milestones;
- background executor/start/status/resume/cancel/checkpoint/lock/notification behavior.

An adapter may not override MADRE immutability, atomic lifecycle safety, exact CANDIDATA reconstruction, approval-before-MADRE, exact candidate-source promotion, update-family identity/signing/versionCode continuity when enabled, permanent history retention, Watchdog safety, visual-status rules, progress-reporting rules, or Background Execution / Single-Chat Continuity rules.

PROGRESS CONTRACT
Broad default milestones:
5 accepted/scope locked
15 current MADRE identified and protected
30 LAB/config changes applied
45 source/static checks complete
60 cache/toolchain/preflight ready
75 build/test output complete
85 regression/artifact verification complete
95 candidate/handoff or promotion package ready
100 requested state verified and delivered

Progress reporting behavior:
- report throughout substantial work, not only at broad milestones;
- report at meaningful subtask/phase/check/build/artifact/checkpoint/watchdog/recovery transitions;
- avoid more than roughly 1-3 meaningful operations without a user-visible update when the surface permits;
- use real micro-milestones for justified intermediate percentages;
- same verified percentage may be repeated with new status;
- never increase because time passed;
- on failure retain last verified percentage;
- watchdog events should include current percentage when visible;
- fireworks messages should include percentage when useful;
- never claim 100% on failed, pending or unverified work;
- detailed behavior is defined by MOTORLAB_PROGRESS_REPORTING_V1.txt.

BACKGROUND EXECUTION / SINGLE-CHAT CONTINUITY CONTRACT
- The project chat where Bruno initiates or continues a task is the canonical user-facing thread when the platform exposes a usable chat reference.
- MotorLab must not make Bruno manually migrate among normal Chat, Work, MotorLab or another executor conversation merely because backend execution changes.
- MotorLab must not wait for app-exit detection. Before a long phase, classify the task as CHAT_LOCAL, BACKGROUNDABLE, USER_BLOCKING or MIXED.
- BACKGROUNDABLE/MIXED autonomous phases should be moved proactively to a real durable executor when available and allowed.
- A normal ChatGPT model turn by itself is NOT durable background execution.
- Durable executors may include adapter-approved GitHub Actions, persistent workers/services, runners, Work/cloud when suitable, or other backends independent of the visible chat lifetime.
- Once handed off safely, the job continues through pre-approved autonomous steps while Bruno is away.
- Normal behavior is CONTINUE + SAVE CHECKPOINTS; checkpoint does not mean pause-on-exit.
- Durable job state preserves operation/project/canonical chat/executor/job/ref/SHA/scope/phase/verified percentage/heartbeat/checkpoint/next step/lock/retry/artifact information when available.
- Job states: QUEUED, RUNNING, WAITING_EXTERNAL, WAITING_USER, RECOVERING, COMPLETED, FAILED_SAFE, CANCELLED_BY_USER.
- On return to the canonical chat, reconcile durable state before starting new work and report what progressed while Bruno was away.
- Never start a duplicate writer when the durable background job is still active on the same lock scope.
- If executor quota/availability ends, preserve completed work/checkpoint and move to another adapter-approved executor when safe and authorized; otherwise stop safely with the blocker.
- Work is optional execution capability, not a required second user-facing chat.
- Notifications may alert completion/WAITING_USER when supported but do not replace the canonical project conversation.
- MotorLab cannot force a suspended ordinary foreground ChatGPT turn to continue computing, so background claims are allowed only after real durable handoff.
- Detailed mandatory behavior is defined by MOTORLAB_BACKGROUND_EXECUTION_V1.txt.

VISUAL SUCCESS CONTRACT
- Every meaningful verified success must be visibly surfaced to Bruno.
- Use 🎆🎆 for small verified successes, 🎆🎆🎆 for significant milestones/builds/features, 🎆🎆🎆🎆 for major/final verified completions.
- Fireworks must always be accompanied by an explanation.
- Do not show fireworks for started, pending, assumed or unverified work.
- Fireworks complement progress percentages and do not create progress by themselves.
- Watchdog lightning and success fireworks are distinct status languages.
- Detailed mandatory behavior is defined by MOTORLAB_VISUAL_STATUS_V1.txt.

WATCHDOG / ANTI-STALL CONTRACT
- Long-running work is assessed by material progress, not time alone.
- Ordinary heartbeat/status checks are internal and must not spam Bruno.
- Repeated identical state is not material progress.
- Thresholds are adaptive to operation type and provider evidence.
- First intervention is non-destructive verification.
- Visible levels are:
  ⚡ Verifica anti-stallo — explain what appears stalled and what is being checked.
  ⚡⚡ Ripresa controllata — explain how execution continues without discarding completed work.
  ⚡⚡⚡ Recupero da checkpoint — explain which verified checkpoint/substep is being recovered.
  ⚡⚡⚡⚡ Protezione MotorLab — explain why automatic recovery cannot continue safely.
- Lightning emoji must always be accompanied by an explanation.
- Preserve completed milestones/artifacts/checkpoints whenever possible.
- Read-only diagnostics may run in parallel, but conflicting writers may not.
- Recovery targets the smallest stalled/failed substep and retries are bounded.
- Detailed mandatory behavior is defined by MOTORLAB_WATCHDOG_V1.txt.

CACHE CONTRACT
Every adapter must use safe persistent cache when supported. Android/Gradle routes use official Gradle caching and --build-cache unless documented incompatible. Node/web routes persist package-manager download cache. Cache misses are allowed and repopulate automatically.

ROUTING CONTRACT
- Public repositories: standard GitHub-hosted runners are the normal remote route.
- Private repositories: conserve included allowance; no automatic paid overage.
- Codemagic is REMOVED from MotorLab routing and must not be selected as primary, fallback or emergency provider.
- If the allowed GitHub/local route is unavailable, stop and report the blocker instead of provider-hopping.
- Real project/code failures are diagnosed; do not blindly rerun the same broken build on another provider.

REGRESSION RULE
A feature-specific change is not acceptable if it breaks an unrelated core function. Candidate verification must include adapter-defined core health checks before promotion.

ROLLBACK RULE
If a LAB or CANDIDATA introduces a serious regression, discard it and return to the current MADRE. Do not repair on top of a corrupted experimental lineage unless Bruno explicitly chooses that path.

SINGLE-SOURCE-OF-TRUTH RULE
Br174/Chatgpt is the private MotorLab control/registry repository. This file, UAB_ENGINE_CONTRACT.txt, UAB_GLOBAL_APK_POLICY.txt, UAB_PROJECT_ROUTING.txt, MOTORLAB_WATCHDOG_V1.txt, MOTORLAB_VISUAL_STATUS_V1.txt, MOTORLAB_PROGRESS_REPORTING_V1.txt and MOTORLAB_BACKGROUND_EXECUTION_V1.txt define canonical engine behavior. Project repositories keep only thin adapters/workflows required to execute their mechanics.
