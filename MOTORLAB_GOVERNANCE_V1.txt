MOTORLAB GOVERNANCE V1 - PERMANENT CORE GOVERNANCE + PROJECT ENGINE COEXISTENCE

STATUS
Mandatory MotorLab CORE governance capability.
Established: 2026-09-29.
Repository authority: Br174/Chatgpt.

FOUNDATIONAL PILLAR - CHANGE COMPATIBILITY
MOTORLAB_CHANGE_COMPATIBILITY_GUARD_V1.txt is a permanent foundational pillar for MotorLab and every current/future managed project.
Every write-capable software/control-plane change must perform read-only conflict/overlap/redundancy preflight before mutation.
Equivalent responsibilities must be merged/extended or explicitly superseded; MotorLab must not accumulate competing implementations for the same responsibility.
No speed/automation/project-local rule may bypass this pillar.

PURPOSE
This contract defines permanent governance rules for MotorLab:
1. MotorLab must always coexist with and support project-native engines; it must never replace them merely because MotorLab is active.
2. MotorLab decisions explicitly approved by Bruno in the canonical MotorLab administration chat are permanent CORE decisions by default and must be persisted in the MotorLab control repository, unless Bruno explicitly marks them temporary, experimental, local-only or reversible for a test.
3. MotorLab activation for registered projects must be structural and implicit: recurring per-chat activation strings are fallback compatibility aids, not the normal architecture.
4. Registered project context has mandatory precedence over software-build intent detection; intent discovery is used only when no registered project context is already identifiable.
5. Protection of external APIs/providers/services is a shared MotorLab control-plane responsibility governed by MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt whenever relevant.
6. Faster idea-to-LAB execution is a shared MotorLab capability governed by MOTORLAB_VELOCITY_LAYER_V1.txt and is strictly additive: no existing capability or safety rule may be removed, weakened or bypassed for speed.

1. PROJECT ENGINE COEXISTENCE - MANDATORY
MotorLab is the shared orchestration, lifecycle, build/test, checkpoint, watchdog, routing, progress, release, continuity, external-service-protection and safe-acceleration control-plane.

A project may also contain one or more project-native/domain engines, for example playback/search/AI/runtime engines in MusicLab, geospatial/POI/AI/runtime engines in GeoVision, or equivalent engines in present and future projects.

Those project-native engines remain part of their own project architecture.

MotorLab MUST:
- operate alongside project-native engines;
- coordinate through adapters, hooks, workflows, status probes, checkpoints and compatible interfaces;
- preserve already working project-native behavior;
- treat project-native engines as authoritative for their own domain responsibilities unless Bruno explicitly approves a migration/change;
- add cross-project control capabilities without unnecessarily rewriting project internals;
- protect external-service integrations through reusable cache/rate-limit/queue/backoff/circuit/failover rules instead of encouraging incompatible ad-hoc retry logic in each project;
- reduce redundant analysis, questions, serial read-only work and avoidable build setup through the additive Velocity Layer where safe.

MotorLab MUST NOT, merely because it is activated:
- replace a project-native engine;
- disable a project-native engine;
- rename or absorb a project-native engine into MotorLab;
- duplicate the same domain responsibility with a competing implementation;
- rewrite a functioning project engine to make it conform to MotorLab terminology;
- classify a project-native engine as obsolete/legacy solely because MotorLab exists;
- remove project-specific automation, memory, AI logic, search logic, playback logic, geospatial logic or other domain machinery that already belongs to that project.

Any replacement, consolidation or migration of a project-native engine requires a separate, explicit Bruno approval that identifies the affected project and scope.

2. MEANING OF "ONE ENGINE" IN EXISTING CORE FILES
Any existing MotorLab/UAB wording such as "one engine", "single engine" or "single lifecycle engine" means ONE SHARED MOTORLAB LIFECYCLE/CONTROL-PLANE ENGINE.

It does NOT mean that applications are allowed to have only one software engine, and it does NOT authorize MotorLab to replace project-native/domain engines.

If older wording is ambiguous, this governance contract provides the controlling interpretation.

3. LAYER PRECEDENCE
MotorLab CORE is authoritative for cross-project control concerns including:
- MADRE -> LAB -> CANDIDATA -> NEW MADRE lifecycle;
- promotion identity and release immutability;
- build/test routing and cost policy;
- Watchdog/anti-stall;
- verified progress reporting;
- visual status;
- background execution and single-chat continuity;
- checkpoint/recovery and single-writer safety;
- control-plane state and registry behavior;
- structural auto-bootstrap for registered projects;
- semantic software-build intent activation for new/unregistered chats when supported by the host;
- activation precedence: registered project context first, intent discovery second;
- external-service/API protection through provider-aware caching, deduplication, batching, request budgets, queue/concurrency control, Retry-After, exponential backoff+jitter, circuit breaker, temporary suspension, health checks, authorized failover and diagnostics;
- safe idea-to-LAB acceleration through project snapshots, Change Capsules, question minimization, pre-approval read-only preparation, safe parallel read-only analysis, FAST LAB mechanics, risk-scaled LAB verification, incremental build/cache reuse and delta-scoped inspection.

Project-native engines are authoritative for their project-specific domain behavior unless Bruno explicitly approves otherwise.

When a generic MotorLab mechanism and a project-native domain mechanism overlap, MotorLab must integrate non-destructively and preserve the functioning project behavior. It must not silently override the project engine.

For external services, MotorLab governs protection/scheduling/recovery policy while the project-native engine remains authoritative for domain semantics, search meaning, playback logic, geospatial logic, AI prompt/domain behavior or equivalent application-specific responsibilities.

Core safety/lifecycle rules still apply to how project changes are developed, tested, promoted and delivered; coexistence does not allow a project adapter to bypass MotorLab lifecycle safety.

4. PERMANENT MOTORLAB DECISION RULE - MANDATORY
The canonical MotorLab administration chat is where Bruno designs, changes and administers MotorLab itself.

When Bruno clearly decides or approves that a capability/rule/behavior is to be implemented in MotorLab, the default interpretation is:
- the decision is permanent MotorLab CORE behavior;
- it applies to future MotorLab use where technically relevant;
- it must be persisted in Br174/Chatgpt, not left only in conversational memory;
- future MotorLab activation must obtain the rule from the canonical repository state;
- implementation should preserve backward compatibility and existing working project behavior.

Bruno does NOT need to repeat words such as "permanent", "save this forever" or "put it in the CORE" each time he approves a MotorLab change in the canonical MotorLab chat.

The permanent default does NOT apply when Bruno explicitly says the change is:
- temporary;
- a test/experiment only;
- for this chat/session only;
- for one named operation only;
- a proposal to discuss rather than an approved implementation.

5. PERSISTENCE REQUIREMENT
Conversational memory is not the technical source of truth for permanent MotorLab rules.

For an approved permanent MotorLab change, MotorLab must persist the authoritative result in Br174/Chatgpt using the appropriate canonical contract/module/registry/configuration file when repository write access is available and the change is technically ready.

If repository write access is temporarily unavailable, MotorLab must explicitly report that the decision is approved but not yet technically persisted, rather than falsely claiming permanent implementation.

Once persisted, future sessions must read the repository state before relying on remembered summaries.

6. REVERSALS AND SUPERSEDING DECISIONS
A later explicit Bruno decision may amend or reverse an earlier MotorLab rule.

When that happens:
- update the canonical repository state to the new rule;
- preserve Git history rather than erasing history;
- avoid leaving contradictory active rules;
- make the newer explicit canonical rule authoritative.

7. PROJECT REPOSITORY PROTECTION
A MotorLab governance change does not, by itself, authorize changes to MusicLab, GeoVision, Cover Lab AI, StudyBook, Visionflix or any other project repository.

Project repositories are modified only when the approved MotorLab feature actually requires project-side adapter/integration work and that project-side scope is authorized under the applicable workflow.

MotorLab governance must prefer additive, compatible integration over invasive replacement.

8. STRUCTURAL + INTENT ACTIVATION / AUTO-BOOTSTRAP - MANDATORY
MotorLab activation must not depend on Bruno remembering or pasting an activation prompt in every new chat.

ACTIVATION PRECEDENCE IS MANDATORY:
A. If the current context can be identified as a project registered in canonical MotorLab routing/integration state, MotorLab bootstrap is implicit by project context alone.
B. Only if no registered project context is identifiable may semantic software-build intent be evaluated as an activation path, according to MOTORLAB_INTENT_AUTO_ACTIVATION_V1.txt.

For a registered project, the current user message does not need to express an app/APK/web-app creation intention. A new project chat is already inside MotorLab scope when the project identity/hook is visible.

Before the first write-capable or lifecycle-changing action in a registered project, the execution surface must, when technically able to do so:
- identify the project context;
- inspect the current Br174/Chatgpt canonical state;
- load current CORE contracts and modules, including MOTORLAB_GOVERNANCE_V1.txt and MOTORLAB_AUTO_BOOTSTRAP_V1.txt;
- load MOTORLAB_VELOCITY_LAYER_V1.txt for additive-only acceleration;
- load MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt whenever external API/provider/service behavior is relevant;
- inspect current routing/registry and relevant durable job/checkpoint/lock state;
- activate MotorLab alongside, never in place of, the project's native engines;
- then continue the requested project work.

For an unregistered chat with clear software-construction intent, and only when the host surface exposes the required persistent intent-trigger mechanism:
- load current canonical MotorLab state;
- apply MOTORLAB_INTENT_AUTO_ACTIVATION_V1.txt;
- initialize project definition/onboarding;
- apply MOTORLAB_VELOCITY_LAYER_V1.txt to reduce redundant specification/re-analysis while preserving consequential clarification and approval;
- apply MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt before designing external-provider integrations;
- transition the project to normal structural activation once it is formally registered.

A manual "ATTIVA MOTORLAB" string may exist only as a fallback for a host surface that has lost project context or cannot expose persistent project/global activation configuration. It is not the normal workflow and must not be required for each new project chat.

If the host platform requires a persistent project-level instruction/integration so that all new chats know their MotorLab relationship, that configuration should be installed once for the project/workspace and must reference the canonical Br174/Chatgpt state rather than embedding a frozen copy of the CORE.

If automatic MotorLab discovery is desired in otherwise unrelated future chats, the host may require a minimal persistent global intent trigger. That trigger is infrastructure only: it should detect genuine software-build intent and then consult Br174/Chatgpt; it must not contain a frozen copy of MotorLab CORE.

Detailed mandatory semantics are defined by MOTORLAB_AUTO_BOOTSTRAP_V1.txt and MOTORLAB_INTENT_AUTO_ACTIVATION_V1.txt.

Do not reconstruct MotorLab from conversational memory when the repository is available.

9. EXTERNAL SERVICE GUARD - MANDATORY WHEN RELEVANT
When a current or future MotorLab project materially uses external APIs/providers/services, MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt is the canonical reusable protection contract.

MotorLab must prefer prevention over recovery by reducing unnecessary provider calls before limits are reached. Where technically and legally applicable this includes:
- provider-aware cache/service shield and controlled cache warming;
- request deduplication/coalescing;
- efficient official batching/pagination;
- documented/conservative rate limiting and shared request budgets;
- bounded queues and concurrency;
- Retry-After compliance;
- exponential backoff with jitter;
- circuit breaker and temporary provider/credential suspension;
- low-cost health checks and gradual recovery;
- sequential, authorized failover rather than continuous credential rotation;
- graceful degradation using acceptable cached data/fallback sources;
- diagnostics without exposing secrets.

Multiple credentials must not be used to evade a provider's intended quota/rate-limit policy. Failover across credentials/providers must remain authorized, quota-scope aware and compatible with provider terms.

This governance rule does not automatically modify existing project repositories. Existing provider-specific implementations are aligned incrementally when that project is being changed, preserving working domain behavior.

10. VELOCITY LAYER - ADDITIVE ONLY, MANDATORY
MOTORLAB_VELOCITY_LAYER_V1.txt is the canonical acceleration contract for current and future MotorLab projects.

Its purpose is to shorten the path from idea/change request to a first useful verified LAB result by reducing avoidable serial work, not by weakening verification.

MotorLab may use, where safe:
- project snapshots tied to authoritative source identity;
- Change Capsules that preserve goal/scope/protected areas/acceptance criteria;
- fewer redundant questions when answers can be safely derived;
- pre-approval read-only preparation;
- parallel independent read-only analysis;
- FAST LAB mechanics for eligible atomic changes;
- risk-scaled FIRST-LAB verification;
- persistent/incremental build readiness and cache reuse;
- delta-scoped inspection with automatic expansion when blast radius requires it;
- precomputed component-to-regression maps;
- reuse of already verified analysis instead of restarting from zero after approval or executor handoff.

ABSOLUTE PRECEDENCE RULE
Velocity Layer may NEVER remove, weaken or bypass an existing MotorLab capability. If a speed optimization conflicts with lifecycle, approval, Watchdog, checkpoint, single-writer, progress truthfulness, regression gates, Background Execution safety, External Service Guard, cost policy, signing/package identity, protected project behavior or another canonical rule, the existing rule wins and the optimization is reduced/disabled.

FAST LAB is not a new lifecycle state and cannot promote directly to CANDIDATA or MADRE. Candidate reconstruction, full adapter-defined regression gates and explicit promotion approval remain unchanged.

This governance rule does not automatically rewrite project repositories. Project-specific acceleration mechanics are introduced through adapters and normal authorized project workflows.

11. NO FALSE GUARANTEE
"Permanent" means the rule is part of the canonical MotorLab design/control repository and remains operative until explicitly superseded.
It does not mean MotorLab can bypass platform limitations, unavailable tools, permissions, quotas or external service failures.
When a permanent rule cannot be executed because of an external limitation, preserve the rule and report the operational blocker instead of silently abandoning or replacing it.

Automatic structural bootstrap cannot physically occur on a completely context-free host surface that provides neither project identity nor persistent project instructions/integration nor repository access.
Automatic intent bootstrap across unrelated chats likewise cannot physically occur unless the host exposes a persistent global intent trigger or another supported mechanism that causes MotorLab activation policy to be consulted.

External Service Guard also cannot manufacture quota or bypass a provider-enforced restriction. Its role is to conserve authorized capacity, avoid avoidable blocks, degrade gracefully and recover safely.
Velocity Layer cannot manufacture speed when an external build/provider/tool is inherently slow; it may reduce avoidable work, overlap safe preparation and reuse valid state, but must report real blockers honestly.

In such exceptional cases MotorLab must report the missing structural/intent/service/execution capability instead of pretending that a per-chat prompt, uncontrolled retry or unsafe shortcut is the architecture.

12. SUCCESS CRITERIA
This governance contract is active when:
- MotorLab consistently operates alongside project-native engines rather than replacing them;
- existing "one engine" wording is interpreted as one lifecycle/control-plane engine only;
- approved MotorLab changes in the canonical MotorLab chat are permanent by default;
- those changes are persisted in Br174/Chatgpt rather than trusted only to chat memory;
- registered project contexts bootstrap MotorLab implicitly without recurring user activation strings and without requiring build intent in the current message when the host exposes the required structural context;
- unregistered future chats with genuine software-build intent can enter MotorLab onboarding when the host exposes the required intent-trigger mechanism;
- project context always takes precedence over intent gating;
- external-service integrations inherit the reusable Service Guard when relevant instead of relying on uncontrolled retries or repeated duplicate provider calls;
- Velocity Layer reduces avoidable idea-to-LAB latency while every pre-existing MotorLab capability remains active;
- manual activation prompts are fallback only;
- project repositories are not modified merely because a MotorLab governance rule changed;
- later explicit Bruno decisions can supersede earlier rules through normal versioned repository updates.
