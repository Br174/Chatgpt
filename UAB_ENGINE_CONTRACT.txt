UAB ENGINE CONTRACT - UNIFIED CORE

COMPATIBILITY NOTE
Official engine name: MotorLab. Legacy UAB filenames and adapter keys remain valid during migration.

Purpose
This file defines mandatory engine-level behavior for every Bruno project handled through MotorLab/UAB. It applies to Android, hybrid Android, web/PWA and delivery projects. Project-specific workflows are adapters, not independent engines.

A. SINGLE ENGINE LIFECYCLE - MANDATORY
1. Canonical lifecycle: MADRE -> LAB -> CANDIDATA -> NEW MADRE.
2. The current MADRE is the last user-approved stable state and is immutable.
3. Every LAB starts directly from the current MADRE unless Bruno explicitly requests continuation of an existing LAB.
4. A failed/corrupted LAB is discarded; do not make a new LAB from that failed lineage by default.
5. A CANDIDATA is rebuilt cleanly from the current MADRE with only the changes proven useful in LAB.
6. A CANDIDATA becomes a NEW MADRE only after regression checks and explicit user approval.
7. Historical MADRI remain preserved as rollback points.
8. Project adapters may customize mechanics but may not override these lifecycle rules.
9. UAB_UNIFIED_ENGINE_V1.txt is the canonical lifecycle/state-machine definition.
10. UAB_ADAPTER_SPEC_V1.txt is the canonical adapter schema.

B. RELEASE IMMUTABILITY - MANDATORY
1. GitHub permanent Releases are a deposit of approved good versions (MADRI), not a scratch area for experiments.
2. LAB and CANDIDATA binaries are temporary test artifacts until promotion is approved.
3. An immutable MADRE tag/asset must never be replaced with --clobber, overwrite_files=true or equivalent.
4. A 'latest' mechanism may exist only as a pointer to the newest immutable MADRE; it must not be the sole storage location and must not erase history.
5. Downloader-style URLs may rely on GitHub's latest-release pointer only when every underlying release is uniquely tagged and preserved.

C. PERSISTENT CACHE - MANDATORY
1. First-run principle: the first clean build may be slow because dependencies, tools and build outputs must be downloaded/generated.
2. Subsequent-run principle: every supported workflow must reuse safe persistent caches whenever the provider supports them.
3. Android/Gradle projects:
   - Use the official Gradle setup/cache action on GitHub Actions.
   - Invoke Gradle with --build-cache unless a project adapter explicitly documents an incompatibility.
   - Use configuration cache and parallel execution when project-compatible; configuration-cache persistence outside the runner must be encrypted when it may contain credentials/secrets.
   - Preserve dependency/tool caches across runs; do not delete provider caches merely to obtain a clean build.
   - Prefer stable same-family build/job/cache identity where feasible so successive LAB revisions can reuse valid state.
   - Measure FROM-CACHE / UP-TO-DATE / executed-task counts and wall time; do not assume cache benefit.
   - Do not cache secrets, signing passwords, plaintext keystores or user-sensitive data.
   - 'clean' may be used when required by a project, but it must not disable the persistent Gradle build cache.
4. Node/web projects:
   - Cache the package manager download cache (npm/pnpm/yarn as appropriate) using a key derived from dependency state.
   - Never cache secrets or deployment credentials.
5. Auxiliary tools:
   - Cache repeatable tool downloads such as protoc, pip wheels or equivalent when safe and useful.
6. Cache fallback:
   - A cache miss must never make the build fail. It only means that run behaves like a first run and repopulates the cache.
7. Cache invalidation:
   - Keys must change when relevant dependency/toolchain inputs change. Do not deliberately reuse incompatible cache state.
8. No false speed promises:
   - A warm-cache build should normally be faster, but source changes, invalidation, provider eviction or non-cacheable tasks can still require full work.

D. VISIBLE PROGRESS PERCENTAGE - MANDATORY
1. Every substantial modification/build task must expose a current completion percentage to Bruno throughout work, not only at major milestones.
2. Percentage is based on completed verified milestones/micro-milestones, not elapsed clock time and not an invented ETA.
3. Default broad scale:
   5% request accepted / scope locked
   15% current MADRE identified and protected
   30% requested LAB/config changes applied
   45% static/source checks completed
   60% preflight completed and cache/toolchain ready
   75% build/test output completed
   85% artifact + regression verification completed
   95% candidate/handoff or promotion package ready
   100% requested state verified and delivered
4. Large phases may be divided into real deterministic micro-milestones so intermediate values can be reported when justified by actual completed work.
5. Non-build work: remove non-applicable phases and proportionally recalculate progress across the real work plan.
6. Failure behavior: keep the last verified percentage, identify the failing phase, and never show 100% until the requested outcome is verified.
7. Interactive reporting frequency:
   - report at task start, meaningful subtask start/completion, phase changes, important file/change application, check transitions, build/test transitions, artifact/checkpoint changes, watchdog interventions, recovery outcomes, handoff/promotion transitions and final delivery;
   - as a practical default, avoid more than roughly 1-3 meaningful tool/operation interactions without a progress update when the interface permits;
   - for a long single operation, report status as provider/job evidence changes;
   - do not spam clock-based identical messages with no new information.
8. Same-percentage updates are explicitly allowed and encouraged when new operational information exists but no new completion has been verified.
9. CI/log reporting should emit machine-readable progress markers plus a short phase description when supported.
10. Cross-project rule: percentage applies to all MotorLab projects and future projects.
11. Watchdog messages should include current last verified percentage when visible.
12. Fireworks success messages should include current percentage when useful, but fireworks alone do not advance progress.
13. Detailed semantics are mandatory in MOTORLAB_PROGRESS_REPORTING_V1.txt.

E. REGRESSION GATES - MANDATORY
1. Each project adapter must define critical unrelated functions that must remain healthy before a CANDIDATA can become MADRE.
2. A feature-specific success is insufficient if it breaks another core function.
3. Serious regression means the experimental lineage is rejected and the current MADRE remains authoritative.

F. ONBOARDING REQUIREMENT
Any new project added to MotorLab must declare:
- project class and current MADRE reference;
- LAB/CANDIDATA/MADRE naming/prefixes;
- cache technology and invalidation inputs;
- progress milestone mapping;
- build/test route;
- regression gates;
- release/delivery mode;
- package/signing strategy when Android is involved;
- watchdog class/status probe/progress signal/checkpoint/lock/recovery fields where supported;
- background executor/start/status/resume/cancel/checkpoint/lock/notification fields where supported.
A project is not fully onboarded until these are defined.

G. PRIORITY
This contract is mandatory alongside UAB_UNIFIED_ENGINE_V1.txt, UAB_ADAPTER_SPEC_V1.txt, UAB_GLOBAL_APK_POLICY.txt, UAB_PROJECT_ROUTING.txt, MOTORLAB_WATCHDOG_V1.txt, MOTORLAB_VISUAL_STATUS_V1.txt, MOTORLAB_PROGRESS_REPORTING_V1.txt, MOTORLAB_BACKGROUND_EXECUTION_V1.txt and MOTORLAB_BUILD_FAST_LANE_V1.txt. If an older project workflow conflicts, the older workflow is legacy and must not be treated as the authoritative promotion path until aligned.

H. MOTORLAB WATCHDOG / ANTI-STALL - MANDATORY
1. Every substantial controllable operation must expose heartbeat and material-progress state when technically available.
2. MotorLab must distinguish elapsed time from real lack of progress; repeated identical polling is not progress.
3. The watchdog uses adaptive thresholds appropriate to the operation class and should verify provider/tool state before recovery.
4. First response to suspected stall is non-destructive observation, never blind cancellation.
5. Every watchdog intervention visible to Bruno must include lightning emoji plus explanation of the stalled phase and the action being taken.
6. Escalation levels are: ⚡ verify; ⚡⚡ safe continuation; ⚡⚡⚡ checkpoint recovery of only the stalled substep; ⚡⚡⚡⚡ safe stop when recovery cannot be proven safe.
7. Completed work, verified artifacts and milestone percentage must be preserved across recovery whenever technically possible.
8. Write-capable work must use a single-writer lock scope. The watchdog may run read-only diagnostics in parallel but may not start a conflicting second writer.
9. Retries are bounded and targeted. Deterministic code/configuration failures go to diagnosis instead of blind repetition or provider hopping.
10. Recovery resumes from the latest verified checkpoint rather than reinterpreting the entire task from scratch.
11. A watchdog event alone does not increase progress percentage; only real verified progress does.
12. Detailed semantics are mandatory in MOTORLAB_WATCHDOG_V1.txt.

I. MOTORLAB VISUAL SUCCESS STATUS - MANDATORY
1. Every meaningful verified success during MotorLab-controlled programming, fixing, building, testing, recovery or delivery must be surfaced visually to Bruno with fireworks plus a plain-language explanation.
2. Fireworks levels are: 🎆🎆 small verified success; 🎆🎆🎆 significant milestone; 🎆🎆🎆🎆 major/final verified completion.
3. Fireworks must never appear alone and must explain what succeeded and, where relevant, how it was verified.
4. Do not show fireworks for work that merely started, is still pending, is assumed successful or remains unverified where verification is possible.
5. Emit fireworks for each meaningful small resolved item as well as larger milestones without duplicating the same success.
6. Fireworks complement progress percentages; they do not themselves increase progress.
7. Watchdog lightning and success fireworks remain semantically distinct.
8. This is a global MotorLab reporting rule. Project adapters may add detail but may not disable it.
9. Detailed semantics are mandatory in MOTORLAB_VISUAL_STATUS_V1.txt.

J. MOTORLAB BACKGROUND EXECUTION + SINGLE-CHAT CONTINUITY - MANDATORY
1. The project chat where Bruno initiates/continues a task is the canonical user-facing thread when a usable chat reference is available.
2. MotorLab must not require Bruno to migrate manually among normal Chat, Work, MotorLab or other executor conversations merely because the execution backend changes.
3. Long background-capable work must be classified and handed proactively to a durable executor before depending on a long foreground chat turn. Do not wait for app exit detection.
4. A normal chat/model turn alone is not persistent background execution and must not be described as such.
5. A durable executor may be GitHub Actions, persistent worker/service, runner, Work/cloud when suitable, or another adapter-approved executor whose lifetime is independent of the visible chat screen.
6. Once safely handed off, background work continues autonomously through pre-approved steps while Bruno is away and continuously preserves checkpoints/progress/locks.
7. Checkpoints are a safety mechanism, not the default stop behavior. The normal model is CONTINUE + SAVE CHECKPOINTS.
8. Durable job state must preserve operation id, project, canonical chat ref when available, executor/job id, repository/ref/SHA, scope, phase, verified percentage, heartbeat/progress timestamps, checkpoint, next step, lock, retry state and artifacts/checksums when available.
9. Canonical job states are QUEUED, RUNNING, WAITING_EXTERNAL, WAITING_USER, RECOVERING, COMPLETED, FAILED_SAFE and CANCELLED_BY_USER.
10. Returning to the same project chat must first reconcile durable job state before launching new work on the same scope.
11. Reopening the chat must never start a duplicate writer when the background job is still active on the same lock scope.
12. If an executor quota/availability ends, preserve completed work and checkpoint; switch to another adapter-approved executor when safe and authorized; otherwise stop safely with the real blocker. Never silently incur paid usage.
13. Work is an optional execution capability, not the required user-facing conversation. MotorLab should not force Bruno into a second Work chat merely to preserve continuity.
14. When the canonical chat becomes available again, report what progressed while Bruno was away using current verified percentage and fireworks/watchdog language as applicable.
15. Notifications may be used when supported for completion or WAITING_USER, but they do not become the authoritative conversation.
16. MotorLab cannot force a suspended ordinary ChatGPT foreground turn to continue computing; therefore the background guarantee applies only after handoff to a real durable executor.
17. MotorLab should proactively avoid leaving long backgroundable phases solely inside normal-chat execution.
18. Detailed semantics are mandatory in MOTORLAB_BACKGROUND_EXECUTION_V1.txt.

K. BUILD FAST LANE + SAFETY SOURCE CHECKPOINT - MANDATORY
1. MOTORLAB_BUILD_FAST_LANE_V1.txt governs Android/UAB build acceleration.
2. A verified LAB aggiornamento normally performs ONE update-family Gradle build.
3. The paired LAB di sicurezza is preserved as an immutable GitHub SOURCE checkpoint plus materialization recipe; its APK is built only on demand by default.
4. Requested update artifact delivery becomes eligible as soon as source/package/version/signing checks pass and the artifact is retrievable; unrelated/deferred work must not delay delivery.
5. Historical eager safety APKs remain valid.
6. Build acceleration may not weaken package identity, signing, update-in-place, source lineage or verification.
