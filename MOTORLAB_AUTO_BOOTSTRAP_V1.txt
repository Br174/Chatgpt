MOTORLAB AUTO BOOTSTRAP V1 - STRUCTURAL PROJECT + INTENT ACTIVATION

STATUS
Mandatory MotorLab CORE capability.
Established: 2026-09-29.
Repository authority: Br174/Chatgpt.

PURPOSE
MotorLab activation must be structural, not dependent on Bruno remembering or pasting an activation prompt in every new chat.

MotorLab supports two activation paths:
1. structural activation for already registered projects;
2. semantic software-build intent activation for new/unregistered chats when the host surface can expose the intent trigger.

CORE PRINCIPLE
REGISTERED PROJECT CONTEXT HAS PRIORITY OVER INTENT DETECTION.

When the current work context can be identified as a project registered in UAB_PROJECT_ROUTING.txt, MOTORLAB_PROJECT_INTEGRATION_REGISTRY_V1.txt or a later canonical MotorLab routing/integration registry, MotorLab activation is IMPLICIT and immediate. The current user message does NOT need to express software-build intent.

Only when no registered project context is identifiable may the software-build intent path be used, according to MOTORLAB_INTENT_AUTO_ACTIVATION_V1.txt.

Bruno must not be required to write "ATTIVA MOTORLAB" or paste any bootstrap string for every new chat.

1. ACTIVATION PRECEDENCE - MANDATORY
Before evaluating message intent, check whether the execution surface exposes a registered MotorLab project context.

A. If REGISTERED PROJECT CONTEXT is identifiable:
- activate MotorLab implicitly;
- do not require keywords or an explicit app/APK/web-app creation request in the current message;
- do not gate activation on semantic intent;
- continue with structural bootstrap.

B. If NO REGISTERED PROJECT CONTEXT is identifiable:
- evaluate software-build intent only if the host surface exposes the persistent intent-trigger policy;
- if clear build intent exists, activate MotorLab and begin new-project onboarding under MOTORLAB_INTENT_AUTO_ACTIVATION_V1.txt;
- otherwise leave MotorLab inactive unless explicitly invoked later.

2. IMPLICIT REGISTERED-PROJECT ACTIVATION - MANDATORY
Before the first write-capable or lifecycle-changing operation in a registered project context, MotorLab must:
- identify the current project/repository when technically available;
- detect MOTORLAB_PROJECT_HOOK.txt when project repository access exposes it;
- read the current canonical MotorLab state from Br174/Chatgpt;
- load the current CORE contracts, governance, routing and integration registry required for that project;
- load MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt whenever the project uses or may modify external APIs/providers/services;
- reconcile current lifecycle/job/checkpoint/lock state where applicable;
- apply MotorLab rules alongside the project's own native engines;
- only then perform the requested project change.

This bootstrap is automatic and does not require a user activation phrase or a build-intent statement.

3. INTENT-BASED NEW-PROJECT ACTIVATION
When no registered project context is identifiable but the user clearly intends to create, develop, modify, package or deliver an application/APK/web app or equivalent software project, MotorLab may activate through MOTORLAB_INTENT_AUTO_ACTIVATION_V1.txt.

Intent activation is an onboarding path, not a replacement for structural registration.

Once the new project is formally registered and receives its project-side hook when applicable, future identifiable project chats must use structural activation and must no longer depend on recurring intent detection.

4. PROJECT-NATIVE ENGINE COEXISTENCE
Auto-bootstrap activates MotorLab as orchestration/control-plane only.
It MUST NOT replace, disable, absorb, rename or rewrite a project-native/domain engine merely because MotorLab has loaded.
MOTORLAB_GOVERNANCE_V1.txt remains authoritative for coexistence.

5. CHAT CONTINUITY
A new chat inside a registered project should treat MotorLab bootstrap as part of project initialization, not as a separate user task.
The current project chat remains the canonical user-facing chat.

A first message such as "continuiamo", a diagnostic question, a short administrative request or any other message without explicit software-build intent does not prevent activation when the project context itself is recognized.

6. BOOTSTRAP ORDER
Minimum safe order for a registered project:
A. identify project context;
B. detect project-side MOTORLAB_PROJECT_HOOK.txt when available;
C. inspect Br174/Chatgpt canonical state;
D. load current MotorLab CORE/governance modules, including MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt when external services are relevant and MOTORLAB_INTENT_AUTO_ACTIVATION_V1.txt when relevant;
E. inspect UAB_PROJECT_ROUTING.txt, UAB_STATE_REGISTRY.txt and MOTORLAB_PROJECT_INTEGRATION_REGISTRY_V1.txt or their canonical successors;
F. reconcile active durable job/checkpoint/lock state when relevant;
G. proceed with the user's requested work.

Minimum safe order for an unregistered chat with clear build intent:
A. confirm no registered project context is already available;
B. detect semantic software-build intent under MOTORLAB_INTENT_AUTO_ACTIVATION_V1.txt;
C. inspect Br174/Chatgpt canonical state;
D. load current MotorLab CORE/governance modules, including MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt before designing external-service integrations;
E. initialize new-project definition/onboarding;
F. register routing/hook only when the project becomes concrete and the applicable workflow permits it;
G. continue under normal MotorLab lifecycle rules.

7. PROJECT-SIDE STRUCTURAL HOOK
For repositories formally onboarded to MotorLab, MOTORLAB_PROJECT_HOOK.txt is the standard persistent project-side declaration when repository integration is applicable.
The hook must:
- point to Br174/Chatgpt as canonical MotorLab authority;
- declare implicit activation;
- declare coexistence/preservation of project-native engines;
- contain orchestration metadata only, not a frozen copy of MotorLab CORE;
- avoid changing application logic by its mere presence.

Current installed hook state is tracked by MOTORLAB_PROJECT_INTEGRATION_REGISTRY_V1.txt.

8. NO MEMORY-ONLY BOOTSTRAP
Saved conversational memory, prior summaries or a copied activation prompt may help identify context, but they are not authoritative MotorLab state.
When repository access is available, Br174/Chatgpt must be consulted before relying on remembered MotorLab rules for write-capable work.

9. NO PER-CHAT ESCAMOTAGE
Manual activation strings are compatibility/fallback aids only.
They are not part of the normal MotorLab architecture and must not be presented as a recurring requirement.

10. PLATFORM BOUNDARY
MotorLab can enforce auto-bootstrap only on execution surfaces that expose enough information to discover one of the supported activation paths.

For registered projects this means enough project/repository/workspace identity or persistent project configuration to recognize the project/hook.

For unregistered future chats this means a persistent global intent-trigger capability, or another host mechanism that causes MOTORLAB_INTENT_AUTO_ACTIVATION_V1.txt to be consulted when software-build intent is expressed.

If the host platform opens a completely context-free chat with no project identity, no project hook visibility, no MotorLab project instructions, no global MotorLab intent trigger and no repository access, MotorLab cannot physically self-start from information the host did not provide.
In that case:
- do not pretend automatic activation occurred;
- prefer a one-time persistent host/project/workspace integration over repeated per-chat prompts;
- once project identity, project hook access or global intent-trigger support becomes available, return to implicit activation.

11. ONE-TIME PROJECT INTEGRATION, WHEN REQUIRED BY HOST
If a host product requires persistent project instructions/configuration to expose MotorLab to every new chat inside a project, that configuration is infrastructure, not a recurring activation step.
It should be installed once per project/workspace and should point to the project-side MOTORLAB_PROJECT_HOOK.txt and/or Br174/Chatgpt canonical state rather than embedding a frozen copy of the CORE.

If automatic intent activation is desired across otherwise unrelated future chats, the equivalent host-level mechanism should be a minimal persistent global trigger that detects genuine software-build intent and then consults the canonical MotorLab state; it must not duplicate the CORE.

12. REGISTERED PROJECTS
Projects listed in current canonical routing/integration registry are MotorLab-managed unless Bruno explicitly removes/suspends them.
Current examples include MusicLab, GeoVision, StudyBook-AI, Visionflix/Verlezza Vision delivery path, Cover Lab AI and future projects added to routing.

Registered project status is sufficient for activation when the chat context is identifiable. Intent detection is unnecessary in that case.

13. NEW PROJECT ONBOARDING
When a new project is discovered through software-build intent and later formally added to MotorLab routing:
- implicit structural bootstrap becomes part of its onboarding contract;
- install MOTORLAB_PROJECT_HOOK.txt when repository-side integration is applicable;
- register the hook in the canonical integration registry;
- preserve project-native engines;
- apply MOTORLAB_EXTERNAL_SERVICE_GUARD_V1.txt to any external API/provider integration instead of inventing an incompatible per-project protection scheme;
- do not require a recurring user activation command or recurring build-intent statement.

14. FAILURE MODE
If bootstrap cannot complete because Br174/Chatgpt is unavailable, permissions are missing, project identity/hook visibility is ambiguous, or the host lacks the global intent trigger required for an unrelated chat:
- do not make a risky write based on guessed CORE state;
- report the exact blocker;
- preserve the project-native engine and current project state;
- use WAITING_EXTERNAL or WAITING_USER only when genuinely necessary.

15. SUCCESS CRITERIA
Auto-bootstrap is considered active when:
- registered project chats activate MotorLab by context alone and do not require build intent in the current message;
- registered project chats do not require Bruno to paste an activation string each time;
- project-side persistent hooks exist where repository integration is applicable;
- unregistered chats with clear software-build intent can enter MotorLab onboarding when the host exposes the intent trigger;
- ordinary discussion about apps does not activate MotorLab by intent alone;
- current MotorLab CORE is loaded before write-capable work;
- External Service Guard is loaded automatically whenever external provider/API design or modification is relevant;
- routing/integration registry/state is reconciled when relevant;
- project-native engines remain intact and authoritative for their domain logic;
- manual activation strings are fallback only;
- platform limitations are stated honestly rather than hidden.
