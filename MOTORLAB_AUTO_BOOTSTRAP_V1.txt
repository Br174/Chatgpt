MOTORLAB AUTO BOOTSTRAP V1 - STRUCTURAL PROJECT + INTENT ACTIVATION

STATUS
Mandatory MotorLab CORE capability.
Established: 2026-09-29.
Repository authority: Br174/Chatgpt.

PURPOSE
MotorLab activation must be structural, persistent and FIRST in software-project sessions. It must not depend on Bruno remembering or pasting an activation prompt in every new chat.

MANDATORY DEPENDENCIES
- MOTORLAB_BOOT_CAPSULE_V1.txt
- MOTORLAB_GLOBAL_PERSISTENT_ACTIVATION_V1.txt
- MOTORLAB_SESSION_BOOT_BANNER_V1.txt
- MOTORLAB_PROJECT_CONTINUITY_V1.txt
- MOTORLAB_RESUME_RECOVERY_V1.txt
- MOTORLAB_FOREGROUND_STALL_GUARD_V1.txt
- MOTORLAB_POLLICINO_CONTINUITY_V1.txt
- MOTORLAB_PROGRESS_REPORTING_V1.txt
- MOTORLAB_ROOT_CAUSE_CLOSURE_V1.txt
- MOTORLAB_CHANGE_COMPATIBILITY_GUARD_V1.txt
- current required CORE modules from MOTORLAB_RELEASE_MANIFEST_V1.txt

MotorLab supports mandatory activation for every recognizable current/future project, plus semantic software-build intent activation outside a recognized project. Unregistered projects are auto-onboarded; registration is never a prerequisite for first activation.

CORE PRINCIPLE
REGISTERED PROJECT CONTEXT HAS PRIORITY OVER INTENT DETECTION.
Bruno must not be required to write "ATTIVA MOTORLAB" or paste any bootstrap/transfer string for every new chat.

0. PRE-RESPONSE MOTORLAB GATE - MANDATORY
Before the first substantive assistant answer, project tool call, code modification, repository write, build/test/lifecycle action or technical plan in a software-project conversation:
A. determine whether any current/future project context is identifiable;
B. if yes, MotorLab activation MUST occur immediately whether or not that project has already been registered;
C. otherwise determine whether genuine software-build intent is clear;
D. if either activation path applies, MotorLab activation MUST occur before the substantive project response/work;
E. the first user-visible line must be the versioned activation proof required by MOTORLAB_SESSION_BOOT_BANNER_V1.txt and MUST match the pinned session release;
E. only then continue bootstrap/reconciliation and the requested work.

This gate is not optional because the user message is short, administrative, says only "continua", arrives in a new chat, or does not contain the word MotorLab.
Do not wait for a later write step to activate if software-project context is already available at the start.

1. ACTIVATION PRECEDENCE - MANDATORY
A. REGISTERED PROJECT CONTEXT identifiable:
- activate MotorLab implicitly and immediately;
- do not require keywords, a build-intent restatement or activation prompt;
- load local verified satellite/hook where available;
- load central current CORE at the first safe boundary;
- load Project Continuity before choosing a project starting point.

B. NO registered project context identifiable:
- evaluate genuine software-build intent;
- if clear, activate MotorLab implicitly and start new-project onboarding;
- otherwise remain inactive until a valid activation path exists.

2. IMPLICIT REGISTERED-PROJECT ACTIVATION - MANDATORY
For a registered project, bootstrap must:
- identify project/repository when technically available;
- detect/read MOTORLAB_PROJECT_HOOK.txt when available;
- activate from verified local satellite immediately when valid;
- consult Br174/Chatgpt canonical MotorLab state;
- load Global Persistent Activation, Project Continuity, Resume Recovery, Foreground Stall Guard, Pollicino Continuity, Progress Reporting and Root Cause Closure;
- load current governance/routing/Velocity/External Service Guard modules as relevant;
- reconcile project continuity ledger with live repository/ref/job/artifact state;
- classify newer live events before treating them as application lifecycle changes;
- restore project-native/domain engine coexistence;
- reconcile lifecycle/checkpoint/pending-action/lock/progress-floor state;
- if unfinished prior work exists, route it through Watchdog/Resume Recovery before unrelated write-capable work;
- if an unexpected stale ledger/missed write-through is found, route the causal defect through Root Cause Closure;
- proceed only after the project starting state is coherent.

3. INTENT-BASED NEW-PROJECT ACTIVATION
When no registered project context is identifiable but the user clearly intends active software construction/development/maintenance, MotorLab is implicitly requested.
Once the project becomes concrete, onboarding must install project hook + local satellite, register routing/integration, and create its central Project Continuity ledger.
Future chats then use structural activation rather than repeated intent detection.

4. PROJECT-NATIVE ENGINE COEXISTENCE
MotorLab is orchestration/control-plane only.
It MUST NOT replace, disable, absorb, rename or rewrite a project-native/domain engine merely because MotorLab has loaded.
Project Continuity restores the native-engine relationship on new-chat boot.

5. CROSS-CHAT CONTINUITY - MANDATORY
A new chat inside a registered/recognized project is a continuation-capable project session, not a blank project state.
It must NOT require Bruno to paste a handoff prompt.

At boot:
A. load the project hook;
B. load the project-specific central continuity ledger referenced by hook/registry;
C. inspect current live repository/ref/head and relevant provider/job/artifact state;
D. classify newer live events as application work, MotorLab control-plane activity, external automation or unknown-before-reconcile;
E. let newer coherent live evidence supersede stale ledger/history without inventing a new app lifecycle operation from control-plane-only activity;
F. load an already-prepared Pollicino RESUME_READY packet first when available; use it to reconstruct ACTIVE_OPERATION_ID, phase, verified progress floor, completed step, pending verification and next safe step;
F1. perform only the smallest live authority/lock freshness check needed before writes; do not begin a broad reconstruction when the prepared packet remains coherent;
G. if prior work is unfinished, invoke Resume Recovery/Watchdog and continue the same logical operation;
H. if expected write-through was missed, invoke Root Cause Closure rather than merely refreshing the file;
I. do not restart from an older copied prompt, older UAB registry, or memory summary when newer evidence exists.

A chat-id change alone never creates a new operation.

5A. FIRST VISIBLE PROGRESS GATE - MANDATORY
Immediately after activation/reconciliation, if a substantial operation is active, pending, newly accepted or visible from live provider/repository evidence:
- establish or reconstruct the evidence-based progress scale;
- emit a user-visible status containing `Progresso MotorLab: <N>%` before entering a long opaque sequence of tool/build/provider work;
- for already-running jobs, derive the current verified band from completed steps/milestones rather than restarting at 5%;
- repeat the same N% on later material state transitions when no new verified milestone exists.

The banner alone is NOT sufficient visibility for an active substantial operation.
If no active quantified operation exists, activation-only output may omit percentage.

6. WRITE-THROUGH CONTINUITY
During substantial work, Project Continuity must be refreshed at continuation-relevant material transitions and before valid terminal turn states when a safe central write surface is available.
A missed expected write-through is itself a Root Cause Closure problem; manual realignment alone is not definitive closure.

7. FOREGROUND STALL PREVENTION - MANDATORY
Before substantial execution classify FOREGROUND_SHORT / FOREGROUND_RISK / BACKGROUNDABLE / USER_BLOCKING.
For FOREGROUND_RISK/BACKGROUNDABLE:
- establish recoverable checkpoint and exact next-safe-step first;
- emit the current numeric progress before entering the long phase when a quantified operation exists;
- prefer a real approved persistent executor for safe backgroundable work;
- otherwise split work into bounded recoverable segments;
- never treat ChatGPT UI processing indicators as MotorLab heartbeat/progress;
- when the next phase is long and an observable persistent executor exists, enroll it in Pollicino liveness/progress monitoring before entering the opaque phase;
- for Codex-hook-capable satellites, sync the external `.codex/hooks/motorlab_pollicino.py` adapter plus SessionStart/UserPromptSubmit/PostToolUse/Stop/Interrupt/SessionEnd hooks at a safe boundary; require provider-native secret provisioning before claiming enrollment;
- when no supported external liveness channel exists, do not invent one: use bounded recoverable segments/checkpoints instead;
- recover at the first later execution cycle under Resume Recovery if host execution is interrupted.

8. REGISTERED-PROJECT BOOT ORDER - MANDATORY
A. recognize project context;
B. activate MotorLab immediately;
C. emit the exact versioned startup banner `⚙️ MotorLab rNN attivo` as the first user-facing line, where rNN comes from the pinned session release;
D. read project hook + verified local satellite/sync state;
E. inspect current central release/entrypoint safely;
F. load Global Persistent Activation + Project Continuity + Resume Recovery + Foreground Stall Guard + Progress Reporting + Root Cause Closure + required CORE;
G. read project continuity ledger;
H. reconcile ledger against live repository/ref/head/provider/job/artifact evidence and classify event source;
I. reconcile lifecycle/checkpoint/lock/pending action/monotonic progress floor;
J. restore project-native engine coexistence;
K. emit the first numeric progress status when a substantial operation is active/pending;
L. if unfinished work exists, Resume Recovery continues it before unrelated writes;
M. if stale-state/write-through failure is detected, Root Cause Closure owns causal closure;
N. apply the foundational Change Compatibility Guard during read-only preflight and resolve redundancy/overlap/conflict before writes;
O. classify substantial execution under Foreground Stall Guard;
P. proceed with the requested work.

9. NEW-PROJECT BOOT ORDER
A. confirm no registered context is available;
B. detect genuine software-build intent;
C. activate MotorLab and emit exact versioned banner `⚙️ MotorLab rNN attivo` first;
D. inspect current central CORE;
E. load mandatory CORE modules including Project Continuity, Progress Reporting and Root Cause Closure;
F. initialize project identity/onboarding;
G. once scope is locked, establish and display the first evidence-based numeric percentage;
H. once concrete, create project hook, satellite, registry entry and project continuity ledger;
I. proceed under normal MotorLab safety/lifecycle rules.

10. PROJECT-SIDE STRUCTURAL HOOK
For formally onboarded repositories, MOTORLAB_PROJECT_HOOK.txt must:
- point to Br174/Chatgpt as canonical MotorLab authority;
- declare implicit activation and mandatory pre-response boot gate;
- point to the project-specific Project Continuity ledger;
- declare coexistence/preservation of native engines;
- bind Global Persistent Activation, Session Boot Banner, Project Continuity and Resume Recovery;
- resolve current entrypoint/release;
- contain control-plane metadata only.

11. NO MEMORY-ONLY BOOTSTRAP
Conversational memory, prior summaries and copied prompts are auxiliary only.
When repository/continuity state is available, current canonical/live state wins.
Older UAB/project registries are advisory when newer continuity/live evidence exists.

12. NO PER-CHAT ESCAMOTAGE
Manual activation strings and handoff prompts are fallback-only aids.
They are not normal architecture and must not be presented as recurring requirements.

13. PLATFORM BOUNDARY
MotorLab can auto-bootstrap only when the execution surface exposes at least one supported signal: recognized project/workspace identity, persistent project/user instruction, project hook/repository identity, conversational context, or clear software-build intent.
A completely context-free host that exposes none of these cannot be forced by repository text alone.
Likewise, MotorLab cannot wake a host that exposes no execution cycle/callback/durable executor.
Do not falsely claim otherwise.

14. ONE-TIME HOST INTEGRATION
If a host product requires persistent project/workspace/user instructions to expose MotorLab in every new chat, that is one-time infrastructure and should point to the current hook/CORE rather than duplicate it.
It must not require Bruno to paste a prompt every time.

15. REGISTERED PROJECTS / FUTURE PROJECTS
Projects in current canonical routing/integration registry are MotorLab-managed until explicitly removed/suspended.
Future concrete software projects inherit:
- pre-response boot gate;
- visible banner;
- project hook/local satellite;
- central project continuity ledger;
- cross-chat state reconciliation;
- numeric progress visibility gate;
- Root Cause Closure;
- current Watchdog/Resume/Foreground/Progress/safety rules;
- native-engine coexistence;
- foundational Change Compatibility Guard with ONE RESPONSIBILITY = ONE ACTIVE COORDINATOR for every write-capable change.

16. FAILURE MODE
If bootstrap/continuity cannot complete because project identity, permissions or canonical state is unavailable:
- do not make risky writes based on guessed state;
- use live/local verified evidence when safe;
- preserve project/native engine/current state;
- report the real blocker and current verified percentage if one exists;
- do not declare a stale-state problem solved without root-cause closure.

17. SUCCESS CRITERIA
Auto Bootstrap is active when:
- MotorLab is the first orchestration layer engaged in every identifiable software-project session;
- the startup banner is the first user-visible line in activated project work;
- registered project chats require no activation phrase;
- new chats require no handoff prompt;
- supported-session interruption can produce RESUME_READY before Bruno sends `continua`, and `continua` consumes that prepared state rather than starting from zero;
- project continuity ledger + live evidence reconstruct the latest operation automatically;
- live event source is classified before lifecycle changes;
- the first substantive status of an active operation contains the evidence-based numeric percentage;
- stale write-through failures route through Root Cause Closure;
- same operation/progress survives chat changes;
- stale memory/registries cannot silently move work backward;
- unfinished work resumes through Resume Recovery;
- project-native engines remain intact;
- platform limits are represented honestly.
