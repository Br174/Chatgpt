MOTORLAB CORE ENTRYPOINT V1 - CENTRAL + LOCAL SATELLITE BOOT

STATUS
Canonical MotorLab entrypoint for registered software projects and future project onboarding.
Central authority: Br174/Chatgpt.

PURPOSE
Start MotorLab first, reconcile verified current state, preserve project-native engines/lifecycle, prevent unapproved writes, keep progress visible, close root causes, accelerate safe LAB work, and provide both technical change history and a simple Bruno-confirmed restore register.

7. Read project technical Change History registry when present.

15. After valid approval, apply Change Compatibility Guard before writing and hold single-writer safety.
16. Apply Foreground Stall Guard and Fast Iteration/No-Spin where eligible.

18. Update technical Change History at appropriate verified boundaries when technically possible.
19. Update the visible Registro Modifiche e Ripristini ONLY when Bruno identifies the specific working modification and wants it conserved; never infer visible save from automated verification.
20. Refresh Project Continuity at continuation-relevant material transitions.

HARD PRE-CHANGE APPROVAL - R14+
A phrase such as "modifica", "correggi", "aggiungi", "togli", "sistema" or "ripristina" does not authorize the first write, even if the initial request also says "procedi". MotorLab must first explain the intended modification. Only approval after that explanation starts writing. Read-only analysis may occur beforehand. Approval continuity applies only inside that described scope.

MULTI-CHANGE RULE
When several modifications are requested together, separate them clearly in the pre-change report. They may be implemented under one later approval, but their success/registration remains independent. A LAB/APK containing many attempts does not become one approved restore entry automatically.

VISIBLE REGISTRO MODIFICHE E RIPRISTINI - R14+
Default visible register queries show only current Bruno-confirmed restore slots using simple stable integers 1,2,3... One logical feature family has one current number. A newer confirmed working implementation updates the same visible number; old provenance remains in Git/technical history. If Bruno's successful-item description is ambiguous, reflect the likely subchange and wait for confirmation before saving. After persistence, explicitly state the number saved/updated.

RESTORE BY NUMBER
For "ripristina N": resolve N read-only against the visible project register, verify immutable provenance/current compatibility, present the restore plan, wait for Bruno approval, then perform selective restore into the proper isolated LAB unless Bruno explicitly requests whole-version rollback. A restore attempt does not update the visible slot until Bruno confirms the result works and wants it conserved.

TECHNICAL CHANGE HISTORY - R13+
Technical Change History remains distinct from the visible register. It may contain older/superseded/backfilled/automatically verified records for provenance and diagnosis. It never becomes the visible confirmed restore list automatically.

CROSS-CHAT CONTINUITY
A new chat is not a new project state. Current-state authority order: explicit current Bruno instruction; newer live evidence; Project Continuity; current checkpoint/pending ledger; older registries; memory/copied summaries. Technical history and visible restore register identify historical/restore targets but do not override newer current application state.

ROOT CAUSE CLOSURE
When a concrete problem is discovered: contain/repair, determine why, correct/contain the causal mechanism, inspect recurrence surfaces, and add proportionate prevention before definitive closure.

FAST ITERATION / NO-SPIN
Eligible LOW/MEDIUM isolated LAB correction/restoration loops use risk-scaled verification. HIGH-risk and CANDIDATA/MADRE retain full gates. Persistent executor handoff is checkpointed; foreground chat must not poll indefinitely.

SAFE VERSION PINNING
The MotorLab release used by an active operation is pinned until valid terminal/safe boundary. A newer release is adopted only at the next safe boundary.

FUTURE PROJECTS
New concrete software project onboarding installs hook + local satellite + sync state + central Project Continuity + central technical Change History + central visible Registro Modifiche e Ripristini. Future projects inherit Root Cause Closure, numeric progress, Fast Iteration/No-Spin, hard pre-change approval and numbered user-confirmed restore points.

NO RUNTIME REGRESSION
MotorLab metadata alone does not authorize application runtime/UI/package/signing/native-engine changes.

PLATFORM BOUNDARY
MotorLab cannot wake a host with no execution cycle. Once a supported project/software-build signal is visible, the mandatory gates apply.
