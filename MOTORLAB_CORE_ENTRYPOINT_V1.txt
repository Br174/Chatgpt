MOTORLAB CORE ENTRYPOINT V1 - CENTRAL + LOCAL SATELLITE BOOT

STATUS
Canonical MotorLab entrypoint for registered software projects and future onboarding.
Central authority: Br174/Chatgpt.

PURPOSE
Start MotorLab first, reconcile verified current state, prevent unapproved writes, accelerate safe artifact delivery, preserve mandatory causal closure, keep progress visible, preserve project-native engines/lifecycle, and provide technical history, persistent operational continuity, runtime diagnostics and a Bruno-confirmed restore register without conflicting sources of truth.

REGISTERED PROJECT BOOT ORDER - MANDATORY
0. Emit `⚙️ MotorLab attivo` before substantive work when project context is identifiable.
1. Read MOTORLAB_PROJECT_HOOK.txt.
2. Read .motorlab/MOTORLAB_SYNC_STATE.txt and .motorlab/MOTORLAB_LOCAL_CORE.txt.
3. Use VERIFIED local core immediately as fallback.
4. When central is available, read MOTORLAB_RELEASE_MANIFEST_V1.txt and MOTORLAB_SATELLITE_SYNC_V1.txt and safely reconcile release ids.
5. Load all manifest-required modules, explicitly including MOTORLAB_PRE_CHANGE_APPROVAL_GATE_V1.txt, MOTORLAB_ARTIFACT_FIRST_ROOT_CAUSE_V1.txt, MOTORLAB_ROOT_CAUSE_CLOSURE_V1.txt, MOTORLAB_PROGRESS_REPORTING_V1.txt, MOTORLAB_FAST_ITERATION_NO_SPIN_V1.txt, MOTORLAB_CHANGE_HISTORY_REGISTRY_V1.txt, MOTORLAB_MODIFICATION_RESTORE_REGISTER_V1.txt, MOTORLAB_AUTHORITY_DATA_OWNERSHIP_V1.txt, MOTORLAB_PERSISTENT_OPERATIONAL_STATE_V1.txt, MOTORLAB_OBSERVABILITY_DIAGNOSTICS_V1.txt, MOTORLAB_KNOWLEDGE_TOOL_ROUTING_V1.txt, MOTORLAB_LIVE_CONTROL_V1.txt, MOTORLAB_EXECUTION_CONTINUITY_V1.txt and MOTORLAB_UPDATE_FAMILY_LIFECYCLE_V1.txt.
6. Read Project Continuity ledger.
7. Read technical Change History registry when present.
8. Read visible Registro Modifiche e Ripristini when present.
9. Reconcile live repo/ref/head/provider/job/artifact evidence and reconstruct operation/progress/lock/next step.
10. When a persistent operational backend is connected, reconcile D1 current operation/checkpoint state against newer GitHub/live evidence; never let stale D1 override newer technical truth.
11. Reconcile MotorLab Live Control at boot/resume and at supported safe control points; apply presentation directives before user-visible status when supported, without interrupting in-flight work or changing write authority.
12. For ALL MotorLab-controlled modifications, reconstruct/show evidence-based numeric progress at the first available visible control point; micro-changes use opening/closing progress and an intermediate material boundary when tools/tests/writes occur.
13. Resume unfinished already-approved scope through Resume Recovery + Watchdog before unrelated writes.
14. Preserve project-native/domain engine authority and lifecycle identity.
15. For EVERY NEW write-capable application/project modification request, apply hard pre-change approval: initial mutation wording is intent only; perform read-only preparation, present the pre-change report, then wait for Bruno approval.
16. After approval apply Change Compatibility Guard + single-writer safety, then MOTORLAB_EXECUTION_CONTINUITY_V1.txt: continue the agreed operation through implementation/recovery/deploy/verification until verified completion or a genuine external blocker, without repeated intermediate confirmation requests.
17. Assign/reuse one MOTORLAB_OPERATION_ID for the logical operation and use it to correlate checkpoints, artifacts, Root Cause records and optional observability/dashboard projections.
18. For defect/regression operations that request APK/ZIP/testable artifacts, apply Artifact-First ordering: repair/contain + risk-appropriate verification + artifact delivery first when safe; defer eligible causal/prevention work into POST_ARTIFACT_ROOT_CAUSE_QUEUE.
19. Non-deferrable high-risk causes remain on the artifact critical path.
20. Apply Foreground Stall Guard and Fast Iteration/No-Spin where eligible.
21. Route optional auxiliary services through Knowledge & Tool Routing: Superpowers for methodology only, Context7 only when current/versioned documentation materially reduces uncertainty, Notion for status projection, GitBook for stable documentation.
22. Use PostHog/observability only as diagnostic evidence; absence of telemetry must not block otherwise safe work.
23. Execute continuously toward the approved outcome. Reopen the decision only for a material change to the agreed objective, an explicit protected boundary, an unrelated destructive action, or new paid usage; ordinary technical substeps do not pause execution.
24. For Android projects in update-family mode, preserve the active family applicationId/signing identity and increment versionCode for LAB aggiornamento builds; LAB -> CANDIDATA creates a new immutable family, while approved CANDIDATA -> MADRE promotes the same candidate family/source identity.
25. Update technical Change History at verified boundaries when appropriate.
26. Update visible Registro Modifiche e Ripristini ONLY when Bruno identifies a specific working modification and wants it conserved.
27. Refresh Project Continuity at material transitions, including artifact-delivered/cause-pending states.
28. Persist major operational transitions to D1 when connected; use GitHub continuity as durable backstop and KV only as reconstructible cache.

HARD PRE-CHANGE APPROVAL - R14+
A phrase such as modifica/correggi/aggiungi/togli/sistema/ripristina does not authorize the first write. Read-only preparation is allowed. Only approval after the pre-change report authorizes writing. Approval continuity applies only inside the described scope.

ARTIFACT-FIRST ROOT CAUSE - R15+
When Bruno expects an APK/ZIP/testable artifact:
- default critical path is REPAIR -> VERIFY -> ARTIFACT -> DELIVER;
- safely deferrable causal/prevention work follows afterward as the same logical operation;
- cause work is never abandoned;
- high-risk/non-deferrable causes stay before delivery when needed to trust the artifact;
- a delivered artifact/ref/checksum is preserved unchanged while Bruno tests it;
- prevention requiring new source changes occurs in a follow-up controlled LAB/ref;
- `Artefatto: 100%` may coexist with `Progresso MotorLab complessivo: <100%` while causal items remain.

MULTI-SERVICE AUTHORITY - R16+
GitHub is the durable technical source of truth. D1 is the live operational source when connected. KV is cache only. PostHog is observational evidence only. Notion and GitBook are projections. Superpowers and Context7 are advisory/subordinate tools. If sources conflict, MOTORLAB_AUTHORITY_DATA_OWNERSHIP_V1.txt decides precedence.

PERSISTENT OPERATIONAL STATE - R16+
Use D1 for active operations, approvals, checkpoints, locks, artifact workflow state and Root Cause queues when connected. Major durable boundaries still receive enough GitHub backstop to recover if D1 is unavailable. Never claim D1/KV integration is live until provider resources/bindings are actually verified.

ROOT CAUSE CLOSURE
Definitive problem closure still requires evidence-based cause handling and proportionate prevention/fallback. Symptom-only repair or artifact delivery is not `✅ Problema risolto`.

MULTI-DEFECT RULE
Several defects encountered on the way to one requested artifact do not require serial full causal archaeology before packaging when those investigations are safely deferrable. Persist each deferred item in POST_ARTIFACT_ROOT_CAUSE_QUEUE with repair/evidence/artifact/next-step provenance.

FAST ITERATION / NO-SPIN
Eligible LOW/MEDIUM LAB corrections use risk-scaled verification and rapid artifact generation. HIGH-risk and CANDIDATA/MADRE retain full gates. Durable executor handoff is checkpointed and must not cause indefinite foreground polling.

VISIBLE REGISTRO MODIFICHE E RIPRISTINI - R14+
Visible slots contain only Bruno-confirmed working modifications using stable plain integers 1,2,3... One feature family keeps one current number. Failed/unconfirmed attempts stay out.

RESTORE BY NUMBER
Resolve N read-only, verify provenance/current compatibility, present restore plan, await Bruno approval, then selectively restore into proper LAB unless whole-version rollback is explicitly requested.

CROSS-CHAT CONTINUITY
A new chat is not a new project state. Live newer evidence and Project Continuity outrank old registries/memory. When D1 is connected, verified current operational state also participates under the authority matrix. Persist artifact-delivered/cause-pending states so later cycles continue the same causal queue instead of restarting.

EXECUTION CONTINUITY
MOTORLAB_EXECUTION_CONTINUITY_V1.txt owns post-approval continuation to verified completion and permanently retires the former 10s / 20s / 1 min / 5 min approval-countdown proposal.

LIVE CONTROL
MOTORLAB_LIVE_CONTROL_V1.txt owns lightweight safe-point presentation directives. Live Control never grants write approval, never creates a second writer, never interrupts an in-flight tool/build solely for presentation, and never authorizes runtime/lifecycle changes. If the active executor did not load Live Control, report that honestly and apply the directive only at a later supported run/resume.

SAFE VERSION PINNING
The MotorLab release used by active work is pinned until a safe boundary; adopt newer releases only at verified safe boundaries.

FUTURE PROJECTS
New projects receive hook + local satellite + sync state + central Project Continuity + technical Change History + visible Registro Modifiche e Ripristini and inherit Root Cause Closure, Artifact-First ordering, dual progress, Fast Iteration/No-Spin, hard pre-change approval, r16 authority/data ownership, persistent-state fallback, observability boundaries and knowledge/tool routing.

NO RUNTIME REGRESSION
MotorLab metadata/policies do not authorize application runtime/UI/package/signing/native-engine changes outside approved scope. Instrumentation SDKs or provider bindings inside apps require normal project approval.

PLATFORM BOUNDARY
MotorLab cannot wake a host with no execution cycle or claim invisible continuation without a real durable executor.

ANDROID UPDATE FAMILY - R17+
When Bruno activates update-family mode, load MOTORLAB_UPDATE_FAMILY_LIFECYCLE_V1.txt. Do not create random package ids for later revisions of the same LAB family. Preserve stable applicationId + signing certificate, increase versionCode, use Bruno-facing "LAB NN aggiornamento" naming, create CANDIDATA as a new immutable family, and promote an approved CANDIDATA to MADRE without reconstructing app source.
