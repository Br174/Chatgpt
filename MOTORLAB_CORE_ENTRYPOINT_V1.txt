MOTORLAB CORE ENTRYPOINT V1 - CENTRAL + LOCAL SATELLITE BOOT

STATUS
Canonical MotorLab entrypoint for registered software projects and future project onboarding.
Established: 2026-09-29.
Central authority: Br174/Chatgpt.

PURPOSE
Make MotorLab start first, load from verified local/central control-plane state, continue each project from its latest verified cross-chat state, keep numeric progress visible, and close discovered problems at the causal level rather than only correcting symptoms.

REGISTERED PROJECT BOOT ORDER - MANDATORY
0. PRE-RESPONSE GATE: when registered project context is identifiable, activate MotorLab before substantive project output/work and emit "⚙️ MotorLab attivo" as the first user-visible line.
1. Read MOTORLAB_PROJECT_HOOK.txt.
2. Read .motorlab/MOTORLAB_SYNC_STATE.txt and .motorlab/MOTORLAB_LOCAL_CORE.txt.
3. If local state is VERIFIED, MotorLab is immediately available from local satellite.
4. When central access is available, read MOTORLAB_RELEASE_MANIFEST_V1.txt and MOTORLAB_SATELLITE_SYNC_V1.txt and safely reconcile release ids.
5. Load current central MOTORLAB_AUTO_BOOTSTRAP_V1.txt, MOTORLAB_GLOBAL_PERSISTENT_ACTIVATION_V1.txt, MOTORLAB_PROJECT_CONTINUITY_V1.txt, MOTORLAB_CHANGE_COMPATIBILITY_GUARD_V1.txt, MOTORLAB_ROOT_CAUSE_CLOSURE_V1.txt, MOTORLAB_FOREGROUND_STALL_GUARD_V1.txt, MOTORLAB_PROGRESS_REPORTING_V1.txt and required CORE modules.
6. Read the project-specific canonical Project Continuity ledger referenced by hook/registry.
7. Reconcile that ledger with current live repository/ref/head and relevant provider/job/artifact evidence; classify newer live events before treating them as application lifecycle changes.
8. Reconstruct active operation, current phase, progress floor, completed step, pending verification, exact next safe step and lock state.
9. If a substantial operation is active/pending/newly accepted, emit an evidence-based `Progresso MotorLab: <N>%` status before entering long/opaque work.
10. If unfinished prior controlled work exists, Resume Recovery + Watchdog continue that same logical operation before unrelated write-capable work.
11. If a real anomaly/problem or missed expected write-through is found, route definitive closure through Root Cause Closure; symptom-only repair is not enough.
12. Preserve project-native/domain engine authority and current lifecycle state.
13. Before ANY write-capable MotorLab/project change apply Change Compatibility Guard.
14. Before substantial execution apply Foreground Stall Guard.
15. Proceed with requested project work.
16. At continuation-relevant material transitions and before valid substantial-turn termination, refresh Project Continuity state when technically possible.

CROSS-CHAT CONTINUITY
A new chat is not a new project state.
Do not require Bruno to paste activation or transfer prompts.
Current-state authority order is:
- explicit current Bruno instruction;
- newer live repository/provider/job/artifact evidence;
- canonical Project Continuity ledger;
- current checkpoint/pending ledger;
- older registries;
- conversational memory/copied summaries.
Older state must never silently move the project backward when newer coherent evidence exists.
Control-plane-only events must not silently create a new application LAB/MADRE/CANDIDATA or reset an application progress scale.

NUMERIC PROGRESS VISIBILITY
For an active substantial operation, the activation banner is only the boot proof; it is not sufficient operational reporting.
After reconciliation, Progress Reporting must establish/reconstruct and display the numeric percentage before a long opaque tool/build/provider sequence.
Material provider/job phase changes must repeat or advance the percentage when the surface permits user-visible status.
Never invent advancement merely to increase the number.

ROOT CAUSE CLOSURE
When a concrete problem is discovered:
- immediate containment/repair may happen first;
- investigate why the problem occurred;
- correct or contain the causal mechanism when safe;
- check proportionate recurrence surfaces;
- add prevention/regression protection when justified;
- do not call the problem definitively solved from symptom-only repair.
MOTORLAB_ROOT_CAUSE_CLOSURE_V1.txt is controlling for this closure gate.

CHANGE COMPATIBILITY PREFLIGHT
Before the first write, determine CLEAR / COMPLEMENTARY / MERGE_REQUIRED / PRECEDENCE_REQUIRED / CONFLICT / OBSOLETE_PATH / BLOCKED_UNSAFE.
Resolve/merge/define precedence before writing; unresolved unsafe conflict blocks the write.

FALLBACK
If central access is temporarily unavailable but the project has a VERIFIED local satellite, use the local release as MotorLab fallback and reconcile live project state where possible. Do not invent missing continuity state.
If the central Project Continuity ledger is unavailable, live repository/provider evidence + existing verified checkpoints may be used conservatively until state can be synchronized.

SAFE VERSION PINNING
The MotorLab release used by an active operation is pinned until that operation reaches a valid terminal/safe boundary. A newer release is adopted only at the next safe boundary.

FOREGROUND STALL PREVENTION
Before long/risky phases classify risk, establish checkpoint/next-safe-step state, emit current numeric progress when available, prefer real persistent execution when safe/available, otherwise use bounded recoverable segments. Client UI "still processing" is not a MotorLab heartbeat.

FUTURE PROJECTS
When a new software project becomes concrete and repository integration is available, onboarding installs:
- MOTORLAB_PROJECT_HOOK.txt;
- .motorlab/MOTORLAB_LOCAL_CORE.txt;
- .motorlab/MOTORLAB_LOCAL_CORE_LAST_GOOD.txt;
- .motorlab/MOTORLAB_SYNC_STATE.txt;
- a canonical central Project Continuity ledger in Br174/Chatgpt;
and registers all pointers in the integration registry.
Future projects inherit Root Cause Closure and the numeric progress visibility gate.

HOST INSTRUCTIONS
A one-time project/user instruction may point to this entrypoint/hook. It must not duplicate the full CORE. Repeated per-chat activation or transfer prompts are fallback-only and not normal operation.

NO RUNTIME REGRESSION
MotorLab control-plane/satellite/continuity metadata do not authorize changes to application runtime, UI, package identity, signing or project-native engines.

PLATFORM BOUNDARY
MotorLab cannot activate before the host exposes any supported project/software-build signal, nor wake a host with no execution cycle. Once a supported signal is visible, pre-response activation, continuity reconciliation, numeric progress visibility and causal problem closure are mandatory when applicable.
