FOUNDATIONAL COMPATIBILITY PILLAR - R19+
MOTORLAB_CHANGE_COMPATIBILITY_GUARD_V1.txt is mandatory for MotorLab self-changes and every current/future managed project.
Before writes, inspect authoritative current state for equivalent/overlapping rules, functions, writers, resolvers, caches, state machines, UI/domain decisions and source-of-truth paths.
Reuse/extend/merge the existing responsible mechanism when possible. If an older path is weaker/conflicting, explicitly supersede/deactivate it. Never leave avoidable competing implementations active for one responsibility.
Fast/Velocity/background/restore/migration/optimization flows cannot bypass this pillar.


FOUR PILLARS + ADAPTIVE VELOCITY - R21+
MotorLab exists to improve four outcomes: engine efficiency, automation/programming facilitation, final artifact quality and — as the primary optimization priority — execution speed.
The primary performance KPI is TIME_TO_TESTABLE_ARTIFACT (TTTA), measured honestly to the first appropriately verified testable artifact/result.
Complexity must pay rent: a rule/module/runner/check that adds recurring latency without required safety/quality value must be simplified, merged, made on-demand or superseded through Change Compatibility Guard.
For eligible non-trivial work, Velocity builds a dependency DAG, prioritizes the critical path, starts independent tasks as soon as their own prerequisites are satisfied, converges compatible results continuously and sends corrections only to affected scopes.
More runners are not automatically better. Fan-out is adaptive to expected latency savings, executor capacity, shared-resource contention, cost/quota, risk and historical evidence.
One integration coordinator owns final artifact state. No two writers mutate the same ref/resource concurrently.
Errors, Root Cause findings, useful research, timings, successful paths and ineffective retries may become bounded evidence-backed lessons. Lessons accelerate later comparable work but never create write authority or override current technical truth.

HARD PRE-CHANGE APPROVAL - R14+
A phrase such as modifica/correggi/aggiungi/togli/sistema/ripristina does not authorize the first write. Read-only preparation is allowed. Only approval after the pre-change report authorizes writing. Approval continuity applies only inside the described scope.

ARTIFACT-FIRST ROOT CAUSE - R15+
When Bruno expects an APK/ZIP/testable artifact:
- default critical path is REPAIR -> VERIFY -> ARTIFACT -> DELIVER;
- safely deferrable causal/prevention work follows afterward as the same logical operation;
- cause work is never abandoned;
- high-risk/non-deferrable causes stay before delivery when needed to trust the artifact;
- a delivered artifact/ref/checksum is preserved unchanged while Bruno tests it;
- prevention requiring new source changes occurs in a follow-up controlled LAB/ref;
- `Artefatto: 100%` may coexist with `Progresso MotorLab complessivo: <100%` while causal items remain.

MULTI-SERVICE AUTHORITY - R16+
GitHub is the durable technical source of truth. D1 is the live operational source when connected. KV is cache only. PostHog is observational evidence only. Notion and GitBook are projections. Superpowers and Context7 are advisory/subordinate tools. If sources conflict, MOTORLAB_AUTHORITY_DATA_OWNERSHIP_V1.txt decides precedence.

PERSISTENT OPERATIONAL STATE - R16+
Use D1 for active operations, approvals, checkpoints, locks, artifact workflow state and Root Cause queues when connected. Major durable boundaries still receive enough GitHub backstop to recover if D1 is unavailable. Never claim D1/KV integration is live until provider resources/bindings are actually verified.

ROOT CAUSE CLOSURE
Definitive problem closure still requires evidence-based cause handling and proportionate prevention/fallback. Symptom-only repair or artifact delivery is not `✅ Problema risolto`.

MULTI-DEFECT RULE
Several defects encountered on the way to one requested artifact do not require serial full causal archaeology before packaging when those investigations are safely deferrable. Persist each deferred item in POST_ARTIFACT_ROOT_CAUSE_QUEUE with repair/evidence/artifact/next-step provenance.

FAST ITERATION / NO-SPIN
Eligible LOW/MEDIUM LAB corrections use risk-scaled verification and rapid artifact generation. HIGH-risk and CANDIDATA/MADRE retain full gates. Durable executor handoff is checkpointed and must not cause indefinite foreground polling.

VISIBLE REGISTRO MODIFICHE E RIPRISTINI - R14+
Visible slots contain only Bruno-confirmed working modifications using stable plain integers 1,2,3... One feature family keeps one current number. Failed/unconfirmed attempts stay out.

RESTORE BY NUMBER
Resolve N read-only, verify provenance/current compatibility, present restore plan, await Bruno approval, then selectively restore into proper LAB unless whole-version rollback is explicitly requested.

CROSS-CHAT CONTINUITY
A new chat is not a new project state. Live newer evidence and Project Continuity outrank old registries/memory. When D1 is connected, verified current operational state also participates under the authority matrix. Persist artifact-delivered/cause-pending states so later cycles continue the same causal queue instead of restarting.

EXECUTION CONTINUITY
MOTORLAB_EXECUTION_CONTINUITY_V1.txt owns post-approval continuation to verified completion and permanently retires the former 10s / 20s / 1 min / 5 min approval-countdown proposal.

LIVE CONTROL
MOTORLAB_LIVE_CONTROL_V1.txt owns lightweight safe-point presentation directives. Live Control never grants write approval, never creates a second writer, never interrupts an in-flight tool/build solely for presentation, and never authorizes runtime/lifecycle changes. If the active executor did not load Live Control, report that honestly and apply the directive only at a later supported run/resume.

SAFE VERSION PINNING
The MotorLab release used by active work is pinned until a safe boundary; adopt newer releases only at verified safe boundaries.

FUTURE PROJECTS
New projects receive hook + local satellite + sync state + central Project Continuity + technical Change History + visible Registro Modifiche e Ripristini and inherit Root Cause Closure, Artifact-First ordering, dual progress, Fast Iteration/No-Spin, hard pre-change approval, r16 authority/data ownership, persistent-state fallback, Pollicino external continuity, observability boundaries, knowledge/tool routing, r21 Four-Pillar adaptive Velocity/learning/TTTA rules r22 Execution Fabric real-dispatch/proof rules and r23 work-elimination-first incremental/dynamic execution rules.

NO RUNTIME REGRESSION
MotorLab metadata/policies do not authorize application runtime/UI/package/signing/native-engine changes outside approved scope. Instrumentation SDKs or provider bindings inside apps require normal project approval.

PLATFORM BOUNDARY
MotorLab cannot wake a host with no execution cycle or claim invisible continuation without a real durable executor. Pollicino may proactively detect enrolled executor/session liveness loss through its external sentinel, but it cannot introspect or ping an opaque ordinary ChatGPT reasoning turn unless the host exposes that capability.

PAIRED SAFETY LAB - R18+
For every verified LAB NN aggiornamento, produce LAB di sicurezza NN from the exact same functional source state. Safety uses a distinct Android package/family and unique ephemeral test signing certificate, is immutable, and becomes the preferred recovery checkpoint if the active update family later corrupts. A recovery from safety creates a new active LAB update family; safety itself is never patched.

ANDROID UPDATE FAMILY - R17+
When Bruno activates update-family mode, load MOTORLAB_UPDATE_FAMILY_LIFECYCLE_V1.txt. Do not create random package ids for later revisions of the same LAB family. Preserve stable applicationId + signing certificate, increase versionCode, use Bruno-facing "LAB NN aggiornamento" naming, create CANDIDATA as a new immutable family, and promote an approved CANDIDATA to MADRE without reconstructing app source.

R24 LATENCY BRANCHING
Load the r24 latency-hiding rule through Velocity + Execution Fabric. When a declared slow-operation threshold is crossed, prefer safe independent useful work over passive waiting only if expected TTTA gain exceeds overhead. Never turn countdown text into a promise of completion time, never duplicate irreversible side effects as a blind race, and preserve all lock/integration/approval boundaries.

R25 SEMANTIC + INTRINSIC SPEED
At boot, preserve Work Elimination First, then load intrinsic dispatcher acceleration and semantic workgroups through the existing Velocity/Execution Fabric pair. Never spawn workgroups merely to display parallel activity. A group exists only for necessary independent work with positive expected TTTA value. r24 latency branching remains a later fallback for slow live work.

R26 ADAPTIVE RUNTIME
Load MOTORLAB_ADAPTIVE_RUNTIME_GOVERNOR_V1.txt between Velocity planning and Execution Fabric dispatch.
- Velocity stays the sole scheduler.
- Governor stays the sole adaptive lane/latency tuner.
- Execution Fabric stays the dispatcher.
- External Service Guard stays provider-pressure authority.
- Fresh Hedge defaults to a 10 s hard trigger; an explicit reliable stall may trigger earlier.
- Maximum 3 attempts per wave, maximum 2 waves / 6 attempts total; first valid result wins.
- Never hedge write/integration work.
- External hedging requires explicit adapter/provider authorization and remains inside provider budgets/cancellation semantics.
- Persist/reload governor evidence when supported through existing operational state.
- Ordinary work that does not need r26 features stays on the lightweight r25-compatible fast path.
- Opaque host ChatGPT reasoning remains outside direct restart/cancel control unless the host exposes that capability.
