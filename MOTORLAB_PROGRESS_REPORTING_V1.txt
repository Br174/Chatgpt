MOTORLAB PROGRESS REPORTING V1 - HIGH-FREQUENCY VERIFIED STATUS

STATUS
Mandatory MotorLab CORE communication capability.
Repository authority: Br174/Chatgpt.

PURPOSE
Let Bruno follow ALL MotorLab-controlled modifications — from micro-changes to long programming, fixing, build, testing, artifact delivery and causal closure work — without invented progress or meaningless spam.

CORE PRINCIPLE
Progress represents verified completion, not elapsed time or ETA. Same-scale verified progress is monotonic unless material evidence invalidates prior work.
WHOLE-PROJECT COMPLETION PRECEDENCE: all percentages, phase milestones, reports, test passes and artifact deliveries are nonterminal unless the ENTIRE approved project outcome is verified complete. On each subtask completion, select the next ready approved dependency immediately, without ending the current turn for a status-only message. No new OK between in-scope subtasks. Respect evidenced blockers, approval gates and genuine host limits.
NON-STOP PRECEDENCE: visible progress is observational, not a completion or pause signal. Status may be shown after every meaningful operation when a non-terminal update channel exists; otherwise accumulate observations and keep executing, then report at the next available control point. No new user OK is needed between already approved steps. Emit intermediate progress only when it can be followed by continued execution in the same available turn. Never end a turn merely to show a percentage, checkpoint, heartbeat, status or Pollicino breadcrumb. Resume Recovery valid terminal states govern stopping. No 15-second or 1-3-tool stop timer exists.

ROLE / PRECEDENCE
Progress Reporting owns user-visible percentages. Visual Status owns emoji labels. Watchdog owns health/stall. Resume Recovery owns continuation. Root Cause Closure owns definitive problem closure. MOTORLAB_ARTIFACT_FIRST_ROOT_CAUSE_V1.txt owns artifact-vs-causal phase ordering.

1. NUMERIC PROGRESS - MANDATORY
For ALL MotorLab-controlled modifications establish or reconstruct a meaningful verified scale and keep `Progresso MotorLab: <N>%` visible at the available user-visible control points. This includes small and one-step changes. Repeating the same value with new state is better than inventing advancement.

2. FIRST-STATUS GATE
After the versioned first-line banner `⚙️ MotorLab rNN attivo`, if MotorLab-controlled work is active/pending/newly accepted, establish/reconstruct and display a verified percentage at the first available visible control point. Use live provider/repository/checkpoint evidence; do not reset because a chat/turn changed.

2A. RE-ENTRY PROGRESS FLOOR
Every supported project-turn re-entry preserves the same operation's verified progress floor. Re-entry, resume, compact, clear or MotorLab release refresh must not reset progress.
When active work exists, the first available visible status after re-entry uses the current verified percentage and current r31 visual/status rules.

3. LONG / EXTERNAL OPERATION VISIBILITY
Before a long build/test/provider phase show current percentage and what is starting. Report material provider/job transitions at the next available control point. Healthy durable jobs follow No-Spin rather than endless foreground polling.

4. R22 GROUPED PARALLEL STATUS
When Execution Fabric is active, do not convert parallel work into serial prose.
At useful visible control points prefer a compact grouped status:
- COMPLETATI INSIEME: verified nodes that finished since the prior status;
- IN CORSO INSIEME: currently overlapping runners/jobs/tools when observable;
- SBLOCCATI: downstream nodes made READY by completed dependencies;
- CRITICAL PATH: current artifact-blocking chain;
- MODALITA: DIRECT_FAST / PARALLEL_OBSERVED / SERIALE NECESSARIA / SERIALE LIMITATA DALL'HOST;
- observed peak runner count when evidence exists.
Do not claim PARALLEL_OBSERVED merely because r22/r23 is installed.
When r23 materially avoids work, status may also report compact evidence such as:
- RIUSO/CACHE: N task evitati;
- RAMI CREATI: N;
- RAMI POTATI: N;
- MATERIALIZZAZIONE RINVIATA when it materially reduces work.
These are execution facts, not percentage inflation.
A serial status is acceptable when dependencies or host limits require it; state the reason rather than inventing concurrency.

5. MICRO-PROGRESS / MICRO-MILESTONES
Small one-step change minimum: opening percentage + verified closing percentage.
Small change with any tool/test/write boundary minimum: opening percentage + at least one intermediate material boundary + verified closing percentage.
Longer work continues the existing high-presence verified model.
Use deterministic milestones: baseline protected, patch applied, diff/static checks, targeted tests, packaging, artifact produced, checksum/identity verified, delivery, causal items confirmed/corrected/prevention verified.
When Live Control supplies FORCE_PROGRESS_DISPLAY=ON, every user-visible active-work status at a supported control point includes numeric progress. When PROGRESS_PRESENCE=HIGH, use the micro-progress minimums above. Live directives never justify false precision.

6. DEFAULT FULL-OPERATION SCALE
5% request accepted / scope locked
15% current source/baseline identified and protected
30% requested LAB/config changes applied
45% static/source checks completed
60% preflight/cache/toolchain ready
75% build/test output completed
85% artifact verification completed
90-98% artifact delivered plus any remaining causal/prevention queue processing
100% entire requested operation verified, delivered and causally closed or explicitly terminal with stated blocker
Remap only using evidence-backed milestones.

7. DUAL PROGRESS - R15+
When Artifact-First applies, MotorLab may and should show two distinct values:
- `Artefatto: <N>%` = requested APK/ZIP/testable artifact readiness;
- `Progresso MotorLab complessivo: <N>%` = full operation including mandatory Root Cause Closure/prevention.
Artifact progress may reach 100% once the requested artifact is built, risk-appropriately verified, identified and delivered.
Overall progress MUST remain below 100% while mandatory causal/prevention items remain pending.
Example:
`🎆 Azione completata — APK/ZIP pronto e verificato per il test. Artefatto: 100%. Progresso MotorLab complessivo: 94%. Restano 2 chiusure causali.`

8. ARTIFACT DELIVERY STATUS
Artifact 100% is an intermediate milestone, not `💯 Conclusione definitiva`, whenever post-artifact causal work remains. It also does not by itself permit `✅ Problema risolto` for the underlying defect.

10. ROOT CAUSE / FAILURE
On failure preserve last verified progress unless evidence invalidates it. Successful containment/retry/artifact delivery does not equal definitive problem closure. When causal work is safely deferred, persist/report the POST_ARTIFACT_ROOT_CAUSE_QUEUE and continue overall progress from the existing recovery floor.

11. ARTIFACT IMMUTABILITY
Once Bruno receives an artifact for testing, later causal/prevention work cannot silently redefine its identity. Report follow-up builds as separate LAB/ref/artifact states.

12. MONOTONIC VERIFIED PROGRESS
Within one logical scale, later values repeat or increase unless explicit material invalidation is explained. Dual artifact/overall scales are independent but each remains monotonic within its own operation.

13. MANUAL `⚡`
Manual recovery reports the current checkpoint/pending step and preserves both artifact and overall progress when dual scales are active.

14. FINAL STATUS RULES
🎆 = a completed action/milestone; may coexist with remaining work.
✅ = underlying problem has Root Cause Closure permission.
💯 = whole requested operation fully completed, verified and causally closed; normally overall 100%.

15. NO FALSE PRECISION
Use only observable milestones. If exact percentage cannot yet be established, keep the last verified value and explain state.

16. CROSS-PROJECT / PERSISTENCE
Global across current/future MotorLab projects. Persist enough operation identity, latest verified overall progress, artifact progress when active, and pending causal queue for deterministic recovery.

17. LIVE CONTROL / LIMITATION
Progress can be reported only when the execution surface provides a control point. No invisible progress claims during a frozen host. A directive queued for an executor that did not load Live Control may apply only on a later supported safe point/run/resume; never claim it was applied without evidence.

18. NO RUNTIME REGRESSION
Reporting behavior does not authorize app/runtime/package/signing/lifecycle changes.

SUCCESS CRITERIA
- meaningful numeric progress remains visible for ALL MotorLab-controlled modifications when a visible control point exists;
- micro one-step changes show opening + verified closing progress;
- micro tool/test/write changes show opening + intermediate material boundary + verified closing progress;
- APK/ZIP can honestly be 100% while MotorLab overall remains below 100%;
- pending causal work is explicit, durable and not mistaken for completed closure;
- final/solved labels are not premature;
- percentages remain evidence-based and monotonic.
