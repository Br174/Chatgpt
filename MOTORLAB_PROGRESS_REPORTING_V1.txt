MOTORLAB PROGRESS REPORTING V1 - HIGH-FREQUENCY VERIFIED STATUS

STATUS
Mandatory MotorLab CORE communication capability.
Established: 2026-09-28.
Repository authority: Br174/Chatgpt.

PURPOSE
Let Bruno follow substantial programming, fixing, build, GitHub, testing and delivery work closely from the chat without inventing progress, exposing hidden chain-of-thought or creating message spam.

CORE PRINCIPLE
Progress percentage represents verified completion, not elapsed time, optimism or ETA.
For the same logical operation and progress scale, verified progress is monotonic unless material evidence explicitly invalidates previously counted work.
MOTORLAB_VISUAL_STATUS_V1.txt is authoritative for user-facing emoji meanings and labels.

ROLE / PRECEDENCE
Progress Reporting owns user-visible operational status and verified percentages.
Watchdog owns health/stall decisions.
Resume Recovery owns checkpoint continuation and recovery-floor reconstruction.
Visual Status owns canonical emoji + label language.
Progress Reporting describes observable actions/results/state, not hidden reasoning.

1. FREQUENT CHAT REPORTING
For substantial tasks, emit useful progress at meaningful starts/completions/phase changes, source/MADRE identification, file/change groups, static checks, build/test state, regression verification, artifact state, checkpoint advance, recovery, handoff/promotion and final delivery.

2. REPORTING DENSITY
Avoid long opaque stretches when the interface permits updates. As a practical default, after roughly 1-2 meaningful operations or material phase/status changes, provide concise status when useful. For long external work use real provider/job evidence. Do not emit repetitive messages merely because time passed.

3. SAME-PERCENTAGE STATUS
A verified percentage may repeat when new operational information exists; do not invent a higher number.
Example:
👍🏻 Procede tutto bene — Progresso MotorLab: 60%; build attiva e runner sano, percentuale invariata finché non arriva nuovo output verificato.

4. MICRO-MILESTONES
Large phases may be divided into deterministic micro-milestones: files located, patch applied, diff verified, workflow started, compilation reached, packaging reached, artifact produced, artifact identity/checksum/regressions verified. No fake increments based on time.

5. DEFAULT FULL-TASK SCALE
5% request accepted/scope locked
15% current MADRE/source identified/protected
30% requested LAB/config changes applied
45% static/source checks completed
60% preflight/cache/toolchain ready
75% build/test output completed
85% regression/artifact verification completed
95% candidate/handoff/promotion package ready
100% requested state verified and delivered
For non-build tasks remap only applicable real milestones.

6. REPORT FORMAT
Preferred format without special event:
Progresso MotorLab: <N>% — <current verified state / active action>.

When a canonical visual event applies, use:
<emoji> <canonical label> — <context>. Progresso MotorLab: <N>%.

Examples:
🎆 Azione completata — modifica applicata e diff verificato; passo ai controlli statici. Progresso MotorLab: 40%.
⚡ Risveglio / recupero — verifico lo stato reale del job senza perdere il lavoro completato. Progresso MotorLab: 60%.
⚠️ Piccolo problema risolvibile — manca un prerequisito circoscritto; il sorgente già verificato resta valido. Progresso MotorLab: 60%.
🧭 Cambiare approccio — due tentativi equivalenti non hanno prodotto progresso; passo a una strategia diversa mantenendo il checkpoint. Progresso MotorLab: 60%.

7. VISUAL LABEL RULE
Every canonical status emoji emitted by MotorLab must include its canonical label beside it. Do not emit bare canonical status emoji or abbreviated unlabeled forms.
The canonical legend is:
⚙️ MotorLab attivo
🎆 Azione completata
⚡ Risveglio / recupero
✅ Problema risolto
👍🏻 Procede tutto bene
⚠️ Piccolo problema risolvibile
🧭 Cambiare approccio
🛑 Stop di sicurezza / blocco reale
♻️ Una parte va rifatta
💀 Tutto da rifare
💯 Conclusione definitiva

8. LONG WAIT / EXTERNAL JOB
When a long job stays in the same percentage band:
- report provider/job phase when it materially changes;
- if no material progress crosses Watchdog thresholds, use the labeled recovery/health status;
- do not increase percentage because time passed;
- do not show 100% until requested output/state is verified.

9. FAILURE / RECOVERY
On failure retain last verified percentage unless material evidence invalidates it. State the failing phase/substep. Recovery itself does not increase progress unless it completes a real milestone. Older checkpoints are not evidence for discarding newer verified progress.

10. MONOTONIC VERIFIED PROGRESS
Within the same logical operation/scale:
- once a percentage is reported as verified, it participates in recovery-floor evidence;
- later normal/recovery status may repeat or increase it, but must not silently display a lower value;
- reconcile checkpoint percentage, current ledger, latest visible verified percentage and current provider/job/ref/artifact evidence before showing recovery progress;
- prefer the highest coherent verified value as recovery floor when sources differ;
- lower progress only with material invalidation evidence or a genuinely new approved operation/progress scale.
Any real invalidation must be explained visibly.

11. MANUAL `⚡`
If Bruno sends `⚡`, the resulting cycle reports using:
⚡ Risveglio / recupero — <current recovery status, checkpoint/pending step and preserved progress when relevant>.
Do not answer with a bare lightning symbol.

12. ACTION / PROBLEM / FINAL COMPLETION
🎆 Azione completata is for one completed action/phase/milestone; more work may remain.
✅ Problema risolto is for a previously identified problem that has now been corrected and verified.
💯 Conclusione definitiva is reserved for the whole user-requested operation being fully completed, verified and closed.
A single build, patch, commit, test or milestone never earns 💯 by itself unless it was genuinely the entire request.

13. PARTIAL / FULL REDO
♻️ Una parte va rifatta means only a bounded portion must be rebuilt while valid work remains preserved.
💀 Tutto da rifare is exceptional and requires evidence that the current overall implementation/approach is materially unusable. Never use it for an ordinary failed substep.

14. NO FALSE PRECISION
Intermediate values come from known completed micro-milestones, not arbitrary guesses. If only broad milestones are observable, keep the broad percentage and provide richer text.

15. CROSS-PROJECT / PERSISTENCE
This rule is global across all current/future MotorLab projects. Persist enough operation identity and latest verified progress metadata for recovery without relying on stale checkpoints alone.

16. LIMITATION
MotorLab can report only when the chat/orchestration surface allows a visible update. If an underlying call is fully frozen with no control surface, status appears at the next available control point.

17. NO REGRESSION
This is reporting/control-plane behavior only and must not alter app logic, UI, package identity, signing, source lineage, lifecycle or release behavior.

SUCCESS CRITERIA
Progress Reporting is active when operational status remains visible, verified percentages are evidence-based/monotonic, recovery does not silently regress progress, and all canonical status emoji use their permanent readable labels with 💯 reserved for true final verified closure.
