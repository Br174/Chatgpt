MOTORLAB PROGRESS REPORTING V1 - HIGH-FREQUENCY VERIFIED STATUS

STATUS
Mandatory MotorLab CORE communication capability.
Established: 2026-09-28.
Repository authority: Br174/Chatgpt.

PURPOSE
Let Bruno follow substantial programming, fixing, build, GitHub, testing and delivery work closely from the chat. Report enough operational state to understand what is happening without inventing progress, exposing hidden chain-of-thought or creating message spam.

CORE PRINCIPLE
Progress percentage represents verified completion, not elapsed time, optimism or ETA.
MotorLab may repeat the same verified percentage when useful if new operational information exists.

ROLE / PRECEDENCE
Progress Reporting owns user-visible operational status and verified percentages.
Watchdog owns health/stall decisions and lightning intervention level.
Resume Recovery owns checkpoint continuation.
Progress Reporting must describe observable actions/results/state, not hidden internal reasoning.

1. FREQUENT CHAT REPORTING - MANDATORY
For substantial tasks, emit useful progress when:
- work begins and scope is locked;
- source/MADRE baseline is identified;
- a meaningful subtask starts/completes;
- phase changes;
- a file/change group is applied;
- static/source checks start/complete;
- preflight/toolchain/cache state changes;
- build/test job starts/changes/completes/fails;
- regression verification advances;
- artifact is created/discovered/verified;
- checkpoint advances;
- preventive Watchdog health check is surfaced;
- Watchdog intervention/recovery occurs;
- handoff/candidate/promotion changes;
- final delivery completes.

2. REPORTING DENSITY / LIVE-LIKE OPERATIONAL VISIBILITY
During active substantial work, avoid long opaque stretches when the interface permits updates.
As a practical default, after roughly 1-2 meaningful tool/operation interactions, or whenever phase/status materially changes, provide a concise update if one has not just been given.
For long external operations, use real provider/job state when available.
Do not emit repetitive messages merely because time passed.

The goal is "live-like operational visibility": what is being done, what was verified, what is next, and whether progress is healthy.
Do NOT expose private chain-of-thought, hidden scratch reasoning, or token-by-token internal deliberation.

3. SAME-PERCENTAGE STATUS IS ALLOWED
If there is useful new operational information but no newly verified completion, repeat the same percentage with a fresh explanation rather than invent a higher value.
Example:
Progresso MotorLab: 60% — build avviata; il runner è attivo. La percentuale resta al 60% finché non ho un output verificato.

4. MICRO-MILESTONES
Large phases may be divided into deterministic micro-milestones, e.g. files located, patch prepared, patch applied, diff verified; workflow started, toolchain ready, compilation reached, packaging reached, artifact produced; artifact identity/checksum/regressions verified.
No fake increments based on time.

5. DEFAULT FULL-TASK SCALE
5% request accepted / scope locked
15% current MADRE/source identified and protected
30% requested LAB/config changes applied
45% static/source checks completed
60% preflight/cache/toolchain ready
75% build/test output completed
85% regression/artifact verification completed
95% candidate/handoff/promotion package ready
100% requested state verified and delivered
For non-build tasks, remap only applicable real milestones.

6. REPORT FORMAT
Preferred concise format:
Progresso MotorLab: <N>% — <current verified state / active action>.

May combine with visual language:
🎆🎆 Progresso MotorLab: 40% — modifica applicata e diff verificato; passo ai controlli statici.
⚡ Progresso MotorLab: 60% — controllo anti-stallo: verifico lo stato reale del job; il lavoro completato resta preservato.

7. PREVENTIVE WATCHDOG VISIBILITY
A Watchdog preventive health check may be visible even before a hard stall when there is meaningful reason to verify progress.
Use current verified percentage when available.
Example:
⚡ Progresso MotorLab: 55% — controllo che questa fase stia producendo progresso reale; verifico stato e fingerprint senza interrompere il lavoro.
If the check confirms healthy progress, continue normally; do not dramatize it as a failure.

8. LONG WAIT / EXTERNAL JOB
When a long job remains in the same percentage band:
- report provider/job phase when it materially changes;
- if no material progress beyond Watchdog threshold, use lightning + status;
- do not increase percentage because time passed;
- do not show 100% until requested output/state is verified.

9. FAILURE / RECOVERY
On failure retain last verified percentage unless evidence invalidates it.
State failing phase/substep.
When recovery succeeds, report what was recovered and the new real state.
A recovery action itself does not increase percentage unless it completes a real milestone.

10. MANUAL `⚡` STATUS
If Bruno sends `⚡`, the resulting Watchdog/Resume Recovery cycle should report concise status including current verified percentage when available, checkpoint/pending step when relevant and the action being taken.
Do not answer with a bare lightning symbol.

11. RELATION TO FIREWORKS
Fireworks mark verified success; percentage shows overall completion.
Use both when useful; do not turn every update into fireworks.

12. NO FALSE PRECISION
Intermediate values come from known completed micro-milestones, not arbitrary guesses.
If only broad milestones are observable, keep broad percentage and provide richer text.

13. CROSS-PROJECT / PERSISTENCE
This rule is global across all current/future MotorLab projects. Project adapters may define finer milestones but may not suppress useful progress visibility.

14. LIMITATION
MotorLab can report only when the chat/orchestration surface allows a user-visible update. If an underlying model/tool call is fully frozen with no control surface, it cannot inject an update inside that frozen call. Watchdog/checkpoint/Resume Recovery apply at the next available control point.

15. NO REGRESSION
This is reporting/control-plane behavior only and must not alter app logic, UI, package identity, signing, source lineage, lifecycle or release behavior.

SUCCESS CRITERIA
Progress Reporting is active when:
- substantial work shows operational status throughout, not only near the end;
- default density is roughly every 1-2 meaningful operations/phase changes when useful and possible;
- same percentage may repeat with real new information;
- preventive Watchdog checks can appear with lightning and verified percentage;
- no hidden chain-of-thought is exposed;
- no time-based fake progress occurs;
- 100% remains reserved for verified requested completion.
