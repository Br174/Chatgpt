CHAT CONTEXT GUARD — TARGET-OF-CHANGE ROUTING (APPROVED 2026-10-12; PROPOSAL BRANCH)
Sole owner of chat/project target routing: THIS UAB_PROJECT_ROUTING contract. Reuse MotorLab's existing Auto Bootstrap for activation and Re-entry Gate for per-turn checks; Change Compatibility Guard remains the sole pre-change compatibility authority. This rule does NOT add a scheduler, process, independent classifier service, database, or second chat state ledger.

CORE IDEA
Classify the effective TARGET of the requested change, not whether the user mentions or asks to USE MotorLab as the shared orchestrator.

ROUTING DECISION
1. Detect CURRENT_CHAT_PROJECT from the reliable identifiable conversation/workspace/project context; do not confuse GitHub repo used as a TOOL (Br174/Chatgpt) with the user's project conversation.
2. Detect CHANGE_TARGET from the substance of the user request:
   A. MOTORLAB_CORE_SELF_CHANGE = add/change/remove central MotorLab governance, scheduler, release/fanout rules, CORE architecture, canonical cross-project policy or central implementation.
   B. CURRENT_PROJECT_CHANGE = use MotorLab to build, configure, accelerate, test or modify the current project's app, domain engine or authorized local satellite/adapter.
   C. OTHER_PROJECT_CHANGE = change a different project's app/native/satellite rather than the current chat's project.
   D. EXPLANATION_ONLY = ask about MotorLab or another project without a change request.
3. If CURRENT_CHAT_PROJECT is reliable and CHANGE_TARGET is MOTORLAB_CORE_SELF_CHANGE while current chat is NOT MotorLab's canonical administration conversation: show a short polite recommendation to use the dedicated MotorLab chat BEFORE any CORE mutation. Do not falsely claim that ChatGPT can automatically move or rename conversations.
4. If CHANGE_TARGET is CURRENT_PROJECT_CHANGE: DO NOT WARN merely because the user says "MotorLab", uses its capabilities, or an authorized local MotorLab satellite/adapter is involved.
5. If CHANGE_TARGET is OTHER_PROJECT_CHANGE: recommend the target project's chat; do not apply writes to the wrong project just because MotorLab is shared.
6. If CHANGE_TARGET is EXPLANATION_ONLY: do not warn. If identity/target remains uncertain, do not manufacture a mismatch; request clarification only where needed for safe write routing.
7. EXPLICIT VOLUNTARY CHAT TRANSFER: If Bruno intentionally moves an existing approved MotorLab operation to a new chat, accept that as the canonical user-facing continuation for that operation after reconciling its real operation_id, approvals, locks, release pin and latest checkpoint. Do not re-run already completed steps, duplicate writers or force a return to an abandoned chat.

NO REGRESSION / BOUNDARIES
- Chat guidance is a recommendation, not a platform-level control, migration or mandatory roadblock.
- The GLOBAL SINGLE-CHAT PRINCIPLE still governs a project's ongoing user-facing thread; a background executor does NOT require chat migration.
- The canonical MotorLab administration chat is for MotorLab CORE self-changes. MotorLab is used routinely INSIDE every project chat.
- Chat context routing never grants modification approval or changes protected native engines, signing, update families or LAST_GOOD.
- In surfaces without accessible chat/project identity or prompt callbacks, this rule is applied at the next available supported reasoning/control point; do not claim independent 24/7 ChatGPT UI monitoring.
- The canonical authority for implementation/rule overlap remains MOTORLAB_CHANGE_COMPATIBILITY_GUARD_V1.txt, including IDENTICAL / CONTRADICTORY / COMPLEMENTARY and old-path retirement tests.

GLOBAL ROUTING RULES
1. Re-check repository visibility before a build.
2. Public build projects -> standard GitHub Actions is default remote compiler/test runner and is a durable background executor for supported build/test phases.
3. Private build projects -> conserve included quota; no automatic paid fallback. Durable runner/local worker may be used only when adapter-approved and available.
4. Codemagic is REMOVED from MotorLab and must not be used as primary, fallback or emergency route.
5. If an allowed route is unavailable, stop and report the blocker rather than switching to an unauthorized provider automatically.
6. Project-specific workflows are adapters/mechanics only and cannot override lifecycle/promotion rules.
7. A normal ChatGPT turn alone is never considered a durable background route.
8. Background-capable work is routed proactively before a long foreground phase; do not wait for Bruno to leave the app.
9. Reopening the canonical project chat first reconciles active job/lock/checkpoint state before starting new writes.
10. Executor migration must not force routine user chat migration.

GLOBAL BACKGROUND RULE
1. Canonical user surface = current project chat.
2. Execution may move among adapter-approved durable executors behind the scenes.
3. While Bruno is away, a durable RUNNING job continues through approved autonomous steps and saves checkpoints.
4. Checkpoint is safety, not pause-on-exit.
5. If the executor stops/quota ends, continue from checkpoint on another approved route when safe; otherwise WAITING_EXTERNAL/WAITING_USER.
6. Never claim background continuity unless a real durable executor is active.
7. Detailed contract: MOTORLAB_BACKGROUND_EXECUTION_V1.txt.

GLOBAL EXACT-PROMOTION RULE
1. LAB = current MADRE + one requested modification (or one small inseparable change-set).
2. CANDIDATA = exact same MADRE + exact same approved LAB change-set, rebuilt fresh rather than renamed from LAB.
3. NEW MADRE source ref = exact approved CANDIDATA source SHA after explicit approval.
4. If this identity chain cannot be proven, promotion stops.

GLOBAL RELEASE RULE
Permanent Release = approved MADRE. LAB and CANDIDATA use temporary test artifacts. Never overwrite an existing MADRE release asset/tag. A latest pointer may identify the newest immutable MADRE but may not replace historical storage.
