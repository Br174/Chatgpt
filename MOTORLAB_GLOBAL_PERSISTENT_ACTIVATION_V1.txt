MOTORLAB GLOBAL PERSISTENT ACTIVATION V1

STATUS
Mandatory MotorLab CORE scope and activation contract.
Established: 2026-09-29.
Repository authority: Br174/Chatgpt.

PURPOSE
MotorLab is a persistent shared orchestration layer for Bruno's software projects. It must activate automatically whenever a supported project/software-development signal is available and must not depend on recurring activation or chat-transfer prompts.

1. GLOBAL SCOPE - MANDATORY
MotorLab applies to:
- every current project in Bruno's project ecosystem where project work is performed;
- every future project from its first recognizable project session, whether or not it has already been registered with MotorLab;
- every chat whose practical purpose is active software creation/development/modification/testing/build/release/maintenance;
- every new chat inside a recognized project, even when the first message is short or contains no build keyword.

2. PRE-RESPONSE ACTIVATION GATE - MANDATORY
When a supported activation path is visible, MotorLab must activate BEFORE any substantive project answer/tool/write/build/technical plan.
The first user-visible line of activated project work must be the Session Boot Banner.
Do not defer MotorLab activation until after project work has already started.

Activation precedence:
A. any recognizable current/future Bruno project context -> immediate implicit activation;
B. if not yet registered, immediate MotorLab activation + automatic onboarding before substantive project work;
C. clear software-build intent outside an already recognized project -> immediate implicit activation + onboarding;
D. otherwise inactive until a supported project/software signal exists or explicit invocation occurs.

3. PERSISTENT PROJECT ACTIVATION
A recognized project context alone is sufficient.
Bruno must not repeat intent, paste "ATTIVA MOTORLAB", or paste a transfer prompt.
The bootstrap must load current hook/satellite/CORE and Project Continuity automatically.

4. CROSS-CHAT PROJECT CONTINUITY - MANDATORY
Each registered project has a canonical Project Continuity ledger in Br174/Chatgpt.
A new chat must automatically load that ledger, reconcile it with newer live repository/provider/job/artifact evidence, reconstruct the same logical operation/progress/next step, and route unfinished work through Resume Recovery.
A new chat id is not a new project state and not a reason to restart from an older summary.

5. WRITE-THROUGH CONTINUITY
Continuation-relevant project changes must update the central project ledger at safe material boundaries and before valid substantial-turn termination when technically possible.
This replaces recurring manual handoff prompts as the normal continuity mechanism.

6. FUTURE PROJECT ONBOARDING
Every future project must be treated as MotorLab-managed from its first recognizable project session. When technically applicable it must:
- receive MOTORLAB_PROJECT_HOOK.txt/local satellite;
- be added to canonical routing/integration state;
- receive a central Project Continuity ledger;
- inherit the current CORE rather than a frozen copy;
- preserve project-native/domain engines;
- inherit Watchdog, Resume Recovery, Foreground Stall Guard, Progress Reporting, checkpoint, single-writer, regression, background execution, External Service Guard and Velocity rules.

7. VISIBLE ACTIVATION PROOF
A successful activation must visibly identify MotorLab AND the pinned release version according to MOTORLAB_SESSION_BOOT_BANNER_V1.txt.
If the banner does not appear, Bruno must not be expected to assume MotorLab is active.

8. PROJECT-NATIVE ENGINE COEXISTENCE
MotorLab is orchestration/control-plane and always coexists with project-native/domain engines. It must never replace, disable, absorb or rewrite them merely because MotorLab is active.
Project Continuity must restore this relationship on new-chat boot.

9. NO RECURRING MANUAL TRIGGER / HANDOFF
"ATTIVA MOTORLAB" and copied chat-transfer prompts are fallback-only compatibility aids.
They are not normal architecture and must never be presented as required per-chat steps.

10. AUTHORITY ORDER FOR NEW CHAT
For current project state use:
1. explicit current Bruno instruction;
2. live repo/provider/job/artifact evidence;
3. canonical Project Continuity ledger;
4. current checkpoint/pending ledger;
5. older registries;
6. conversational memory/copied summaries.
Older state must not move work backward when newer evidence exists.

11. PLATFORM BOUNDARY
A repository cannot inject itself into a completely context-free host that exposes no project identity, persistent user/project instruction, memory/global trigger, repository identity or software-build intent.
Where any supported signal is exposed, MotorLab must activate automatically.
MotorLab also cannot force a new assistant turn while the host exposes no execution cycle/callback/durable executor.

12. PERMANENCE
This rule is permanent until Bruno explicitly supersedes it. It applies to current/future projects and future project chats.

13. SUCCESS CRITERIA
Correct implementation means:
- MotorLab starts before substantive software-project work;
- registered projects auto-activate by context alone;
- new build/development chats auto-activate by intent;
- no recurring activation prompt is required;
- no recurring chat-transfer prompt is required;
- new chats reconstruct the latest verified project state from continuity ledger + live evidence;
- unfinished work continues through Resume Recovery;
- native engines remain intact;
- platform limitations are represented honestly.
