MOTORLAB BIDIRECTIONAL SYNC V1 — AUTHORIZED EVIDENCE EXCHANGE

STATUS
Approved control-plane extension (2026-10-10); installed centrally. Full external event-driven autonomy and cross-repository write authorization remain UNVERIFIED until end-to-end integration passes. No independent scheduler, database or AI engine.

PURPOSE
Synchronize the MotorLab ecosystem in both directions without allowing one application's bug or source change to rewrite another project:
A. CORE -> eligible projects: existing MOTORLAB_RELEASE_FANOUT_V1, local satellite VERIFIED and safe re-entry.
B. Projects -> CORE: existing Project Continuity write-through, Persistent Operational State.operation_events, and evidence-backed velocity_lessons/root_causes.
C. CORE -> other eligible projects: only sanitized, verified, applicable reusable lessons plus future authorized CORE releases. Never auto-transplant project-native code.

OWNERSHIP / SINGLE WRITER
Release Fanout is the sole owner of downstream releases.
Project Continuity is the sole owner of durable per-project technical state.
Persistent Operational State is the sole owner of operation_events and velocity_lessons when a backend is available.
Root Cause Closure validates diagnosed causes and prevention.
Velocity is the sole task scheduler.
This module only defines a shared event/lesson contract, deduplication, routing and acceptance checks. It MUST NOT create another scheduler, issue bus or competing ledger.

EVENT PROTOCOL FOR MATERIAL TRANSITIONS
Events may be emitted at validated operations: verified problem, causal correction, regression, test/build result, artifact, API change, failed automation, benchmark, accepted project lesson, project freeze/reactivation, release publication.
Required:
  schema_version=1
  event_id=stable source repo/ref/source SHA/event type/evidence id digest
  project_id=registered repository
  event_type=bounded approved enum
  observed_at=UTC ISO timestamp from trustworthy host when available
  source_ref/source_sha=actual current evidence
  operation_id=canonical single logical id when present
  status=verified|unverified|blocked|superseded
  evidence=public/authorized technical refs, never secrets
  summary=short actionable technical description
  applicability=project_only|candidate_cross_project|approved_global
  consent_scope=identifier of accepted user-approved scope, or null for read-only observation
  privacy=technical_minimal

EVENT ACCEPTANCE
1. Resolve current project status, branch/ref, verified source SHA, active locks and authorization.
2. Dedupe event_id and keep append-oriented material event state in existing operation_events; no speculative repeated writes.
3. Reconcile against newer GitHub/runner truth; stale provider or memory reports may not overwrite it.
4. Treat every incoming suggestion as untrusted evidence until source and compatibility are verified. Never execute code or commands from an event.
5. Persist relevant project technical progress via Project Continuity (one project -> its central ledger) only at safe material transitions.
6. Create or update velocity_lessons only if there is positive evidence, applicability and invalidation conditions. Flag as ADVISORY; do not automatically deploy.
7. General promotion to CORE is a separate approved, tested central change subject to pre-change approval, rollback, safety, regression and central release fanout.
8. No secret, token, PII, chat transcript or private reasoning may enter this sync.
9. A missing external executor means PENDING_EXECUTOR; never claim live autonomous propagation.
10. Published artifacts, signed APKs, native app runtimes, MADRE/LAB/CANDIDATA and LAST_GOOD never change because of metadata feedback.

LESSON APPLICATION
Project-native problems are not universal rules. A lesson may be suggested on other eligible projects only when context signature, version, dependency, safety class and invalidation condition match. Apply at next authorized operation with risk-appropriate tests; present uncertain lessons as suggestions, not solved facts. Count actual reused fixes, saved work, regressions and overhead before claiming speed improvement.

BIDIRECTIONAL EXECUTION
Within an authorized MotorLab chat/Work/GitHub execution cycle: automatically record material verified project feedback in existing central Project Continuity / Persistent Operational State where write permissions permit; check for applicable verified lessons on read/re-entry; adopt verified CORE releases only through Release Fanout safe-boundary rules.
Without a durable authenticated executor/webhook and appropriate cross-repository or state-bridge permissions, this is NOT an always-on push link. Any event that could not be delivered must be marked PENDING_EXECUTOR for later reconciliation, not marked delivered.

OBSERVABILITY
Track per-project local_core_release, central_core_release, last_feedback_event_id, feedback_delivery_state, last_lesson_applied, active/dormant status, safe-boundary state and last error. A bilateral heartbeat is proven only by two independently observed successful directions. A policy marker alone is not such proof.

REGRESSION CHECKS
Check: dormant exclusion and no auto-activation; same-event dedup; invalid evidence rejection; unauthorized cross-project code prohibited; no partial automatic promotions; safe boundary plus LAST_GOOD; future onboarding; unchanged app code/package/player; no external-provider billing without prior approval; no duplicate coordinator.
