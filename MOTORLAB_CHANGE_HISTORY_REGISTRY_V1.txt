MOTORLAB CHANGE HISTORY REGISTRY V1 - TECHNICAL SEMANTIC PROVENANCE INDEX

STATUS
Mandatory MotorLab CORE technical-history capability.
Central authority: Br174/Chatgpt.

PURPOSE
Maintain a durable Git-backed semantic index of project modifications for provenance, diagnosis, historical search and selective reconstruction. This is the TECHNICAL history layer, not the r14 user-visible Registro Modifiche e Ripristini.

CORE PRINCIPLE
GIT IS THE IMMUTABLE SOURCE; THIS REGISTRY IS THE TECHNICAL SEMANTIC INDEX.
Exact restore provenance must resolve to real repository refs/commits/trees/files.

R14 TWO-LAYER SEPARATION
- MOTORLAB_CHANGE_HISTORY_REGISTRY_V1.txt + project MOTORLAB_CHANGE_REGISTRY_* files may contain verified, historical, superseded, automatically captured or backfilled technical records.
- MOTORLAB_MODIFICATION_RESTORE_REGISTER_V1.txt + project visible restore-register files contain only Bruno-confirmed working restore points he wants conserved.
- A technical record never becomes a visible numbered restore point automatically.
- When Bruno asks for the ordinary "Registro Modifiche e Ripristini", show the visible r14 register, not this technical archive.
- This technical registry remains available when Bruno asks to search old history, diagnose provenance, or when a visible restore slot needs its exact Git source.

PROJECT TECHNICAL REGISTRY
Each MotorLab-managed project has one canonical central technical change registry, normally MOTORLAB_CHANGE_REGISTRY_<PROJECT>_V1.txt.

TECHNICAL RECORD FIELDS
When available: CHANGE_ID, PROJECT/REPOSITORY, DATE, TITLE, SEMANTIC_TAGS/ALIASES, USER_INTENT, CHANGE_SCOPE, lifecycle identity, source base/ref/SHA, result ref/SHA, implementation commits, changed files/hunks, behavior summary, verification evidence, technical STATUS, supersedes links, restore hints and source confidence. Never store secrets.

TECHNICAL WRITE-THROUGH
At verified material boundaries MotorLab may append/update technical history records automatically when useful and write access exists. This does NOT mean Bruno approved the change as a visible restore point.

SEMANTIC SEARCH
Search title/tags/intent/behavior/files. Prefer exact semantic matches. Reconcile a candidate against immutable Git before restoration. If several materially different technical records match and Bruno has not disambiguated, show concise choices only when he is searching technical history; do not inject them into the visible confirmed register.

HISTORICAL BACKFILL
Pre-r13 work can be backfilled from verified Git/ledger evidence on demand. Do not perform unbounded archaeology on every boot. Persist verified backfill so later technical searches are faster.

SELECTIVE RESTORE PROVENANCE
Technical history provides exact source identity for restore/reconstruction. Default feature restoration preserves the current proper baseline/unrelated newer work, uses the smallest safe patch/hunk/file scope, runs Change Compatibility Guard and lifecycle protections, and never direct-edits MADRE. Whole-version rollback requires explicit whole-version intent.

R14 APPROVAL INTERACTION
Any restore write, whether selected from visible register or technical history, must pass MOTORLAB_PRE_CHANGE_APPROVAL_GATE_V1.txt: resolve/analyze read-only, show the proposed restore plan, then wait for Bruno's post-plan approval before writing.

COMPOSITE SAFETY
A composite commit/LAB must not replay unrelated subfeatures when a safe scoped boundary exists. If safe separation cannot be proven, explain the ambiguity before any restore write.

REGRESSION LINKING / ROOT CAUSE
When a later change regresses an earlier behavior, preserve technical provenance and link the incident/earlier record. Restoration alone does not close Root Cause Closure.

HISTORY PRESERVATION
Do not delete technical records merely because they are superseded, rejected or no longer visible. Git/technical history is the audit trail; the r14 visible register stays short by pointing only to the latest Bruno-confirmed working point per feature.

CURRENT/FUTURE PROJECTS
All current/future MotorLab projects inherit both layers: technical Change History and the separate user-confirmed numbered Registro Modifiche e Ripristini.

NO RUNTIME COUPLING
Registry metadata alone must not alter app runtime/UI/package/signing/lifecycle/native engines.
